# 15 — Gap 5: Production hardening (security, upgrades and schema evolution)

This report closes a gap in reports 01–10 and in `FEATURES.md`. None of them specified authentication,
authorization, transport encryption, schema evolution of durable relations and channels, the format of
WAL and checkpoint headers across program versions, or how a Raft or Paxos cluster runs while its nodes are
on different program versions. The user asked for a "fully working production ready" system, so these are
in scope.

The report has two halves:

- **Security** (§2–§4): what the BOOM lineage and production systems do, and the model we adopt.
- **Upgrades and evolution** (§5–§6): what the literature and production systems do, and the model we adopt.

It ends with a MUST-IMPLEMENT CHECKLIST (§8) and TEST PROGRAMS (§9). Every checklist item has the ID it was
given in `FEATURES.md`. The tag for this report in `FEATURES.md` is **R15/G5**.

Syntax in the examples follows the hybrid surface recommended by ODD-01(c): Datalog atoms, Bloom arrows
(`<=`, `<+`, `<~`), named fields and typed declarations. The new keywords (`from`, `principal`, `accept from`,
`migrate from`, `emit … to`) are provisional until ODD-01 is settled. Their semantics is the normative part.

## 1. Summary of what we adopt

**Security.**
1. **Mutual TLS 1.3 on every network transport by default.** Plaintext exists only behind an explicit
   development flag, which the runtime reports. Peers and clients have separate trust roots (etcd, Flink,
   CockroachDB).
2. **Identity is bound by the runtime and never claimed in the payload.** A certificate yields a `Principal`
   (a SPIFFE URI SAN, with the CN as a configurable fallback). The node directory maps each `Node` to its
   expected principal. A frame is accepted as coming from node N only if the connection's principal is N's
   principal. Timely's self-declared worker index and Hydro Deploy's wiring-based identity are the
   anti-patterns this fixes.
3. **The receiver sees an implicit `sender` column and an implicit `principal` column.** This is SeNDlog's
   import predicate `N says p`, with hop-by-hop transport authentication in place of per-tuple signatures.
4. **Per-channel ACLs are inferred from the choreography, and the default is deny.** A channel accepts a
   message only from roles that have a rule able to send on it. Explicit ACLs can narrow or extend this.
   Module interfaces carry ACLs. Data-dependent authorization is written as ordinary rules over `principal`.
5. **Every ingress rejection is an omission.** This covers authentication, ACL, schema/version and rate
   limits. The message is dropped before the tick, counted and logged. Programs that are safe under lossy
   delivery stay safe, so CALM, LDFI and the verifiers need no new fault class. We reject SecureBlox's
   rollback of a whole transaction.
6. **External clients** get sessions, ingress/egress channels and per-principal quotas. Their channels are
   the only ones a client listener serves.

**Upgrades.**
1. **Versioned everything.** A program declares `version N`. Channels and durable relations get stable field
   numbers, recorded in a checked-in `schema.lock`. The wire handshake and every frame carry schema ids.
   WAL segments and checkpoints carry the storage format version, the program version, the catalog digest
   and per-relation schema hashes. Recovery refuses unknown schemas with a clear error.
2. **Migrations are rules** (`migrate from N { … }`) that run at recovery. The compiler classifies them as
   tuple-local, monotone or non-monotone, and this decides whether the rollout can proceed without
   coordination. A migration of a lattice column is coordination-free only if it is a lattice morphism.
3. **Cross-version channel translation is written as tuple-local rules** (`emit c to N { … }`), which are
   Ajmani's simulation objects restated as rules. A message that cannot be translated is "disallowed" and
   dropped as an omission.
4. **Understand before you speak.** A new behavior is gated on `cluster_version`, a monotone `lmax` input.
   For replicated state machines the activation is an entry in the consensus log, as with etcd's
   `ClusterVersionSetRequest`. The compiler rejects an ungated write or send of a feature introduced in the
   current version.
5. **A compatibility checker compares two versions.** Its field rules come from Protobuf and Avro, plus rules
   for keys and lattices that have no Protobuf analogue. It derives a rollout order over roles and runs in CI.
6. **Mixed-version deterministic simulation**, following Hydro's `next_version`, together with
   DUPTester-style upgrade scenarios and UpFuzz-style differential oracles.

## 2. Security in the BOOM lineage and its neighbors

### 2.1 Binder (DeTreville, IEEE S&P 2002)

- Every component has its own local **context**, running its own Binder program. "Each Binder context has its
  own cryptographic key pair; the exporting context uses the private key … to sign statements, and the
  corresponding public key … also serves to name the context, as in SDSI/SPKI."
- A fact, rule or derivable atom can be exported into a signed certificate. When another context imports it,
  it is "automatically quoted using says". Example: `rsa:3:c1ebab5d says employee(john_smith, bigco).`
- The importing context decides whether to trust the statement, with a rule such as
  `employee(X, bigco) :- rsa:3:c1ebab5d says employee(X, bigco).` "In the absence of any such rule, the
  imported statement will by default be inert."
- **Monotonicity and revocation (§6).** "Binder is monotonic … One consequence of monotonicity is that
  traditional certificate revocation cannot be modeled from inside Binder." The paper studies three remedies:
  1. short-lived statements with validity intervals that constrain the validity of derived atoms;
  2. `fresh P(X,Y)` freshness constraints;
  3. references to distributed "valid" state.
- A client can build the proof and the service only checks it. This moves work off the service and helps
  against DoS.

**Lesson for us.** Revocation is non-monotone. In CALM terms, withdrawing an authorization is a point of
order. We follow Binder's first remedy, short-lived credentials (DIST-064). Changes to ACL relations are
applied at tick boundaries and sealed per epoch, the same way as membership (DIST-042, ANA-065).

### 2.2 SeNDlog (Zhou, Mao, Loo, Abadi, ICDE 2009)

SeNDlog unifies Binder with NDlog.

- **Contexts.** Rules are written `At N, r1 p :- p1, …`. N may be a variable bound at install time.
  "Composite location specifiers" such as `Chord::K` layer overlays.
- **Definition 1.** An *import predicate* has the form `N says p` in a rule body.
- **Definition 2.** An *export predicate* has the form `N says p@X` in a rule head, and "principal N exports
  the predicate p to the context of principal X". If X is a variable, it must occur in the body. `N says` may
  be omitted when N is the local principal.
- **Definition 3, the honesty constraint.** "A SeNDlog rule in the context of principal N is honest if … the
  rule head is 'X says p' … either X is N, or 'X says p' occurs in the body of the rule." When a node
  forwards X's statement, it must forward X's signature with it.
- **Levels of says.** "`N says0 p@X` exports predicate p to X with security level 0 (which may simply involve
  a cleartext principal header with no signatures), and X can only import p … via an authentication scheme
  at the same or higher security level."
- **Execution: Authenticated PSN (APSN).**
  - Every import predicate gets its own authenticated delta rule.
  - The dataflow gains two operators. `SigGenerator` sends (p, s, t) triplets. `SigChecker` verifies s with
    p's public key and discards the tuple on failure (Fig. 1 shows a `Discard` branch).
  - "Key management is an orthogonal problem to our work."
  - HMAC is supported as a cheaper alternative to RSA.
- **Provenance leakage (§VI).** "A naïve implementation of network provenance may result in information
  leakage: the provenance of each tuple reveals information on the derivation rules used". Distributed
  provenance mitigates this, "since … the source of each rule invocation can enforce access control over
  such queries."
- **Examples.** Authenticated path-vector routing (`z1`–`z3`); Chord join through a CA-issued `nodeIDCert`
  (`ni1`–`ni3`, `ca1`, `li1`); a PIER join over Chord with *layered authentication* at either layer.

**Lessons.**
1. SeNDlog's `N says p` in a body is exactly "p was received from N". We expose it as an implicit `sender` or
   `principal` column on a received channel tuple (LANG-241). Authentication is by the transport (mTLS). In
   the crash-fault model a message is sent directly by its author, so the honesty constraint holds trivially.
2. The honesty constraint does matter when one node forwards another principal's statement, for example a
   follower forwarding a client's request to the leader. Hop authentication only proves "the follower says
   the client said X". End-to-end authenticity needs signed values (LANG-245, P2).
3. SigChecker *discards* bad tuples. This is the per-message ingress drop we adopt (§4.9).
4. Provenance must be access-controlled (DIST-069).

### 2.3 LBTrust (Marczak et al., CIDR 2009)

LBTrust implements Binder, D1LP and SeNDlog on LogicBlox. It does this with **meta-programming over a meta-model**
(`rule`, `head`, `body`, `atom`, `functor`, …), which it describes as "similar to the recently proposed Evita
Raced", plus **meta-constraints**.

- **Constraints.** `F1 -> F2` means `fail() <- F1, !(F2)`. Constraints evaluated at runtime make the whole
  evaluation fail.
- **`says` as a meta-predicate.**
  - `says0: says(U1,U2,R) -> prin(U1), prin(U2), rule(R).`
  - `says1: active(R) <- says(_,me,R).` This activates any rule that another principal said to `me`, so
    communication carries *rules* as well as facts.
- **Authorization by meta-constraint.**
  ```
  says(U,me [| A <- P(T*), A*. |]) -> mayRead(U,P).
  says(U,me [| P(T*) <- A*. |]) -> mayWrite(U,P).
  ```
- **The signature scheme is swappable.** Rules `exp1`/`exp3` use RSA. Replacing them with `exp1'`/`exp3'`
  gives HMAC: "only two rules (exp1' and exp3') need to be modified, while the trust policies that utilize the
  says predicate remain unchanged."
- **Speaks-for and delegation.**
  - `sf0: active(R) <- says(bob,me,R).`
  - `delegates(U1,U2,P)` is compiled into speaks-for restricted to predicate P.
  - Depth limits: `dd0`–`dd4`. The paper notes a limitation: a non-conforming delegation that existed before
    the depth limit was added causes a violation, but "none of the principals in the delegation chain up to
    that point will be aware of the violation."
- **Threshold trust.** Rule `wd2` counts `U` in `pringroup(U,creditBureau)` that say `creditOK(C)`, and
  `wd1` requires N ≥ 3. This is D1LP's k-of-n.
- **Evaluation.** It was preliminary: a two-principal Binder microbenchmark, plaintext vs HMAC vs RSA.

**Lessons.** Shipping *rules* between principals (`says1`) is the most dangerous feature in the lineage. It is
remote code execution by design. We do **not** allow a remote principal to install rules. Runtime rule install
(LANG-203) is an admin-plane operation only (DIST-066). Delegation and threshold trust are useful as
**library** policies (LIB-121, LIB-122). They should not be language primitives.

### 2.4 SecureBlox (Marczak et al., SIGMOD 2010)

SecureBlox extends LogicBlox with distribution and **BloxGenerics**. BloxGenerics is static meta-programming:
generic rules `<--`, code templates `` `{…} ``, variadic argument sequences `V*`, and generic constraints
`-->`, which are checked at compile time for every instantiation.

- **`says[T]` is generic.** It maps every predicate `T` to a "said" predicate `ST`:
  ```
  says[T]=ST, predicate(ST),
  `{ ST(P1,P2,V*) -> principal(P1), principal(P2), types[T](V*). }
  <-- predicate(T).
  ```
  With it, the distributed transitive closure is
  `reachable(X,Y) <- link(X,Z), says['reachable](Z,self[],Z,Y).`
- **Authorization:** `` `{ says[T](P1,P2,V*) -> writeAccess[T](P1). } <-- predicate(T). ``
- **Signatures:** a constraint `says[T](P,self[],V*) -> sig[T](P,self[],V*,S), public_key(P,K), rsa_verify[T](K,V*,S)`
  together with a signing rule. HMAC comes from swapping the functions.
- **Batching.** Footnote 2: "In practice, we have found it useful to sign aggregates of serialized facts, rather
  than signing individual tuples, as a transaction may result in the transit of multiple tuples to a single node."
- **Principals are distinct from nodes (§5.1).** "A principal is temporarily associated with a node through the
  `principal_node` mapping". The local principal is `self[]`. Export and import rules serialize, sign,
  optionally AES-encrypt with `secret(N,K)`, and ship over **UDP**.
- **Enforcement point (§5.2).** "SecureBlox enforces constraints by processing a batch of incoming facts from a
  remote node in a local ACID transaction that encapsulates a fixpoint computation. If a derivation in the
  transaction violates a runtime constraint, then the transaction (including the input tuples) are rolled back.
  Derivations are committed to the workspace and network messages are sent only after a transaction succeeds."
  The paper contrasts this with PSN: PSN "may send a tuple whose local transitive consequences later result in
  a local constraint violation", and without distributed transactions there is no clean way to retract it.
- **Other mechanisms:** trust delegation (`trustworthy(P)`, `trustworthyPerPred[T]`) and Tor-style onion
  anonymity (`anon_says`).
- **Evaluation (§8).** A 36-node path-vector run:
  - per-node traffic: NoAuth ≈197 KB, HMAC 223 KB, RSA 258 KB, where RSA adds "256 byte signatures per message";
  - fixpoint latency: ≈15 s NoAuth, 19 s HMAC, 25 s RSA, 26 s RSA+AES.

  The authors expect latency to fall "as we relax the ACID transactions currently executed per-message".
  For the hash join, crypto overhead grows with parallelism, because batches get smaller.

**Lessons.**
1. SecureBlox's aim is right: security policy should be decoupled from the system specification and
   reconfigurable per environment. We get it by making the transport security mode and the ACLs *deployment
   configuration and declarations*, not by rewriting the protocol rules. Raft's rules do not change between a
   test cluster and a production one.
2. **We reject tick-level rollback as the enforcement point.** Under SecureBlox's §5.2, one malformed or
   unauthorized fact rolls back the whole batch from that remote node. In our tick model a batch mixes senders
   (SEM-002 step 1), so a rollback would let one bad message suppress good ones. Worse, our ticks commit
   durable state and release outputs atomically (SEM-072). Rolling back would need a second
   staging area and would make the tick outcome depend on which messages share a batch, which breaks
   determinism reasoning. We drop at ingress per message, as SeNDlog's SigChecker does. Because loss is
   already allowed (SEM-043), dropping adds no new behaviors (§4.9). This is recorded as CR-40.
3. The measured cost of per-message signatures (latency roughly +67% for RSA in their setup) is why the
   default is a per-connection AEAD channel (TLS 1.3). Per-tuple signatures are only an opt-in value type.

### 2.5 P2/Evita SecLog, and why it was rejected

R01 §3.2 records that Evita Raced's grammar has `weak ref`/`strong ref` and `says(...)<pred>` /
`materializeSays`, "the secure-networking 'SecLog' extensions". R01 §7 lists "SecLog wrappers" among the
metaprograms Evita supported. FEATURES §12 rejects SecLog together with other P2 leftovers and puts nothing in
its place. §4.13 below is the replacement.

### 2.6 Summary: what the lineage gives us and what it lacks

| Topic | Lineage position | Our decision |
|---|---|---|
| Who sent a fact | Binder/SeNDlog `N says p`; SecureBlox `says[T](P,self[],V*)` | Runtime-populated `sender`/`principal` columns (LANG-241) |
| How authenticity is established | Per-tuple RSA/HMAC signatures (SeNDlog, SecureBlox), batched in practice | mTLS per connection (DIST-060); per-tuple `signed<T>` optional (LANG-245) |
| Authorization | Meta-constraints `mayWrite`, `writeAccess[T]` | Inferred and explicit channel ACLs (LANG-242) plus rule-level policies (LANG-244) |
| Enforcement point | SeNDlog: discard in SigChecker. SecureBlox: roll back the batch transaction | Drop at ingress = omission (SEM-090, CR-40) |
| Rule shipping | LBTrust `says1: active(R) <- says(_,me,R)` | Forbidden; rule install is admin-only (DIST-066) |
| Key management | "orthogonal" (SeNDlog) | Certificates plus directory binding (DIST-061); rotation (DIST-064) |
| Revocation | Impossible inside monotone Binder; short-lived statements | Short-lived certificates; ACL changes as epoch-sealed state (DIST-064) |
| Provenance confidentiality | SeNDlog §VI warns about leakage | Access-controlled provenance export (DIST-069) |

## 3. How production systems bind identity and authorize RPCs

### 3.1 etcd

- **Peer TLS.**
  - `--peer-client-cert-auth`: "etcd will check all incoming peer requests from the cluster for valid client
    certificates signed by the supplied CA".
  - `--peer-trusted-ca-file`.
  - `--peer-cert-allowed-cn` (since 3.3): "an exact string comparison against the certificate's Common Name".
  - `--peer-cert-allowed-hostname`.
- **Clients.** `--client-cert-auth`. "if authentication is enabled, the certificate provides credentials for the
  user name given by the Common Name field". The CN becomes the RBAC user.
- **Hardening knobs:** `--cipher-suites`, `--tls-min-version`, `--tls-max-version`. `--auto-tls` gives
  "encryption without authentication".
- **Takeaways.** Peer and client trust are separate. Identity comes from the certificate. Authorization is RBAC
  on top.

### 3.2 CockroachDB

- **Node certificates.** "the node certificate is multi-functional, as in the same certificate is presented
  irrespective of whether the node is acting as a server or client … the `node.crt` must have `CN=node`." Every
  address used to reach a node must be in the SAN. Client certificates use `CN=<username>`.
- **CA layout.** One CA by default. Optionally a split node CA and client CA ("We do not recommend … unless your
  organizational security practices mandate"). A UI certificate from a public CA is optional.
- **Rotation.** Certificates can be rotated "without restarting nodes" (docs: "Rotate Security Certificates").
- **Takeaway.** All nodes share the identity `node`. There is no per-node authorization between nodes, so any
  node certificate can act as any node. That is weaker than we want: we bind each `Node` id to its own
  principal (DIST-061).

### 3.3 Apache Flink

- "Internal connectivity" covers "all connections made between Flink processes": RPC, data shuffle between
  TaskManagers, and the blob service. It uses mandatory "mutual authentication (mTLS)".
- The recommendation is "a dedicated public/private key pair and self-signed certificate for the Flink
  deployment". If the certificate is not self-signed, "it is critical that you specify the fingerprint … to pin
  that certificate as the only trusted certificate".
- The REST endpoint "does not authenticate the client" by default. mTLS is optional there, and a sidecar proxy
  is recommended.
- **Takeaway.** Internal and external surfaces are separate. Internally every holder of the deployment
  certificate is fully trusted. There is no per-role authorization.

### 3.4 Timely Dataflow

`communication/src/networking.rs`. `start_connections` does `TcpStream::connect(address)` and then
`stream.write_u64::<ByteOrder>(my_index as u64)`. On the other side, `await_connections` reads
`let identifier = stream.read_u64::<ByteOrder>()` and files the socket under that worker index. Peer identity is
**self-declared** in the first 8 bytes of a plaintext TCP stream. There is no TLS.
`initialize_networking_from_sockets<S: Stream + 'static>` lets an embedder supply its own streams (for example
TLS), but identity is still the self-declared index.

**Takeaway.** This is the pattern to avoid. Any process that can reach the port can claim to be any worker.

### 3.5 Hydro Deploy

`hydro_deploy_integration/src/lib.rs` connects with `TcpStream::connect` or `UnixStream::connect`. There is
no TLS in the transport. The only TLS references in `hydro_deploy/core` are Terraform `hashicorp/tls` SSH keys for
cloud VMs. Sender identity (`MemberId`) comes from deployment wiring (`ServerPort::Tagged(port, tag)`), not from
cryptography.

**Takeaway.** Research dataflow systems assume a trusted network. We cannot.

### 3.6 SPIFFE X.509-SVID

"An X.509 SVID MUST contain exactly one URI SAN, and by extension, exactly one SPIFFE ID". Leaf SVIDs have
`cA=false` and must set `digitalSignature`. Validation is RFC 5280 path validation against the trust domain's
bundle, then extraction of the SPIFFE ID. The CN is not used.

**Takeaway.** The SPIFFE ID is a standard, structured principal (`spiffe://trust-domain/path`). We can encode
role and node in the path, for example `spiffe://prod.example/raft_kv/peer/n3`.

### 3.7 Biscuit tokens

- A token is an append-only chain of signed blocks (Ed25519 by default). Block 0 is the authority block.
  Attenuation blocks only add checks.
- Scoping: "by default, a block's rules and checks can only apply on facts created in the authority, in the
  current block or in the authorizer."
- Checks come as `check if`, `check all` and `reject if`. The authorizer's policies are `allow if` / `deny if`,
  and the first match wins.
- Revocation ids are block signatures. The Datalog has no negation.

**Takeaway.** Biscuit is a Datalog-native, attenuable bearer credential for external clients. It fits our
language well: token facts become tick-local input facts, and checks become rules. We make it P2 (DIST-067).

### 3.8 Comparison

| System | Transport | Peer identity source | Per-peer authorization | External clients |
|---|---|---|---|---|
| etcd | TLS, optional mTLS | Certificate (CA, optional CN/hostname allow-list) | Allow-listed CN or hostname | Certificate CN or password becomes the RBAC user |
| CockroachDB | TLS 1.3 mTLS | Certificate with `CN=node` | None between nodes (all are "node") | CN becomes the SQL user |
| Flink | mTLS internally | Shared deployment certificate | None | REST: none by default |
| Timely | Plain TCP | Self-declared u64 | None | n/a |
| Hydro Deploy | Plain TCP/Unix | Deployment wiring | None | n/a |
| **bloom-remake** | mTLS 1.3 (DIST-060) | SPIFFE/CN principal bound to `Node` (DIST-061) | Inferred channel ACL plus rules (LANG-242/244) | Sessions and principals (LANG-243, DIST-065) |

## 4. The security model for bloom-remake

### 4.1 Threat model and non-goals

**In scope:**
- A network attacker who can read, inject, replay or alter traffic.
- An unauthenticated party that reaches a node's port.
- An authenticated but under-privileged party, such as a client, or a node of another role or another
  program, sending on a channel it has no business using.
- An authenticated client that puts someone else's identity in a payload field.
- A misconfigured ACL or expired certificate. This is a liveness risk, and it must be visible.

**Out of scope (non-goals for v1):**
- A Byzantine (compromised) cluster node. SEM-074 already excludes Byzantine faults. Least-privilege ACLs limit
  what such a node can reach; they do not make it harmless.
- Side channels.
- Volumetric DoS beyond per-principal quotas and handshake limits.
- Encryption at rest is P2 (DIST-068).

### 4.2 Identities

| Type | What it is | Who assigns it |
|---|---|---|
| `Node` (LANG-022) | A routable location of the program: a logical node id | Deployment (DIST-041/042) |
| `Principal` (LANG-240) | An authenticated identity, e.g. `spiffe://td/prog/role/n3` or `spiffe://td/clients/alice` | Certificate or token, verified by the runtime |
| `Role` | A location role from the choreography (LANG-009/153): `peer`, `leader`-capable, `client`, … | Compiler (projection) plus deployment |
| `Session` (LANG-243) | One external client connection | Runtime |

The **directory** (DIST-004) is extended. Each row is `node(Node, Address, Principal, Role)`. It is a `static`
relation in the static-membership case and an epoch-sealed relation in the dynamic case (DIST-042).
`principal_of(n)` and `role_of(n)` are built-in lookups over it. This is SecureBlox's `principal_node`, turned
around and made authoritative.

### 4.3 Transport (DIST-060)

- **TLS 1.3 with mutual authentication** on every TCP and QUIC transport, using rustls. The in-process and
  simulator transports have no TLS. Identity there is by construction (§4.10).
- **Production mode refuses to start** if any network listener is plaintext. Development mode allows plaintext
  but sets a gauge `security_mode{mode="insecure"} = 1` and logs a warning at every startup. This is SeNDlog's
  `says0` (a cleartext principal header), confined to development.
- **Two listeners with two trust roots.** The **peer listener** needs a client certificate from the peer CA and
  serves peer channels only. The **client listener** needs a client certificate from the client CA, or TLS with
  server authentication plus a token (DIST-065, DIST-067), and serves external-ingress channels only.
- **Principal extraction:** exactly one SPIFFE URI SAN (SPIFFE rules). As a configurable fallback, the CN
  against an allow-list (etcd, CockroachDB). Anything else is rejected at the handshake with reason
  `bad_identity`.
- **Post-handshake hello frame**, inside TLS: `{program_id, program_version, supported_version_window,
  claimed_node_id | client, per-channel schema ids and hashes}`. It feeds both identity binding (§4.4) and
  versioning (§6.6, DIST-080).

### 4.4 The ingress admission pipeline (DIST-062)

For every connection, and then every frame, the runtime runs these steps in order. Any failure drops the frame,
increments `net_rejected_total{reason, channel, peer_role}` and writes a rate-limited audit record. Nothing
reaches the tick.

1. **TLS handshake.** Chain validation against the listener's trust root. Reasons: `handshake`, `expired`,
   `bad_identity`.
2. **Identity binding** (peer listener). The claimed `Node` in the hello frame must have
   `principal_of(claimed) == connection principal`. Reasons: `unknown_principal`, `principal_node_mismatch`.
   A peer cannot claim another node's id. This closes Timely's gap.
3. **Version window.** The peer's `program_version` must lie in the cluster's admitted window (DIST-084).
   Reason: `version_unsupported`.
4. **Frame decode.** The frame's channel schema id must be known, either current or with a translation
   (DIST-087). Reasons: `schema_mismatch`, `decode`, `disallowed`. A frame is never allowed to crash the
   receiver. CASSANDRA-4195, where an old node crashed on an unknown field, is the counter-example (SOSP21 §4.1.1).
5. **Channel ACL** (LANG-242). The sender's role or principal must be admitted by the channel's ACL. Reason:
   `acl`.
6. **Quota and backpressure** (DIST-008, DIST-065). Reason: `rate_limit`.
7. **Enqueue** for the receiver's next tick, with the implicit columns `sender` and `principal` attached.

For **self-sends and loopback** (LANG-046) steps 1–3 are skipped: `sender = self` and the principal is its own.

### 4.5 `sender` and `principal` columns (LANG-241, SEM-091)

**Semantics.** In Dedalus an async rule `m(@D, X̄)@async :- body` is evaluated at the location of its body.
Call that location S. We add S as an implicit column of the message: `m(@D, X̄, S)`. This is a pure syntactic
extension of the IR. It changes nothing observable unless a rule reads the column, because SEM-007 already
makes the sender part of a message's identity: "one message per (sender, send tick, receiver, fact)". The
column is dropped by projection when no rule refers to it. The receiver's set semantics therefore works
exactly as before. Two senders that deliver the same fact in one tick merge into one tuple when `sender` is
not read, and stay two tuples when it is.

`principal` equals `principal_of(sender)` for peers and the session's principal for clients. Neither column is
ever part of the payload, so a payload cannot forge them.

**Syntax (provisional):**
```
// Raft follower: only accept AppendEntries from the node it currently believes is leader for term T,
// and learn the leader's identity from the authenticated sender, not from a payload field.
ae(T, PI, PT, Es, C, L) <= append_entries(@self, T, PI, PT, Es, C) from L;

// KV: a client may write only under its own prefix. The principal comes from the runtime.
put_ok(S, K, V)   <= client_put(@self, K, V) from session S principal P, owns_prefix(P, K);
authz_denied(S, K) <= client_put(@self, K, _) from session S principal P, notin owns_prefix(P, K);
reply(@S, "denied") <~ authz_denied(S, _);
```

**Lint (ANA-106).** A channel column of type `Node` that is used as an identity must be equated with `sender`.
Examples are a Raft `leader_id` or a Paxos proposer id used in a comparison or as a reply address. If a rule
derives state from such a column without that equation, the compiler warns: "payload identity not bound to
authenticated sender".

### 4.6 Channel and module ACLs (LANG-242, ANA-105)

- **Inferred default-deny ACL.** The compiler projects a choreographic program onto its roles (LANG-009).
  For each channel `c` it computes `senders(c)`: the set of roles that have an async rule with `c` in the head.
  At runtime channel `c` accepts a frame only if `role_of(sender) ∈ senders(c)`, or, for external channels,
  only if the frame came from an admitted client. In the Raft flagship this alone stops a client from sending
  `append_entries` or `request_vote`, and stops any node of another program from injecting into this one.
  Nobody has to write an ACL.
- **Explicit ACLs** narrow the inferred ACL, or extend it for external channels:
  ```
  channel client_put(@dst: Node, key: string, val: bytes)
      accept from external client where principal in kv_writers;   // kv_writers: static or table relation
  channel admin_cmd(@dst: Node, cmd: AdminCmd) accept from principal in admins;
  ```
  An ACL predicate may read only unary principal or role sets held in `static` or `table` relations of the
  receiving node. It is evaluated against the **last committed tick** (the tick boundary). Because rejection is
  an omission (§4.9), checking against a slightly stale snapshot is sound.
- **Module ACLs.** Interface channels of an imported module instance (LANG-003/004) carry the module's ACLs. The
  importer may narrow them further: `import raft as r acl { r.client_req: accept from external client }`. It may
  not widen a module's peer channels.
- **Consistency check (ANA-105).** It is a compile-time **error** if an explicit ACL excludes a role in
  `senders(c)`, because the program would silently lose its own messages. It is a warning if an external channel
  has no explicit ACL.
- **Revocation and changes.** Changes to ACL relations take effect at tick boundaries. Removing a principal is
  non-monotone (Binder §6), so ACL relations should be sealed per epoch, like dynamic membership (DIST-042,
  ANA-065).

### 4.7 Rule-level authorization (LANG-244)

Authorization that depends on data is ordinary rules over `principal`. Examples: "the client owns this key",
"only the leader of term T may do X", "a quorum of admins approved". The standard pattern:

- `authorized(P, Op, Obj)` is derived by policy rules: RBAC, Binder-style delegation, k-of-n thresholds (LIB-120–122).
- Protected actions join `authorized`. A missing authorization derives `authz_denied(Session, Op, Obj, Reason)`.
- The runtime counts `authz_denied` tuples in `authz_denied_total{rule}`. A library rule turns them into error
  replies.

This is *program logic*, not an omission. The client receives an explicit error, and the analyses treat these
rules like any other. The `notin authorized` makes such rules non-monotone, so they are points of order; for a
local check against local policy state that is expected and harmless.

### 4.8 External clients and sessions (LANG-243, DIST-065)

- External clients are the `external` role (LANG-009; Hydro's `External` location). They are not `Node`s and are
  not in the membership.
- When a client connects, the runtime injects `session_open(S: Session, P: Principal, T: timestamp)` as an input
  event at the next tick. When the connection closes or its idle timer expires, it injects
  `session_closed(S, Reason)`. Programs use these to garbage-collect per-session state.
- Client frames arrive on ingress channels with implicit columns `session` and `principal`. Replies go to
  `@S` on egress-only channels. A session is a location that accepts only egress channels. A reply to a closed
  session is dropped and counted (`reason="session_closed"`).
- **Raft client sessions** (FLAG-011, exactly-once) are application-level client ids. A lint recommends deriving
  or checking the client id against `principal`, so one client cannot consume another's sequence numbers.
- **Forwarding.** A follower that redirects or forwards a client request to the leader forwards a claim about
  the principal. The leader accepts `on_behalf_of` columns only on channels whose ACL admits only cluster roles.
  In the crash-fault model cluster nodes are trusted to relay principal claims. With `signed<T>` (LANG-245) the
  client's own signature can travel end to end instead (SeNDlog's honesty constraint).
- **Quotas.** Each principal has a token bucket at ingress (`rate_limit` rejections) and a bound on concurrent
  sessions. Rejections to clients are sent as a `REJECTED(reason)` frame on the connection. This frame is outside
  program semantics. Peers receive no such frame.

### 4.9 Soundness: every rejection is an omission (SEM-090)

**Claim.** Let P be a program and let E be an execution of P under ingress enforcement, where the set of rejected
frames is R. Then E is also an execution of P under the lossy network mode (SEM-043), with exactly the messages
in R lost.

**Argument.**
1. Enforcement happens before a message enters any tick (§4.4).
2. A rejected message leaves no trace in program state. It is not in any relation, and no rule fires on it.
3. Under the lossy mode any message may be lost "per (sender, receiver, send tick)" (SEM-073).
4. A rejection is a per-message decision, so it is such a loss.
5. Accepted messages are delivered unchanged, with `sender` and `principal` set to their true values.

**Consequences.**
- **Safety.** Every safety property that P satisfies under lossy delivery also holds with ACLs, authentication,
  schema checks and quotas. Our consensus and commit protocols are designed to be safe under loss.
- **Liveness.** It needs more than the fairness assumption of SEM-040. Messages that are part of the protocol
  must eventually not be rejected. A misconfigured ACL or an expired certificate is a *permanent* omission and
  can stall liveness. That is why rejections must be observable (DIST-063) and why ANA-105 rejects
  self-contradictory ACLs statically.
- **Analyses.** CALM certificates, Blazes labels and Edelweiss rewrites need no change. An Edelweiss ARM rewrite
  (ANA-061) that relies on acks keeps retrying through rejections, which is correct.
- **LDFI.** Rejections are omissions, so existing O(f,to,t) variables cover them. No new hazard type is needed
  (TEST-105).
- **This is why we do not use SecureBlox-style transaction rollback** (CR-40).

### 4.10 Composition with the simulator, LDFI and provenance (TEST-104, TEST-105)

- **One code path.** The ACL decision function takes `(channel, sender role, sender principal, ACL relations
  snapshot)` and returns accept/reject. It is pure. The live runtime and the simulator (TEST-001) run the same
  function. The simulator does no cryptography: simulated connections carry a principal assigned from the
  scenario's directory.
- **New simulator fault kinds.** Each one is recorded in the trace as `REJECTED(reason)`, not `LOST`:
  - `reject(from, to, channel, t)`: an explicit rejection of one message;
  - `cert_expired(n, t)`: every frame to or from n with send tick ≥ t is rejected (`expired`). Under mTLS both
    directions fail, so this is an *isolation* of n, a partition burst in SEM-073's terms. Node n keeps
    computing. That differs from a crash (SEM-070), and it is the realistic model of a lapsed certificate;
  - `acl_misconfig(channel, role)`: every frame on `channel` from `role` is rejected.

  Certificate validity is checked against the virtual clock under simulation (DIST-031).
- **LDFI.** By default a rejection needs no new variable. For reporting, `--explain-omissions-as=auth` labels
  an LDFI counterexample's omissions as possible authentication rejections. An optional macro-fault `Iso(n,t)`
  with `Iso(n,t) ⇒ Iso(n,t+1)` encodes certificate-expiry isolation. It is monotone like K(n,t) but does not stop
  n's rules (P2).
- **Why-not provenance.** The message log (TEST-023) records `REJECTED(reason)` alongside send and receive ticks.
  `whynot` with NRECEIVE/NARRIVE (TEST-051) can then answer "message m from a was rejected at b by the ACL on
  `append_entries`: role `client` ∉ {peer}".

### 4.11 Observability and audit (DIST-063)

- **Counters:**
  - `net_rejected_total{reason, channel, peer_role}`, with reasons `handshake | expired | bad_identity |
    unknown_principal | principal_node_mismatch | version_unsupported | schema_mismatch | decode | disallowed |
    acl | rate_limit | session_closed`;
  - `tls_handshake_failures_total{listener, reason}`;
  - `authz_denied_total{rule}`.
- **Gauges:** `cert_expiry_seconds{cert}`, `sessions_active{listener}`, `security_mode{mode}`.
- **Audit log.** A structured record for each rejection kind, rate-limited per (peer, reason), plus
  certificate-rotation events and admin-plane actions.

### 4.12 The admin plane (DIST-066)

The following operations need a principal with the `admin` role, over mTLS:
- the node control API (`pause`, `stop`, DIST-040);
- the network REPL (TEST-090);
- runtime rule install (LANG-203);
- upgrade control and finalization (DIST-085);
- distributed provenance and trace queries (DIST-045, DIST-069).

A remote principal can never install rules through the data plane (§2.3).

### 4.13 What replaces SecLog, and `signed<T>` (LANG-245)

SecLog's `says(...)` is replaced by:
- the `from`/`principal` bindings (LANG-241), which authenticate the hop;
- channel ACLs (LANG-242);
- policy rules (LANG-244).

For end-to-end authenticity of a statement relayed through other nodes (SeNDlog Definition 3), a P2 value type
`signed<T>` carries a serialized `T`, the signer's principal and a signature. Its built-ins are `sign(T)`, run
by the local principal with its key through the host keystore, and `verify(signed<T>) -> Option<(Principal,
T)>`. Both are pure UDFs (LANG-181), and verification is memoized per value. Two uses are the SeNDlog Chord
`nodeIDCert` issued by a CA and a client-signed command carried in a Raft log entry.

## 5. Upgrades and schema evolution: literature and practice

### 5.1 Ajmani, Liskov, Shrira (ECOOP 2006)

**Model.** A distributed system is a set of objects that communicate by RPC. Each node runs one top-level
class. A **class upgrade** is ⟨oldClass, newClass, TF, SF, pastSO, futureSO⟩:

- **TF, the transform function.** It "generates an initial persistent state for the new object from the
  persistent state of the old one". "A TF must be restartable, because the node might fail while the TF is
  running." "A TF may not call methods on other nodes, because we can make no guarantees about when one node
  upgrades relative to another".
- **SF, the scheduling function.** It decides when a node upgrades. Rolling upgrade, big flip and fast reboot
  each take "just a few lines of script". "We guarantee [eventual upgrade] trivially by requiring that the
  upgrader specify a timeout for each SF." A schedule can avoid a hard simulation, e.g. "servers upgrade to the
  new type before any clients upgrade".
- **Simulation objects (SOs).** A *future SO* lets a node that has not upgraded yet support the new type. A
  *past SO* lets an upgraded node support the old type.
- **The upgrade layer** "labels outgoing calls with the version number of the caller" and "dispatches incoming
  calls by looking at their version number".

**Correctness of mixed mode.** The paper sets three requirements:
- the *Type requirement*: each version's class implements its type;
- the *Sequence requirement*: "Each event in the computation at a node must reflect the effects of all earlier
  events … in the order they occurred";
- the *Disallow constraint*: "Calls to the current object must not be disallowed". Only SO calls may fail, and
  "any RPC can fail … so that clients won't be surprised by such a failure".

An incompatible upgrade is specified by:
- an **invariant** I(O_old, O_new), which must be total;
- a **mapping function** MF that establishes I;
- **shadow methods**: T_new.$m gives the effect on O_new of each old mutator m, and vice versa.

The proof is by induction: MF is the base case and the shadows are the step. Methods are disallowed wherever the
compound type T_old&new is not a subtype. "The upgrader should choose the weakest invariant that makes sense …
in order to disallow as little as possible."

**Implementation.**
- The *interceptor* approach: the newest SO receives every call. It beats the *direct* approach, because in the
  direct approach an SO cannot observe calls that go straight to its delegate.
- "a good upgrade strategy is to always retire an incompatible upgrade before introducing the next incompatible
  upgrade."
- A node several versions behind processes upgrades "one-by-one".

**How this maps to our language.**
- A TF is a `migrate from N` block that runs at recovery (LANG-262). It is restartable, because it is a
  deterministic function of the old checkpoint, and it may not make remote calls.
- Past and future SOs are channel translation blocks (LANG-263). Translation is tuple-local and therefore
  stateless, so the direct approach's stale-state problem does not arise. Translation that needs state is
  written as ordinary rules over explicit dual channels, in the interceptor style (§6.5).
- A disallowed call is an untranslatable message, dropped as an omission (DIST-087). Ajmani's rationale that
  "any RPC can fail" is our SEM-090.
- SFs become the orchestrator's role order (ANA-101, DIST-085). A timeout makes the upgrade finish.
- "Retire before the next incompatible upgrade" becomes the version window (DIST-084).

### 5.2 SOSP'21 upgrade-failure study; DUPTester and DUPChecker; UpFuzz (NSDI'26)

**The 123 failures across 8 systems (SOSP21):**
- **Finding 1.** Upgrade failures have higher priority: 38% are Blocker, against 10% of non-upgrade bugs.
- **Finding 2.** 67% are catastrophic.
- **Finding 3.** 70% have easy-to-observe symptoms.
- **Finding 4.** 63% were not caught before release.
- **Finding 5 and root causes.** Incompatible cross-version interaction 63%, broken upgrade operation 33%,
  misconfiguration 3%, library dependency 2%. Of the incompatibilities, 60% concern persistent data and 40%
  network messages. About two thirds are syntax problems and one third semantics.
- **Findings 6–7.** About 20% of syntax incompatibilities involve serialization-library data or enums:
  - HDFS-14726 and HBASE-25238 added a *required* protobuf field;
  - HDFS-15624 inserted an enum member "in the middle", which shifted serialized indices.

  About 80% come from missing or incomplete hand-written deserializers. An example is CASSANDRA-4195, where an
  old node receives an unknown UUID field and aborts.
- **Finding 8.** Two thirds of *semantic* incompatibilities come from incomplete version handling. The lessons:
  - every source version needs a distinct version id (KAFKA-10173 changed a format without bumping it);
  - leave room between version ids (CASSANDRA-5102);
  - map each version id to a **feature set** (HDFS-1936, `LayoutVersion`);
  - "the version ID should be used in all messages". CASSANDRA-6678 carried the version only in the connection
    handshake, so a gossip message that raced the handshake was misclassified.
- **Broken upgrade operations.** In HDFS-11856 a client's 30-second tolerance for an unreachable DataNode was
  shorter than an upgrade restart. In CASSANDRA-15794 a 4.0 node wrote commit logs before failing, which blocked
  downgrade to 3.11.4 ("does not recognize commit logs generated by Cassandra 4.0").
- **Findings 9–13 on triggers:**
  - all failures need ≤ 3 nodes; 57% need a single worker node;
  - about 90% are deterministic;
  - consecutive major/minor versions expose all but 14;
  - half are triggered by stress tests with default configuration.

**DUPTester** runs three scenarios on containerized 3-node clusters: full-stop upgrade, rolling upgrade, and new
nodes joining an old cluster. It uses stress tests, and unit tests translated into client scripts. It found 20
new failures.

**DUPChecker** statically compares Protobuf and Thrift definitions for four rules:
1. a tag number changed;
2. a required field added or removed;
3. a field changed from required to non-required (a warning);
4. an enum needs a 0 value when members are added or removed.

It also checks enums serialized by index. It found 878 incompatibilities (700 errors and 178 warnings) in 7
systems.

**UpFuzz (NSDI'26)** fuzzes full-stop upgrades of Cassandra, HBase and HDFS. It prioritizes "transitively
persisted states" whose formats changed, using a likely-invariant engine. It found 15 new bugs, 8 of them
confirmed. Its oracle is **differential**: "compares the new version's behavior against the old version's
behavior, treating the old-version result as the testing oracle", with false positives below 1% after
normalization. Rolling upgrades are listed as future work.

**Consequences for us.**
1. Our compiler knows every channel and durable schema exactly. A DUPChecker-class check is therefore precise
   and not heuristic (ANA-100).
2. Our deterministic simulator runs 3-node clusters of two consecutive versions cheaply. Findings 9–11 say this
   covers the large majority (TEST-100/101).
3. Every frame, not only the connection, carries a schema id (DIST-080).
4. The storage format must not change before finalization, so a rollback stays possible (DIST-086). This is
   the CASSANDRA-15794 lesson.
5. Differential oracles against the previous version (TEST-102).

### 5.3 Erlang/OTP hot code upgrade

- "The code of a module can exist in two variants in a system: current and old." Loading a third variant purges
  the old one, and "any processes lingering in it are terminated". Fully qualified calls (`M:F`) go to current
  code. Local calls stay in the variant the process is running.
- In a release upgrade, a gen_server state change is an appup instruction `{update, Mod, {advanced, Extra}}`.
  The process transforms its state through `code_change(OldVsn | {down, Vsn}, State, Extra) -> {ok, NewState}`,
  and the same callback handles downgrades. `{load_module, Module, DepMods}` orders loading, and the order is
  reversed for a downgrade.

**Lessons.**
- At most two versions coexist (DIST-084).
- A state transform runs at a quiescent point. In our system the tick boundary is a natural quiescent point, so
  hot install switches programs between ticks (SEM-094, P2).
- Downgrade is a first-class direction (`{down, Vsn}`), which becomes our `migrate from N down`, P2.

### 5.4 Protobuf, Avro and Confluent compatibility modes

- **Protobuf (proto3).**
  - Wire-unsafe: changing a field number; moving fields into an existing `oneof`.
  - Wire-safe: adding fields, removing fields (the number **must** then be reserved: "Field numbers should never
    be reused"), adding enum values.
  - Compatible but possibly lossy: `int32/uint32/int64/uint64/bool` are interchangeable; `sint32/sint64` only
    with each other; `string/bytes` if the bytes are UTF-8; `enum` with the integer types.
  - Proto3 keeps unknown fields. The first enum value must be zero.
- **Avro.**
  - Record fields are matched *by name*. A writer field absent from the reader is ignored. A reader field absent
    from the writer takes the reader's default, and it is an error if there is none.
  - Promotions: int→long/float/double, long→float/double, float→double, string↔bytes.
  - An enum symbol unknown to the reader maps to the reader's default, or is an error.
  - Schemas have a *Parsing Canonical Form* and a fingerprint: SHA-256, MD5 or a 64-bit Rabin CRC. The
    single-object encoding is `C3 01` followed by an 8-byte fingerprint.
- **Confluent modes.**
  - BACKWARD (new reader, old data): "upgrade all consumers before you start producing new events".
  - FORWARD (old reader, new data): producers first.
  - FULL: both directions; "upgrade the producers and consumers independently".
  - The `*_TRANSITIVE` variants check against every earlier version.

**Lessons.**
- Fields need stable numeric identity, and removed numbers must be reserved (LANG-261).
- Hash canonical schemas (DIST-080/081).
- The *direction* of compatibility determines who must upgrade first (ANA-101).

### 5.5 etcd, CockroachDB and hashicorp/raft: rolling upgrades of consensus clusters

**etcd.**
- "an etcd cluster supports mixed versions of etcd members, and operates with the protocol of the lowest common
  version". Upgrade happens "one by one". New capabilities are enabled only when every member has upgraded. After
  completion, downgrade to 3.4 "is not possible".
- In code (`server/etcdserver/version/monitor.go`), the leader's `decideClusterVersion` takes the minimum member
  server version. If the current cluster version is lower, it calls `UpdateClusterVersion`. The change is applied
  **through the Raft log**: `InternalRaftRequest.cluster_version_set = 1300` (`membershippb.ClusterVersionSetRequest`),
  with `downgrade_info_set = 1302` for downgrades (release-3.5 protos).
- `UpdateStorageVersionIfNeeded` moves the **storage version** to match the cluster version.
- In 3.6, "a new storage version (SV) is persisted within the etcd data file", together with "a comprehensive
  schema" recording which version introduced each field. Downgrade works like this:
  1. `etcdctl downgrade enable`;
  2. the cluster version drops to the target, and etcd migrates the schema;
  3. a rolling replacement of binaries.

  "When a wal snapshot happens, all older incompatible entries should be applied, so they no longer need to be
  read and the storage version can be downgraded."

**CockroachDB.**
- The cluster version gates features. `cockroach_versions.go` spells out the rule for RPCs: "with
  requests/RPCs originating at other crdb nodes, the initiator of the request gets to decide what's supported. A
  node should not refuse functionality on the grounds that its view of the version gate is as yet inactive."
  If the sender has seen the gate, the receiver necessarily runs a binary that understands it.
- Internal versions are even. "The odd versions are used for internal book-keeping": these are the fence versions.
- The long-running-migrations RFC replaced gossip. The orchestrator makes each node "first durably persist the
  target version, then bump it's local version gate". It re-reads liveness until the node set is stable, so that
  "new nodes will always join with the version gate enabled". Each version's migration hook is idempotent and
  runs only once "all nodes in the system will have seen the associated version tag". `AdminMigrate`/`Migrate`
  rewrites every range.
- Operationally, finalization runs the migrations. Rollback is possible only before it: "Once a major-version
  upgrade is finalized, the cluster cannot be rolled back".

**hashicorp/raft.** `ProtocolVersion` is "the version of the protocol (which includes RPC messages as well as
Raft-specific log entries) that this server can *understand*". The configured value is what it *speaks*.
Protocol 1 "can understand the new LogConfiguration Raft log entry but will never generate one". Moving from
0 to 3 needs a rollout per step (N → N+1 → N+2). There is "no auto-negotiation".

**Lessons for a replicated state machine.**
1. **Understand before speak.** Version V+1 must accept everything V and V+1 send. It sends V+1-only formats
   only after activation.
2. **Activate through the log.** Every replica must interpret log entry k with the same code, because apply is a
   deterministic fold. Activation is therefore itself a log entry, so every replica switches at the same index.
3. **Persist, then activate, with a fence** so that no old binary can join after activation.
4. **Storage version follows finalization**, so a rollback before finalization stays possible.

### 5.6 Hydro multi-version simulation (source read)

- `FlowBuilder::next_version(&cluster)` declares the next version of a location. The simulation keeps
  `location_version` and `location_version_group_root` maps. When any location has version > 0,
  `splice_versioned_networks` runs over the IR.
- The splice keys every `HydroNode::Network` that has a name by
  `ChannelKey { name, src_group_root, dst_group_root }`. The same named channel is thereby identified across
  versions. It then merges the senders of all versions into one `VersionedNetworkFork { channel_id,
  channel_name, senders: Vec<(u32, Box<HydroNode>, NetworkSend)> }`, and each receiver becomes a
  `VersionedNetwork { fork, version, deserialize }`.
- Serialization is split into `NetworkSend`/`NetworkRecv` "so that the multi-version simulation merge can reason
  about each side independently".
- Corresponding clusters share one membership. `cluster_sizing` gives each version "a contiguous member-id slice
  … in version order".
- Sending to a multiversioned location needs a name: "Cannot send to a multiversioned location without a channel
  name." At this commit `Cluster::multiversioned()` returns `false` with a TODO, so the check is enforced only for
  processes. `.name()` is still what the splice keys on.
- The test `sim_multi_version_gossip` is `#[should_panic(expected = "read from member 1 got unexpected response:
  [Response { value: 0 }]")]`. v1 routes each request to the *last* sorted member and v2 to the *first*, and the
  exhaustive simulator finds the linearizability violation with one member per version.

**Lesson.** Named channels plus mixed-version membership plus exhaustive exploration is a proven technique. We
generalize it: translation blocks, per-version schemas, and upgrade *events* inside a run (TEST-100). DIST-010's
"named, versioned channels" is this mechanism.

### 5.7 Runtime rule install in the lineage

- **JOL** keeps programs as catalog rows: `program`, `rule`, `predicate`, and others (R07 §2.3). Its compiler and
  stratifier are Overlog (`compile.olg`, `stratachecker.olg`). R07 §6 concludes that "the engine must support
  installing new rules at runtime (hot program modification)".
- **Evita Raced** stages rewrite the catalog, and the Installer turns P2DL into dataflow elements (R01 §7).
- **LogicBlox**, which hosts LBTrust and SecureBlox: "the LogicBlox API allows an application to query and modify
  the data defined by the workspace, including adding/removing facts and rules. When predicate data is modified,
  the active rules are incrementally recomputed" (LBTRUST §3.1).
- **None of these** defines what happens to in-flight messages or to durable state whose schema changes. None
  offers mixed-version reasoning. They are mechanisms, not upgrade semantics.

## 6. The upgrade and evolution model for bloom-remake

### 6.1 Principles

1. **P-VER.** Everything that crosses a process boundary or survives a restart carries a schema identity: frames,
   WAL records and checkpoints (DIST-080/081).
2. **P-LOCK.** Schemas evolve under a checked-in `schema.lock`. The compiler compares against it and never guesses
   (ANA-100).
3. **P-UBS, understand before speak.** Features new in version V+1 are written or sent only after
   `cluster_version ≥ V+1`. The compiler enforces this (ANA-102).
4. **P-OMIT.** A message that cannot be understood or translated is an omission, counted and never a crash
   (SEM-090, DIST-087).
5. **P-TF.** A migration is deterministic, restartable and local (no remote calls), and runs at recovery
   (LANG-262, DIST-082).
6. **P-CALM.** Whether a rollout needs a coordination barrier follows from the monotonicity class of its
   migrations (ANA-103/104).
7. **P-TWO.** At most two program versions coexist in a cluster (DIST-084).
8. **P-FINAL.** The storage format changes only at finalization. Rollback is possible until then, and downgrade
   afterwards only with explicit down-migrations (DIST-086).

### 6.2 Versions, the schema lock and stable field numbers (LANG-260, LANG-261)

```
program raft_kv version 7;          // monotone integer; also a semver string for humans

channel append_entries(@dst: Node,
    term: u64 #1, prev_idx: u64 #2, prev_term: u64 #3,
    entries: List<Entry> #4, commit: u64 #5);

durable table kv(key: string #1, val: bytes #2, ver: u64 #3 = 0) key(key);   // #3 added in v7

enum Entry { #1 Put(PutCmd), #2 Del(DelCmd), #3 Noop, #4 Cas(CasCmd) since 7, unknown }
```

- **Field numbers.** Every column of a `channel`, `durable table`, `input`/`output` interface, or a type that
  reaches one (records and ADT variants), has a stable **field number** `#n`. The compiler auto-assigns numbers
  on first release and records them in `schema.lock`. It is an error to reuse a number, and removed numbers are
  kept as `reserved` (Protobuf rule).
- **Positional syntax is unaffected.** Numbers give identity only on the wire and on disk. The
  in-memory layout stays positional (ENG-020).
- **Enums and ADTs** stored or sent must declare an `unknown` fallback variant. An unknown variant is carried as
  opaque bytes, re-encodes identically, and matches only `unknown` patterns. Variants are serialized by their
  stable number, never by index (the HDFS-15624 lesson). `since N` marks a variant or field introduced in
  version N. The gating check (ANA-102) uses it.
- **`schema.lock`** is a canonical text file in the repository. For each version it lists every channel, durable
  relation and wire type with:
  - field numbers, names, types and defaults;
  - key columns;
  - lattice type identities (a hash of the merge definition);
  - reserved numbers;
  - the canonical-form hash;
  - the program version and the minimum supported version (CockroachDB's MinSupported).

  `bloomc release` appends the new version's section. CI fails if a schema changed without a version bump, or if
  the lock is stale (the KAFKA-10173 lesson; TEST-108).

### 6.3 Compatibility rules (ANA-100)

Terms: **R-new** means the new version reads data written by the old one (BACKWARD). **R-old** means the old
version reads data written by the new one (FORWARD). Both together are FULL.

| Change | Channel (wire) | Durable relation (storage) | Notes / source |
|---|---|---|---|
| Add non-key field with default (`= v` or `Option`) | FULL. Old readers ignore it (keep as unknown); new readers default it | R-new with auto-migration (default fill). Written only after finalization (P-FINAL) | Protobuf "adding fields is safe"; Avro reader default |
| Add non-key field without default | **Breaking** for R-new | **Breaking** unless a `migrate` block defines it | HBASE-25238, HDFS-14726 |
| Remove a field | FULL if every live reader has a default for it; the number becomes `reserved` | Needs a migration (usually a projection, tuple-local) | Protobuf reserve rule |
| Reuse a field number or change its type | **Error** | **Error** | DUPChecker rule 1 |
| Widen an integer (i32→i64, u32→u64) | R-new only. R-old values may not fit, so the field is lossy toward old | Auto-migration | Protobuf/Avro promotions |
| Add an enum or ADT variant | FULL if the type has `unknown`; otherwise **breaking** for R-old | As for channels | Proto3 open enums; Avro enum default |
| Change a key (add, remove or reorder key columns) | **Breaking**. Changes the FD, dedup and SEM-050 conflicts | **Breaking**. Needs a migration; the checker verifies the new key is functionally determined (ANA-080) | Specific to our model |
| Change a lattice type or its merge definition | **Breaking**. Mixed merges diverge | **Breaking**. Needs a migration; coordination-free only if the migration is a morphism (§6.4.3) | CR-23; R04 |
| Change a field's meaning without changing its type | Undetectable by schema. Must be declared `semantics_changed since N`, which forces a new field number | Same | KAFKA-7403 (SOSP21 §4.1.2) |
| Rename a field (same number) | FULL. Names are not on the wire | FULL | Protobuf |
| Add a channel | FULL. Old nodes never receive it (sends are gated, ANA-102) | n/a | CockroachDB gate |
| Remove a channel | Allowed once no live version sends it (checked against the window) | n/a | Ajmani "retire" |
| Add a durable relation | n/a | Written only after finalization (ANA-102) | CASSANDRA-15794 |

For each channel the checker computes a direction: identical, FULL, R-new-only, R-old-only or breaking. It does
the same for each durable relation, and it records any required migration. Breaking changes need an explicit
`migrate` or `emit` block (§6.4, §6.5); otherwise the release is rejected.

### 6.4 Migrations for durable state (LANG-262, DIST-082, ANA-103, ANA-104)

#### 6.4.1 Syntax and semantics

```
program kv version 7;
durable table kv(key: string #1, val: bytes #2, ver: u64 #3 = 0) key(key);
durable table tomb(key: string #1, at: u64 #2) key(key);          // new in v7

migrate from 6 {
  kv(K, V, 0) <= old.kv(K, V);                                    // tuple-local
  tomb(K, T)  <= old.deleted(K, T), notin old.kv(K, _);           // non-monotone
}
```

- `old.r` names relation `r` **as recorded in `schema.lock` for version 6**. It is typed by that schema and
  read from the decoded checkpoint plus WAL.
- The heads are durable relations of the current version.
- **Evaluation.** At recovery, if the checkpoint's program version is 6 and the binary is 7:
  1. load the v6 state into `old.*`;
  2. evaluate the migration block as a stratified Datalog program, which is a single tick with no temporal
     rules;
  3. write the result as a **new checkpoint**, tagged v7, atomically, with the old checkpoint kept (DIST-082);
  4. resume at a fresh tick (SEM-071).
- **Allowed.** Temporal operators and async rules are forbidden inside `migrate` (P-TF: no remote calls). Pure
  UDFs are allowed. `now()`/`random()` are forbidden, because the migration must be deterministic and
  restartable.
- **Auto-migration.** For relations whose only changes are defaults, projections, widening or renames, the
  compiler synthesizes the tuple-local rules. An explicit block is needed only for real reshaping.
- **Key safety.** If two old tuples map to the same new key with different non-lattice values, that is SEM-050's
  error. The checker tries to prove it impossible with FD inference (ANA-080). If it cannot, the runtime raises a
  hard error that names both source tuples. It never truncates silently.
- **Chains.** A node that is several versions behind applies `migrate from N`, then `from N+1`, and so on, one
  step at a time (Ajmani).
- **Downgrade.** `migrate from 7 down { … }` is P2 (Erlang `{down, Vsn}`, etcd 3.6).

#### 6.4.2 Classification of migrations and coordination (ANA-103)

This reuses the monotonicity machinery (ANA-020):

| Class | Definition | Why it matters for rollout |
|---|---|---|
| **Tuple-local** | Every rule has exactly one `old.*` atom in its body, plus static relations and pure UDFs | Distributes over union: M(A ∪ B) = M(A) ∪ M(B). Old state and old in-flight data can be migrated separately, lazily and in any order. **Coordination-free.** |
| **Monotone** | Joins among `old.*` atoms; no negation, non-lattice aggregation, `reveal` or deletion | Correct on the complete old state at recovery. Data that is still arriving in old format (messages from v6 nodes) must be joined against the persisted old relations. The runtime keeps `old.*` materialized for the mixed window. **Coordination-free**, but it costs memory. |
| **Non-monotone** | Negation, aggregation, `reveal` or deletion over `old.*` | The result depends on having *all* the old data. It must run at a cut after which no v6 data can arrive. It therefore runs at **finalization** as a cluster-wide barrier (DIST-085 step 4), like CockroachDB's per-version migrations, which run only once "all nodes in the system will have seen the associated version tag". **Coordination required.** |

The report printed by `bloomc compat` states the class of each migration and whether the rollout is
coordination-free.

#### 6.4.3 Migrating lattice columns: morphisms (ANA-104)

Suppose a replicated lattice column changes type from L_old to L_new (a CRDT upgrade). Replicas on both
versions merge each other's deltas during the mixed window. Let f: L_old → L_new be the migration.

- If f is a **morphism** (join-preserving, CR-23), then f(a ⊔ b) = f(a) ⊔ f(b). Migrating before a merge and
  after it give the same result, so replicas converge whatever the order of upgrades and deliveries. This is
  CALM applied to the migration itself.
- If f is only monotone, the order matters. Old-format deltas must stop before the migration, which means a
  barrier at finalization.
- f must be declared `morphism` (LANG-182). The compiler checks the claim with the law harness (TEST-083),
  extended to the pair (L_old, L_new), and with SMT where supported (VER-014). Otherwise the migration is
  classified non-monotone.

An example is `lmax<u32>` → `lmax<u64>`, by widening; the widening is a morphism. `lset<T>` → `lmap<T, lbool>` by
`x ↦ {x: true}` is a morphism as well. A size-capped set is not.

### 6.5 Cross-version channel translation (LANG-263, DIST-087)

A receiver on V+1 automatically decodes frames written with V's schema, using defaults and `unknown` variants.
Only three cases need rules:

1. A field was **removed or reshaped** so that V's frames cannot be decoded with V+1 defaults.
2. **Sending to a V receiver** a tuple that V's schema cannot express.
3. A **semantic change**.

```
// v7 adds `prevote` to request_vote. v6 receivers do not know it.
channel request_vote(@dst: Node, term: u64 #1, last_idx: u64 #2, last_term: u64 #3,
                     prevote: bool #4 = false since 7);

emit request_vote to 6 {
  old.request_vote(D, T, LI, LT) <= request_vote(D, T, LI, LT, false);
  // No rule for prevote = true: such tuples are *disallowed* toward v6 receivers.
}
accept request_vote from 6 {
  request_vote(D, T, LI, LT, false) <= old.request_vote(D, T, LI, LT);   // what the default would do anyway
}
```

- **Tuple-local only.** Each translation rule has one channel atom in its body and pure UDFs. It runs in the
  codec layer, per message, at egress (`emit … to N`, chosen by the receiver's version from its hello frame) or at
  ingress (`accept … from N`). It never touches program state, and ANA-103 verifies that it is tuple-local. This
  is Ajmani's simulation object reduced to what is safe without state.
- **Disallow.** If no `emit` rule matches a tuple, the tuple is dropped with `reason="disallowed"` (DIST-087).
  This is Ajmani's disallowed call, which fails like any RPC can. It is an omission (SEM-090).
- **Gating instead.** `bloomc compat` warns about every partial translation. The better fix is usually to gate
  the new behavior (§6.6): `prevote` is sent only when `cluster_version ≥ 7`, and then every receiver is on v7.
- **Stateful mixed-version behavior** is written in the program itself with explicit dual channels. Example:
  `append_entries` and `append_entries_v7` coexist, and rules choose one by `cluster_version`. This is the
  interceptor style: the newest program handles both formats. hashicorp/raft's protocol 1 is the same thing, "can
  understand the new LogConfiguration … but will never generate one".

### 6.6 Cluster version, gates and log activation (LANG-264, DIST-083, DIST-084, SEM-092)

- **`cluster_version`** is a built-in input relation of lattice type `lmax<u32>`. It is fed by the runtime
  between ticks, sampled once per tick like `now()`, and recorded for replay. Programs read it only through
  thresholds: `cluster_version.at_least(7)` (LANG-126). The value only rises, because downgrade after
  finalization is forbidden (P-FINAL). A gate read is therefore **monotone**: once true it stays true. It adds no
  point of order, and a gated rule is CALM-friendly.
- **Who raises it.**
  1. Each node durably records `understood_version` = its binary's version when it starts.
  2. A controller computes the minimum over all members of the membership epoch. It re-reads membership until the
     set is stable (CockroachDB); this is our fence. In a Raft or Paxos cluster the controller is the leader (etcd
     `decideClusterVersion`).
  3. It proposes `activate_version(v)` only if min ≥ v and v ≤ the operator's finalization target.
  4. In a replicated-state-machine program (FLAG-014), `activate_version(v)` is a **log entry**. Every replica's
  apply fold (LANG-110) switches semantics at the same index: "entry k is interpreted by the rules active at
  version(k)". This is required for deterministic apply (SEM-081), and it is etcd's `ClusterVersionSetRequest`
  pattern.
  5. A non-replicated program learns the value from the controller over a runtime channel. A node may see the
     gate later than another node. CockroachDB's rule makes this safe: "the initiator of the request gets to
     decide", because a receiver of a gated message necessarily runs a binary that understands it (P-UBS).
- **Fence (DIST-084).** After activation of v, the handshake rejects any node whose binary is below v
  (`version_unsupported`). The admitted window is {cluster_version, cluster_version + 1}. A node that has fallen
  behind further is upgraded offline by chained migrations (§6.4.1). This is Ajmani's and Erlang's two-version
  rule.
- **Gated-write check (ANA-102).** A rule is flagged if it writes a durable relation, column or variant marked
  `since V`, or sends on a channel or field `since V` with a non-default value, where V is the current version,
  and its body is not dominated by `cluster_version.at_least(V)`. The check follows the dependency graph, so a
  gate on an upstream relation counts. The error reads: "ungated use of v7 feature `Cas` in rule r12; guard with
  `cluster_version.at_least(7)`". `unsafe_ungated "reason"` overrides it, mirroring `nondet` (LANG-204), and is
  reported.

### 6.7 WAL and checkpoint formats (DIST-081)

Yes: WAL and checkpoint formats carry schema hashes. The format:

- **Segment and checkpoint header:**
  - `magic`;
  - `storage_format_version` (the engine's own format, gated like any feature);
  - `program_id`, `program_version`;
  - `finalized_cluster_version` at write time;
  - `catalog_digest`;
  - a table of `(relation_id, relation_name, schema_hash, field layout)`.
- **Records** refer to `relation_id`. A record for a relation absent from the header is corruption.
- **Recovery:**
  1. Read the header.
  2. If every `schema_hash` equals the current one: load.
  3. Otherwise, if a `migrate` path exists from `program_version`: run it (§6.4).
  4. Otherwise, **refuse to start** with an error listing each unknown relation and hash and the versions the
     binary supports. Never skip, never truncate.
- **Before finalization**, an upgraded binary writes WAL and checkpoints in the **old storage version**. This is
  possible because every write of a new relation or field is gated off. So a node can roll back to the old
  binary and read everything written so far (P-FINAL; etcd storage version; the CASSANDRA-15794 lesson). The
  first checkpoint after finalization bumps the storage version.
- **Snapshots** sent between nodes (Raft `InstallSnapshot`, FLAG-010) use the checkpoint format, with the same
  header and the same pre-finalization rule. A snapshot from an upgraded leader is readable by an old follower.

### 6.8 The compatibility checker, step by step (ANA-100, ANA-101)

Input: `schema.lock` (versions ≤ N), the program source of version N+1, and the deployment's role map.

1. **Schema extraction.** Take the canonical schema of every channel, durable relation and wire type in N+1.
   Assign field numbers to new fields.
2. **Field-level diff** against N, and against every version down to MinSupported when `--transitive` is given,
   under the rules of §6.3. Each entity gets a direction (FULL / R-new / R-old / breaking) and a list of problems
   with source spans.
3. **Migration coverage.** Every durable relation whose storage schema changed must have an auto or explicit
   migration from every supported older version. Migrations are classified (ANA-103), lattice morphisms checked
   (ANA-104), and FDs checked.
4. **Translation coverage.** For every channel not FULL-compatible: if it is R-old-broken, then either every
   send of it is gated (step 5) or an `emit … to N` block exists, and the block is reported partial or total. If
   it is R-new-broken, an `accept … from N` block must exist.
5. **Gating** (ANA-102).
6. **Rollout order (ANA-101).** Choreography gives, for each channel, the sender roles and receiver roles.
   - An R-new-only channel (new reads old) needs its **receivers** upgraded before its senders speak the new
     format. Gated, this is automatic.
   - An R-old-only channel whose sends are *not* gated needs its **senders** upgraded last. Build the precedence
     graph over roles. If it has a cycle, no rolling order exists: report the cycle and suggest gating
     (Confluent's consumers-first and producers-first, generalized to multi-role choreographies).
   - The output is a role order, for example "acceptors → replicas → proposers" or "any order". It is written into
     the release manifest that the orchestrator consumes (DIST-085).
7. **Report.** A table per entity; the migration class; whether the rollout is coordination-free (all migrations
   tuple-local or monotone, all lattice migrations morphisms) or needs a finalization barrier; and any
   `semantics_changed` fields. JSON output is available for CI.

### 6.9 Rolling upgrade of a Raft cluster (DIST-085, FLAG-016)

Starting from v6 everywhere, with the v7 binary having passed `bloomc compat`:

1. **Admit v7.** Its handshake window is {6, 7}. The cluster version is 6.
2. **Upgrade one node at a time, in the role order from ANA-101.** For Raft every node has the same role, so
   followers go first and the leader last.
   - Before stopping the leader, transfer leadership with TimeoutNow (FLAG-013), as etcd transfers leadership
     "gracefully before shutdown".
   - Each node: stop (crash-restart, SEM-071) → start v7 → recovery loads the v6-format checkpoint and WAL → runs
     tuple-local or monotone migrations **in memory only**, because the on-disk format stays v6 → rejoins →
     catches up.
   - The orchestrator waits for health before continuing: the node is in the membership and caught up to the
     commit index. It also enforces SOSP21's HDFS-11856 lesson: an upgrade restart must not be mistaken for a
     permanent failure. The orchestrator raises failure-detector suspicion timeouts for the node it is upgrading.
3. **Pause or abort.** Until finalization, any node can be restarted on v6 (rollback), because everything on disk
   is v6-readable.
4. **Finalize.** Automatically once every member's `understood_version` = 7 and the membership has been stable
   for a configured period, or manually (CockroachDB's `SET CLUSTER SETTING version`):
   1. the leader proposes `activate_version(7)`, which commits at index i;
   2. every replica's `cluster_version` becomes 7 at index i;
   3. non-monotone migrations run as barrier jobs;
   4. the next checkpoint bumps the storage version.

   After this, v6 binaries are rejected (fence), and downgrade needs down-migrations (P2).
5. **Invariants checked in tests (BENCH-220):**
   - no committed entry is lost or changed;
   - every replica decodes every committed entry;
   - no gated feature takes effect before index i;
   - the linearizability checker (TEST-008) passes on the client history of the whole run;
   - the result is identical to a single-version reference run on the same client inputs (differential, TEST-102).

### 6.10 Hot rule install (LANG-203 → SEM-094, P2)

Hot install is the same operation without a process restart. The admin plane (DIST-066) submits program P′ with a
migration block. The node:
1. compiles P′ and runs the full analysis. The stratification check is repeated, as JOL's `stratachecker.olg`
   does. On failure it rejects P′ atomically;
2. at the next tick boundary t, runs the migration over its durable **and** non-durable state;
3. runs P′ from tick t+1.

In-flight messages keep their schema ids and are translated or dropped exactly as in §6.5. Indexes and delta
state for changed rules are rebuilt (ENG-003/004). Semantically, P runs ticks ≤ t and P′ runs ticks > t. Nothing
new is needed in the Dedalus model: the tick boundary is the quiescent point Erlang needs `sys:suspend` to reach.

### 6.11 Mixed-version simulation and upgrade testing (TEST-100 to TEST-103, TEST-106)

- **Mixed-version simulation (TEST-100).** The deterministic simulator loads several compiled versions of one
  program. Nodes are assigned versions, and channels are matched by name and schema id and translated by the same
  codec layer the runtime uses (DIST-087), generalizing Hydro's `VersionedNetworkFork`. An
  `upgrade(node, to_version)` event is a crash-restart under the new program, with migration. Upgrade events,
  finalization and rollback are scheduling choices, so fuzz and bounded-exhaustive exploration (TEST-002) interleave
  them with message deliveries and faults.
- **Scenarios (TEST-101).** From DUPTester, for every consecutive version pair (N−1, N), and (N−2, N) when
  `--transitive` is set:
  - full-stop upgrade;
  - rolling upgrade under load;
  - new-version nodes joining an old cluster;
  - rollback before finalization;
  - attempted downgrade after finalization (must be refused cleanly);
  - crash in the middle of an upgrade.

  Workloads are the program's own simulation tests and stress drivers (SOSP21 Findings 12–13). 3 nodes are enough
  by default (Finding 10).
- **Differential oracle (TEST-102).** From UpFuzz: run the same seed and workload on a v(N−1)-only cluster and on
  the upgraded cluster, and compare client-visible outputs after normalizing declared nondeterminism (LANG-204)
  and `semantics_changed` fields.
- **Migration crash testing (TEST-103).** Crash at every durable write of a migration. The recovered state must
  equal a single uninterrupted run (P-TF).
- **Golden storage fixtures (TEST-106).** Checkpoints and WAL produced by every released version are committed as
  fixtures, like HDFS's pre-built fsimages (SOSP21 §5.3). Every new binary must load them, or refuse them with the
  documented error.

## 7. Edge cases and interactions

1. **Raft log entries are both wire data and durable data.** `Entry` is a field of `append_entries` and a column
   of the durable `log`. It must satisfy both rule sets. A new entry type (for example `Cas`) must be gated, or a
   follower still on v6 could receive a committed entry it cannot apply. Apply cannot skip committed entries, so
   the follower would have to halt. The gating check (ANA-102) catches this.
2. **InstallSnapshot across versions.** Before finalization, a v7 leader's snapshot is in v6 storage format
   (§6.7). After finalization no v6 node is admitted.
3. **Lattice gossip across versions (Anna-style KVS, FLAG-060).** The merge function must be identical in both
   versions, or the migration must be a morphism applied at ingress (§6.4.3). Otherwise replicas diverge
   permanently. That is the one upgrade bug CALM *can* rule out statically.
4. **The sender column and set semantics** (§4.5). If `sender` is read, identical facts from two senders stay
   distinct tuples. If it is not read, they merge. Aggregates over messages (`count<X>`) are unaffected unless
   they group by `sender`.
5. **Quorum counting must use `sender`,** never a payload id. `majority<N in Members>` (LANG-111) over votes should
   be written with `from S`, and the lint (ANA-106) enforces it. A payload `voter` field would let one node vote
   many times.
6. **Clock-dependent certificate expiry under simulation** uses virtual time (DIST-031). Under LDFI, expiry isolation
   is modeled as omissions (§4.10).
7. **ACL changes are non-monotone** (revocation, Binder §6). They take effect at tick boundaries and are sealed per
   epoch. A message accepted just before a revocation is legitimately processed.
8. **Replays.** Non-causal WAL replay (DIST-025) runs under the migration if the WAL predates the binary.
   Deterministic replay of a recorded run (TEST-001) needs the recorded `cluster_version` samples as well as
   `now` and `random`.
9. **Loopback and self-sends** skip authentication (§4.4) but still get `sender = self`.
10. **Messages in flight during an upgrade restart** are lost anyway (SEM-071). Protocols already retransmit.
11. **Provenance and traces contain payloads.** Exporting them is an admin-plane operation (DIST-069). Tier-C
    firing logs from an LDFI run on production data must not leak to clients.
12. **`signed<T>` inside durable relations or channels** is an opaque bytes value for schema evolution. Its inner
    `T` evolves separately and must not be migrated in place, because the signature covers the original bytes.
13. **Two versions only (P-TWO)** also bounds the translation blocks: a v8 program needs `accept`/`emit` blocks for
    v7 only. Blocks for v6 are deleted when v6 retires, which is Ajmani's "retire" step.

## 9. TEST PROGRAMS and BENCH scenarios

Each is added to `FEATURES.md` §11.9. All run in the deterministic simulator unless marked *live*.

- **BENCH-220** [P1] **Rolling upgrade of a 3-node Raft KV, v6 → v7.** v7 adds a column with a default to the KV
  table, the `prevote` field, and a gated `Cas` command. There is continuous client load, random omissions and
  one crash, and ≥ 1000 seeds are explored. The upgrade runs followers first, then the leader after TimeoutNow,
  then automatic finalization. Expected:
  - no committed entry is lost or altered;
  - every replica decodes and applies every committed entry;
  - `Cas` requests before activation fail with "feature not active", and succeed after;
  - `activate_version(7)` is applied at the same log index on every replica;
  - the client history is linearizable (TEST-008);
  - client outputs equal those of a v6-only reference run on the same inputs, apart from `Cas` responses (TEST-102).
- **BENCH-221** [P1] **Rollback and downgrade.** In the BENCH-220 setup, roll one node back to v6 before
  finalization: it restarts and rejoins with no error. After finalization, starting a v6 binary on v7 storage is
  refused with an error naming the relation, the storage version and the supported range. No data file is modified.
- **BENCH-222** [P0] **A durable table gains a column, with a migration rule.** v1 has
  `kv(key, val) key(key)`. v2 has `kv(key, val, ver: u64 = 0)` and an explicit `migrate from 1 { kv(K,V,0) <= old.kv(K,V); }`.
  Expected:
  - after restart every row has `ver = 0`;
  - the checkpoint header's schema hash changes only after the migration commits;
  - a crash injected at every write of the migration yields the same final state (TEST-103);
  - removing the migration block makes `bloomc compat` accept the change as an auto-migration;
  - making the new column a key column is rejected as breaking unless a migration is given (ANA-100).
- **BENCH-223** [P1] **Non-monotone migration needs finalization.** v2 splits `log(i, op)` into `live` and
  `tomb` with `notin`. `bloomc compat` classifies it non-monotone. The orchestrator runs it only at finalization,
  and a mixed-version run that tries to apply it earlier is rejected by the tool.
- **BENCH-224** [P0] **Compatibility-checker corpus.** Each case has an expected verdict:
  1. a required field added without a default, the HBASE-25238 analogue → error;
  2. a field number reused → error;
  3. an enum variant added to a type without `unknown` → error for R-old;
  4. an enum variant inserted in the middle of a type with stable numbers, the HDFS-15624 analogue → OK;
  5. a key column added → breaking;
  6. a `lmax<u32>` → `lset<u32>` column change without a migration → breaking;
  7. `lmax<u32>` → `lmax<u64>` with a declared morphism migration → coordination-free;
  8. a format change without a version bump, the KAFKA-10173 analogue → CI error (TEST-108);
  9. ungated send of a `since 7` channel → ANA-102 error;
  10. a role-order cycle → reported with a gating suggestion.
- **BENCH-225** [P1] **Mixed-version semantic incompatibility.** Port Hydro's `sim_multi_version_gossip`: v1 routes
  to the last sorted member and v2 to the first, with one member per version. Expected: exhaustive search finds
  the read-after-write violation (`[Response { value: 0 }]`). With identical routing in both versions
  (`sim_multi_version_extra_unrelated_location`) no violation is found.
- **BENCH-226** [P1] **Write-before-finalize guard (CASSANDRA-15794 analogue).** Mark a v2 durable write
  `unsafe_ungated`, write under v2 before finalization, then roll back to v1. Expected: v1 refuses to start with
  "unknown relation schema hash in WAL segment k". There is no crash and no silent skip. Without the override,
  ANA-102 rejects the program at compile time.
- **BENCH-227** [P0] **An unauthenticated peer's `<~` is rejected.** *Live and simulated.* A process without a
  valid certificate connects to the peer listener of a 3-node Raft KV and sends `append_entries(term = 999)`.
  Expected:
  - the handshake fails;
  - `net_rejected_total{reason="handshake"}` and `tls_handshake_failures_total` increment by at least 1;
  - no tick runs on the frame, the term stays unchanged and the leader is not disturbed;
  - an audit record exists.

  In the simulated variant the fault is `reject(...)`, and the trace shows `REJECTED(handshake)`.
- **BENCH-228** [P0] **Authenticated but unauthorized sender.** A valid *client* certificate sends
  `append_entries` to the client listener, and separately a peer of another program sends to the peer listener.
  Expected:
  - rejected with `reason="acl"` and `reason="unknown_principal"` respectively;
  - the metrics carry `channel="append_entries"` and `peer_role`;
  - the Raft invariants (BENCH-170) hold;
  - `whynot` on the non-delivery names the ACL.
- **BENCH-229** [P0] **Identity spoofing.**
  - Node n2 claims `node_id = n1` in its hello frame → `principal_node_mismatch`.
  - A Raft variant that takes the leader id from a payload field triggers the ANA-106 lint. With `from L`, a
    follower that forges a payload `leader_id` cannot make others treat it as leader.
  - A vote-counting variant that counts a payload `voter` field lets one node vote many times in simulation. The
    `from S` version does not, and ANA-106 flags the first.
- **BENCH-230** [P1] **Certificate rotation and expiry.** *Live.* Rotate all certificates during load without
  restarts: no errors beyond reconnects, and throughput recovers within 2 s. Separately, let n3's certificate
  expire, in virtual time under simulation:
  - n3 becomes isolated, and `cert_expiry_seconds` < 0 and `net_rejected_total{reason="expired"}` increase;
  - the majority keeps committing;
  - after renewal n3 rejoins and catches up.
- **BENCH-231** [P1] **Rule-level authorization.** In a KV with per-principal prefixes:
  - client alice writing `bob/x` gets a `denied` reply;
  - `authz_denied_total{rule}` increments;
  - no state changes;
  - alice writing `alice/x` succeeds.
- **BENCH-232** [P1] **LDFI with rejections equals LDFI with omissions.** On `2pc`, `rdlog` and `ack_rb` from
  BENCH-130/131, with ACL-rejection faults enabled, the verdicts and minimal falsifiers equal the omission-only
  results.
- **BENCH-233** [P1] **Version window.** A v8 node joining a cluster whose cluster version is 6 is rejected with
  `version_unsupported`. So is a v5 node joining after v6 is finalized.
- **BENCH-234** [P1] **Upgrade scenario sweep.** Run TEST-101's six scenarios for every consecutive version pair of
  the flagship Raft KV, Multi-Paxos and BOOM-FS test programs, on 3 nodes. All pass, and the TEST-106 fixtures
  load.
- **BENCH-235** [P1] **Cost of security.** Rerun BENCH-202's protocols with mTLS against plaintext at the same
  batch sizes. The target is at most a 15% drop in throughput [ours]. SecureBlox's per-message RSA signatures cost
  roughly 67% in fixpoint latency (SBLOX §8), which is why per-tuple signatures are not the default.

## 10. Open design decisions (added as ODD-30 to ODD-34)

- **ODD-30 ⚑ Default security posture.**
  - Options: (a) secure by default: production mode requires mTLS, and plaintext needs an explicit development
    flag; (b) TLS off unless enabled, which is common in research systems (Hydro, Timely).
  - Recommendation: **(a).** The user asked for production-ready.
- **ODD-31 Principal format.**
  - Options: (a) SPIFFE URI SAN only; (b) CN only (etcd, CockroachDB); (c) SPIFFE, with CN as a configurable
    fallback.
  - Recommendation: **(c).**
- **ODD-32 ⚑ Upgrade mechanism.**
  - Options: (a) restart-based rolling upgrades with migrations; (b) hot rule install only; (c) (a) at P1 and hot
    install (SEM-094) at P2.
  - Recommendation: **(c).**
- **ODD-33 Channel ACL default.**
  - Options: (a) open, any authenticated peer; (b) default-deny ACLs inferred from the choreography, plus explicit
    ACLs.
  - Recommendation: **(b).**
- **ODD-34 Per-tuple signatures (SeNDlog/SecureBlox `says`).**
  - Options: (a) never; (b) the `signed<T>` value type at P2; (c) a per-channel "signed" mode that signs every
    tuple.
  - Recommendation: **(b).** Per-connection AEAD covers hop authenticity, and SecureBlox measured the cost of
    per-tuple signatures.
