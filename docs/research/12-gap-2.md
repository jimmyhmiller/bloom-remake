# 12 / Gap 2: Nondeterministic and order-sensitive operators under persistence, replay and incremental maintenance

Tag used in FEATURES.md: **R12/G2**. This report closes a gap in CR-26. CR-26 says the Dedalus replay semantics and
the delta-maintaining engine (ENG-004) differ observably "only for async sends derived from persistent state and for
host callbacks". That is incomplete. The following operators also diverge between "re-derive everything every tick"
and "maintain deltas" unless their semantics is pinned down:

- `choose((X),(Y))`, `choose(x)` and `argagg(:choose)`;
- `choose_rand`;
- derivations that depend on `random()`;
- `index()`/`enumerate`, which FLAG-021 uses for Paxos slots;
- `sort`, `limit`/`topk`;
- `fold_ordered`, `reduce` and user-defined aggregates.

The report gives, for each of these operators, one semantics that holds both in the Dedalus reference semantics and in
the incremental engine. It also gives a record and replay format, and a differential-testing oracle.

Rule sketches use the Molly-style Dedalus pseudo-syntax that R07 and R10 use (`:-`, `@next`, `@async`, `notin`,
head aggregates written `min<X>`), plus the new forms defined here. They are marked **SKETCH (ours)**. The real
surface syntax is ODD-01's decision. Where this report says "normative", it proposes text for FEATURES.md.

## 1. Executive summary: the decisions

1. **One contract for every such operator (SEM-083).** Take any nondeterministic or order-sensitive operator. At tick
   t, its output is a *function* of three things:
   - the operator's input set at t;
   - state that the operator's own Dedalus expansion explicitly carries across ticks;
   - the run's seeds.

   The output never depends on any of the following:
   - iteration order, hash-map order or interning order;
   - arrival order within a tick;
   - plan shape, or engine-internal caches.

   Each operator is defined by a **Dedalus expansion over deterministic built-ins**: the canonical total order
   (LANG-024) and a keyed pseudo-random function (PRF) of the seed. Naive evaluation of that expansion is the oracle
   (ENG-067). The incremental engine must reproduce it *exactly*. No "modulo nondeterminism" slack is allowed inside
   our own system.
2. **`choose` is per-tick.** The tick, and the node's location, are always part of the FD's determinant. This is what
   Dedalus does for async choice (DL11 §5.3: `choose((A1,…,An,T),(S))`). If the tick were left out of a user-level FD,
   the FD would range over all time. That is Krishnamurthy–Naqvi-style *static* choice, and it can pick a candidate
   that only exists in the future. We reject it (§4.2).
3. **`choose` resolves by a seeded priority (rendezvous hashing).** Among a group's candidates, it picks the one with
   the least priority `prio = PRF_σ(site, X̄, Ȳ)`, with ties broken by canonical order. This is a greedy "choice-least"
   computation in GZ01's sense (§3.3), so the result is a genuine stable (choice) model. Consequences:
   - the choice is a pure function of the candidate set and the seed;
   - it stays stable across ticks until a lower-priority candidate arrives or the chosen one is retracted;
   - the incremental algorithm is an argmin index (ENG-068);
   - with a deployment-wide seed, all nodes that see the same candidates make the same choice (HRW);
   - under fault injection, the choice changes only when the fault removes the chosen candidate. That keeps LDFI
     hypotheses comparable with the failure-free run.
4. **Stickiness is explicit (`choose sticky`, LANG-115).** It has an exact Dedalus expansion. The previous tick's
   choice is kept while it is still a candidate. It is *revoked* at the first tick in which it is no longer a
   candidate, and a fresh priority choice is then made in that same tick. Sticky choice is monotone in time for
   insert-only candidates, which is GPZ01's monotone multi-valued mapping. But it depends on the schedule, so it is
   not confluent.
5. **`choose_rand` and `rand(k̄)` are counter-based randomness.** Their PRF key includes the node, the node's
   incarnation and the tick. The draw is redone every tick and is independent across groups. Nothing is recorded per
   draw. The run seed and the incarnation ids are enough to replay (R123 is the counter-based-RNG idea). `random()`
   stays one sample per node per tick (LANG-174), defined as `rand(())`.
6. **`index()`/`enumerate` are dense per-tick ranks in `(key, canonical)` order**, computed after head
   deduplication. Stable arrival numbering, which is what Hydro's `enumerate::<'static>` does over a persisted body,
   is a separate operator `seq()` (LANG-098) with a high-water-mark expansion. FLAG-021's slot assignment uses
   per-tick `index()` over each tick's client batch plus a persisted `next_slot`. It is deterministic.
7. **`sort`, `topk`, `limit`, `percentile` and list-valued aggregates always break ties by canonical order.** So they
   are deterministic. LANG-093's "flag" becomes a *lint*, "ties broken by canonical order", which is decided by FD
   closure (ANA-038). It is no longer a nondeterminism label.
8. **`fold_ordered` is a pure left fold over the tick's rows in `(key, canonical)` order.** Its incremental
   implementation is a prefix-checkpointed fold (ENG-073). The "carried-state" form re-applies every row of a
   *persistent* input every tick, because Dedalus demands it. That form is linted (ANA-011) because it is almost
   always a bug.
9. **Choice is stratified** (SEM-086). A choice site is a negative edge and cannot sit on a same-tick recursive
   cycle; SZ90 imposes the same restriction. Greedy recursive choice, as in Prim's algorithm, is expressed across
   ticks, or with lattices, or later through a P2 in-tick greedy operator that implements GZ01's Algorithm 7.2 with
   our priority.
10. **Replay needs only the inputs, the seeds and any overrides** (TEST-010). Choices are *recomputed*. Traces carry
    per-tick digests so that divergence is detected at the first tick where it happens. The oracle compares engine
    and naive evaluation *exactly*. External systems such as Bud, Hydro and Soufflé make choices differently; they are
    compared "modulo choices" by extracting their choices, validating them, and replaying our oracle with those
    choices as overrides (TEST-014).
11. **The amended CR-26 (§9) allows no observable difference at all.** It lists the places where a naive delta engine
    *would* diverge, and the mechanism that prevents each one.

## 2. The problem, concretely

Under Dedalus, a persisted fact exists at every tick, so every derivation from it recurs at every tick (CR-26). A delta
engine computes only what changed. For monotone, order-insensitive operators the two agree by construction. For the
operators in scope they agree only if the operator's semantics was written with both readings in mind. Here are the
divergences found in real systems:

| Divergence | Where it occurs | Source |
|---|---|---|
| `choose` over a persisted input keeps the first value it ever saw, while a per-tick re-choice could pick another | Hydro `dfir-datalog`: over a persisted body, `choose` lowers to `fold_keyed::<'static>` with `Some(prev)` kept ("By default we select the 1st") | DFDL `apply_aggregations` |
| `choose` depends on physical iteration order within a tick | Bud `Choose#trans` keeps the first value pushed. Soufflé keeps "the first one in the evaluation order". Hydro keeps the first element in join/hash order | BUD aggs.rb; SDOC; DFDL |
| `choose` is sticky until *any* deletion from the upstream table, and is then re-made from scratch in storage order | Bud: a table is invalidated iff a tuple was actually deleted at tick start; invalidation clears `PushGroup`/`PushArgAgg` state and rescans | BUD collections.rb `BudTable#tick`, group.rb `invalidate_cache` |
| `choose_rand` draws from a process-global RNG stream | Bud `ChooseOneRand` calls Kernel `rand` (Vitter reservoir). Replay needs the global RNG state, and a draw anywhere else perturbs every later draw | BUD aggs.rb |
| `index()` over a persisted body numbers facts in arrival order and never renumbers; over a non-persisted body it renumbers from 0 each tick | Hydro: `enumerate::<'static>` over the persisted delta stream, vs `enumerate::<'tick>`. With an aggregate in the head, `fold_keyed::<'static>` replays groups in hash-map order, then `enumerate::<'tick>` renumbers them every tick | DFDL snapshot `test_index` |
| `index()` numbers body instantiations, not distinct head tuples | Hydro: `enumerate` runs on `pre_fold_keyed_map` rows before the head's `unique::<'tick>`. Two body rows with the same head fields get two indices | DFDL lib.rs |
| `collect_vec` order is hash order | Hydro: `FxHashSet` | DFDL lib.rs |
| A fold with carried state over a persistent input: Dedalus re-applies every row every tick, a delta engine applies only new rows | Any `state@next = fold(state, R)` where R is persisted | §5.11 |
| A `random()`-dependent derivation over persistent state is recomputed every tick under replay semantics, but a cache would keep the old draw | Any engine that treats `random` as static | §5.8 |
| Replay of a nondeterministic reducer can retract outputs it never emitted | DD avoids this by keeping an *output arrangement* rather than re-running user logic: "to efficiently reconstruct what it has previously produced as output without extensive re-invocation of the supplied user logic (and to avoid potential non-determinism therein)" | SHARR §5.3 |

Modern IVM systems simply forbid nondeterminism:

- DBSP's theorem Q^Δ = D ∘ ↑Q ∘ I needs Q to be a function, lifted pointwise. DBSP also requires time-invariant
  operators: "DBSP only uses time-invariant operators", Def 2.6 (DBSP §2).
- Feldera: "Feldera's incremental query engine assumes that all computations are deterministic. Using a
  non-deterministic UDF is likely to result in incorrect outputs" (FELD).
- Materialize forbids *unmaterializable* functions such as `now()`, `current_timestamp()` and `mz_now()` in indexes
  and materialized views, "because their output depends upon state besides their input parameters" (MZF). Feldera
  supplies `NOW()` as a per-step value: "The value of `NOW()` remains constant within a step" (FELD). That is exactly
  CR-18's per-tick sampling.

Our position is between the two. We **keep** choice as a language feature, as Dedalus and Bloom demand. We make it a
function of the seed so that the DBSP/Feldera discipline applies to it.

## 3. What the literature says

### 3.1 Saccà and Zaniolo, PODS 1990: choice models are stable models

**Choice programs** (SZ90 §6). A choice goal is `choice((X),(Y))`, where X and Y are disjoint lists of variables and X
may be empty. A choice program must satisfy:
- (a) at least one rule is a choice rule;
- (b) no choice predicate occurs in a head;
- (c) "the head of each of its choice rules is not mutually recursive with some of the goals of the rule".

That is, SZ90 treats programs *stratified with respect to choice*. It remarks that "every program with choice in
recursive rules can be substituted by a program stratified w.r.t. choice".

The original programs are positive. SZ90 adds that "some kind of negation (e.g., stratified negation) can be allowed".

**Choice models** (Def 11). Each choice rule `ri: A ← B, C` has C, its conjunction of choice goals. It is split into:

```
A ← B, extChoice_i(Z).
extChoice_i(Z) ← B.
```

Z is the list of choice variables. Relation R_i (the extension of extChoice_i) gets the FD set
`F = {X → Y | choice((X),(Y)) is a goal of ri}`. A *reduced version* of R_i is "a maximal subset of R_i for which all
the functional dependencies in F hold". A choice model is the minimal model of a reduced version of P.

**Maximality is part of the meaning.** Every group that has a candidate gets a choice.

**Stable version** SV(P), verbatim modulo layout:

```
A ← B, chosen_i(Z).
chosen_i(Z) ← extChoice_i(Z), ¬diffChoice_i(Z).
extChoice_i(Z) ← B.
diffChoice_i(Z) ← chosen_i(U), Y ≠ Ỹ.      -- one rule per choice((X),(Y)); U = Z with each Y renamed
```

**Theorem 6.** The choice models of P coincide with the stable models of SV(P), modulo the new predicates. Lemma 1:
every stable model of SV(P) is total, and at least one exists.

**Prop. 10.** The "stable backtracking fixpoint", applied to SV(P), "never backtracks and never outputs 'no stable
models'". In SZ90's words: "making a choice is a complex operation [from] the semantic viewpoint, but computationally it
is a rather simple one."

**Consequence for us.** Choice has a precise stable-model meaning. Every maximal FD-respecting selection is a model.
Any deterministic resolution rule that always produces *some* maximal FD-respecting selection is faithful to the
semantics. It simply selects one stable model.

### 3.2 Giannotti, Pedreschi, Saccà and Zaniolo (DOOD 1991) and GPZ01: static vs dynamic, lazy vs eager

**Static choice** (Krishnamurthy–Naqvi, as described in GPSZ91 §4 and GPZ01 §4): "static choice assumes that a single
global selection is performed 'at the end' of recursion". It fails in recursion. In `p(Y,J) ← p(X,I), g(X,Y), J=I+1,
choice((Y),(J))` over g = {(a,b),(b,b)}, one choice model properly contains another. That contradicts maximality, and
the extension it would need is infinite (GPSZ91 §4).

**Dynamic choice** makes "many local choices … dynamically 'during' recursion, i.e. interleaved with the deduction
steps". Its meaning is the stable models of SV(P) (GPSZ91 Def 2).

**DCF procedure** (GPSZ91 §7). It alternates a *saturation* mode (the ordinary fixpoint of the non-choice rules) with a
*choice* mode (fire chosen rules plus their diffChoice rules). "An early choice is clearly correct with respect to the
functional dependencies, although it may inhibit possible later choices. This implies that DCF cannot compute every
stable choice model of a program, but only some preferred ones."

**Lazy vs eager** (GPZ01 §8.1).
- *Lazy*: exactly one new chosen atom per step. It is complete: "any dynamic choice model of P is the limit of a
  computation based on" the lazy operator (Lemma 8.11).
- *Eager*: a maximal FD-consistent set of new chosen atoms per step. It is incomplete but strictly more expressive. It
  can emulate negation (Ex. 8.12, `NOT[p,u]`).
- On the spanning-tree example, static, lazy and eager choice have four, three and one choice model respectively.

**Monotonicity** (GPZ01 §9, stated in LDLPP as Thm 2.2). "Dynamic choice programs define monotonic transformations on
the underlying database." Formally, if EDB′ ⊇ EDB and M is a choice model on EDB, then some choice model M′ ⊇ M exists
on EDB′. Also, "any deterministic query specified using the lazy dynamic choice is indeed monotonic", whereas eager
choice is not monotone.

**Consequence for us.** There are two different notions of "monotone" for choice:
- *existential* monotonicity: *some* resolution extends the old one. That is exactly our sticky rule (§5.5): keep
  the old choice when it is still a candidate.
- *functional* monotonicity: *the* resolution only grows. A fixed preference, such as our priority, generally
  violates it: a new lower-priority candidate displaces the old choice.

This is the formal root of the sticky-vs-per-tick trade-off.

### 3.3 Greco and Zaniolo (JICSLP 1998, TPLP 2001): the fixpoint operator, choice-least, and implementation

**foe(P)** (GZ01 Def 3.1, crediting SZ90). A choice rule
`r: A ← B(Z), choice((X1),(Y1)), …, choice((Xk),(Yk))` must satisfy "Xi ∩ Yi = ∅ and Xi, Yi ⊆ Z". It becomes:

```
r′: A ← B(Z), chosen_r(W).                 W = ∪ (Xj ∪ Yj)
    chosen_r(W) ← B(Z), ¬diffchoice_r(W).
    diffchoice_r(W) ← chosen_r(W′), Yi ≠ Yi′.   (one per choice goal; W′ primes the variables not in Xi)
```

The stable models of foe(P) are the choice models, and "the chosen atoms in each stable model of foe(P) obey the FDs".

**Nondeterministic immediate consequence Ψ_P** (Def 5.1). Ψ_P(I) = { T_{P_D}↑ω(I ∪ ΔC) ∪ ΔC | ΔC ∈ Γ_P(I) }, where
Γ_P(I) ranges over non-empty FD-consistent subsets of the newly enabled chosen atoms. So "if there are possible new
choices, then at least one has to be taken". An *inflationary choice fixpoint* is a sequence I₀ = ∅,
I_{n+1} ∈ Ψ_P(I_n).

- **Thm 5.1** (from Giannotti et al. 1991): M is a choice model iff M is an inflationary choice fixpoint (sound and
  complete).
- **Thm 5.2**: computing one choice model is PTIME in data complexity.

**Greedy choice** (§5.2). `choiceleast((X),(C))` and `choicemost((X),(C))` "coincide" declaratively with
`choice((X),(C))`. Operationally, the lazy operator's singleton δ is restricted to δ ∈ least(Θ_I) (Def 5.4, the
least-cost immediate-consequence operator). A rule may have "at most one choice-least or one choice-most atom".

- **Thm 5.3**: every least-choice fixpoint is a choice model and is PTIME. The computation is "sound but no longer
  complete".
- Footnote 2 compares this to Prolog: the declarative semantics is the set of all models, "but then one particular
  [model] will be generated instead of others according to some preference criterion". **This is precisely our
  design.** Declaratively, choose may pick any candidate. Operationally, we generate the model preferred by a seeded
  priority.

**Examples** (verbatim modulo symbols, used below as tests):

```
actual_adv(S, P) ← student(S, Majr, Yr), professor(P, Majr), choice((S), (P)).      (Ex 3.1)
matching(X, Y) ← g(X, Y, C), choice((Y), (X)), choice((X), (Y)), choice((X), (C)).    (Ex 4.2)
st(root, a, 0).
st(X, Y, C) ← st(_, X, _), g(X, Y, C), Y ≠ a, Y ≠ X, choice((Y), (X)), choice((Y), (C)).  (Ex 4.3)
st(X, Y, C) ← st(_, X, _), g(X, Y, C), Y ≠ a, choice((Y), (X)), choiceleast((Y), (C)).  (Ex 6.2, Prim)
dj(Y, C) ← dj(X, C1), g(X, Y, C2), Y ≠ a, C = C1 + C2, choiceleast((Y), (C)).          (Ex 6.3, Dijkstra)
```

For Ex 4.3 over the edges {ab:1, bc:2, ac:3} (both directions), the paper lists exactly three choice models:
{ab, bc}, {ab, ac} and {ac, cb}.

**Implementation** (§7).
- "The chosen atoms need to be memorized in a set of tables chosen_r … diffchoice atoms need not be computed and
  stored … checked dynamically against the table chosen_r".
- "For each functional dependency X → Y there is an hash index on the attributes specified by the variables in X".
- Algorithm 7.1 is a semi-naive choice fixpoint. It keeps a differentially maintained candidate table `theta_r` and
  removes `conflict(theta_r, δ)` after each choice.
- Algorithm 7.2 selects the least-cost tuple.
- For a single choice-least goal, the "unique key" optimization keeps one tuple per left-side key in theta: "the tuple
  with the smaller cost value is entered in the table and the other is discarded". This is *not* valid with several
  choice goals (TSP, matching): "c3 … cannot be eliminated, since it has a chance to be selected later".
- With priority queues, Prim and Dijkstra reach O(e log n).

These are the direct ancestors of ENG-068 and ENG-075.

### 3.4 Stratified choice and XY-stratification (GSZ95, LDLPP)

- GSZ95 §4: "If P is stratified modulo choice (i.e., by removing the choice predicates) the stable model is not in
  general unique but existence of at least one is guaranteed … if P is a stratified modulo choice program then one of
  the stable models can be computed in polynomial time."
- LDLPP Def 2.2 and the text after it: the stable models of a stratified choice program "can be computed by modifying
  the iterated fixpoint procedure used for stratified programs so that choice models (rather than the least models) are
  computed for strata containing choice rules". **That is exactly our tick evaluation.** A choice site is evaluated when
  its stratum is reached, over the complete candidate set of that stratum.
- **Determinism is undecidable** (GSZ95 §3): "the problem of whether a query on a given database is deterministic
  under the non-deterministic semantics is in D^p; worse, the problem of whether a query is deterministic for all
  databases is not decidable at all". **So LANG-093/LANG-108 flagging must be a sound sufficient condition, never an
  exact one** (§6).
- **XY-stratification** (LDLPP §2, Def 2.3 and Procedure 2.1). "XY-stratified programs are locally stratified
  explicitly by a temporal argument". X-rules keep the head's temporal argument. Y-rules take some body arguments at
  "one less". The *bistate* version renames same-stage atoms `new_` and previous-stage atoms `old_`, drops the stage,
  and must be stratified. The evaluation "reduces to a repeated computation over the stratified program P_bis", with
  `old ← new` pointer swaps between stages. Up to syntax, this is Dedalus₀: deductive rules are X-rules and `@next`
  rules are Y-rules.

  LDLPP shows choice and XY-stratification side by side, but *I found no statement in the accessible papers of how a
  choice FD treats the stage argument*. That is the TKDE 2001 paper's topic, and I could not access it (§0.2).
  §4.2 settles the question from first principles.

### 3.5 Dedalus's own use of choice

- DL11 §5.1 and TR §6.1 define `choose((X1),(X2))` exactly as Greco–Zaniolo's FD choice, "expanded into an
  unstratifiable strongly-connected component of rules, and each possible choice is associated with a different model".
- DL11 §5.3, the async rule: each async head `p(A1,…,An)` gets `time(S), choose((A1,…,An,T),(S))`, and "communication
  rules include the location specifier appearing in the rule body among the functionally-determining attributes …
  even if it does not occur in the head". **The body time T is written explicitly into the determinant.**
- DS-TR §2.3, formal async: `R(y,t,v̄) ← B{x,s | v̄,w̄,y}, time(t), choice(⟨x,s,y,v̄⟩,⟨t⟩)`. Again, the sender's location
  x and time s are in the determinant.
- **Neither paper says whether a *user-level* `choose` in a deductive rule implicitly includes T.** The async case
  suggests the authors meant choices to be per (location, time).

### 3.6 Soufflé: relation-level choice by guarded insertion

**Syntax.** `.decl R(x1..xn) choice-domain D1, …, Dk`. Each Di is an attribute or an attribute tuple, and declares the
FD Di → (all other attributes) (SDOC, HU21 §3). Example: `.decl list(prev, next) choice-domain prev, next` gives a
total order.

**Semantics** (HU21 §3).
- A choice function c_D keeps one tuple per D-value, chosen by `SingleChoice`, which "arbitrarily chooses one element".
- An exclusion function drops new tuples whose D-value is already present: e^A_D(A′) = A′ \ {t ∈ A′ | t|D ∈ A|D}.
- The consequence operator is Γ^c_P(I) = I ∪ c(e_I(T_P(I))). The paper calls it "monotone" and takes its least
  fixpoint.

**Implementation** (HU21 §4, SSRC). Every `Insert` into a choice relation becomes a `GuardedInsert` whose condition is
an `ExistenceCheck` for the pattern (D-values, ⊥ elsewhere). In semi-naive evaluation this check is against *both*
`new_R` and `R`. The docs admit the order dependence: "Soufflé only chooses arbitrary one of them (the first one in the
evaluation order)… the order of insertion cannot be controlled by the program".

**Rule-based vs relation-based choice.**
- With rule-based choice, a spanning-tree rule can still re-derive an edge to the root through the exit rule. The fix
  is an extra `u != "L1"` guard (HU21 §3).
- Relation-based choice constrains all rules of the relation.
- HU21 claims the two have the same expressiveness, and rule-based choice can be emulated with an auxiliary relation.
- Speed-ups over encoded choice reach 10k× (Table 1).

**What SSRC tests show.**
- The `choice_highest_mark` test is deterministic only because the input has no ties at the maximum. The choice
  there just enforces uniqueness.
- `tests/semantic/choice` rejects the explicit SZ90 encoding (`chosen`/`diffchoice`) as "Unable to stratify": cyclic
  negation.

**Consequences for us.**
1. Relation-level resolution is ergonomic and worth having (LANG-117). But the relation must be complete before
   choosing (stratified), not first-come.
2. Soufflé allows choice inside recursion, and the result depends on evaluation order. We reject that for P0/P1
   (SEM-086). The P2 greedy operator (LANG-099) makes it deterministic.

### 3.9 Differential Dataflow and DBSP

- DD `reduce_trace` doc (DDR): "The `logic` closure is expected to take a key, accumulated input, and tentative
  accumulated output, and populate its final argument with whatever it feels to be appopriate updates … ideally the
  updates would if applied to the tentative output bring it in line with some function applied to the input."
  - The operator re-evaluates at "interesting times" and diffs against the accumulated **output** it has already
    produced (`output_produced`). It never diffs against a recomputation of the old output.
  - SHARR §5.3 gives the reason: to avoid re-invoking user logic "and to avoid potential non-determinism therein".
  - **Rule for us:** every choice/order operator materializes its current output, and retractions are computed
    against that materialization (ENG-068).
  - Because logic receives the tentative output, DD *can* express output-aware ("sticky") reductions. That is how
    `choose sticky` is maintained.
- DD `identifiers.rs`: unique ids are assigned by hashing `(round, record)`. On collision, "the one with the lower
  round, breaking ties by record" wins, and losers retry with round+1. The result is a deterministic, incrementally
  maintainable, *non-dense* identifier. It contrasts with dense ranks, which shift on insertion (§5.9).
- DBSP (§2–3): circuits of causal, time-invariant operators over Z-sets. The incremental theorem needs every operator
  to be a function. A per-tick operator whose result depends on the tick number is still causal but **not
  time-invariant**. In DBSP terms it must take the clock as an input stream. That is how `choose_rand`/`rand` are
  classified (ENG-074).

### 3.10 Counter-based randomness and rendezvous hashing

- **R123.** A counter-based PRNG is a keyed bijection or PRF applied to a counter. A sample is `F_key(counter)` and
  depends on no generator state. This gives *splittable, replayable* randomness: any (node, tick, site, key) draw can
  be recomputed independently.
- **HRW.** Rendezvous hashing picks, for an object, the server with the highest `hash(object, server)`. It "allows
  clients to achieve distributed agreement on a set of options" with no coordination. Adding or removing a server
  moves only the objects whose winner changed.

Our `choose` is HRW over candidates, with the site and group in place of the object.

## 4. Design principles (normative)

### 4.1 The determinism contract (SEM-083)

For every operator o at site s on node n in tick t:

```
out_o(n, t) = f_o( in_o(n, t),  carried_o(n, t),  seeds,  overrides_o(n, t) )
```

- `in_o(n,t)` is a **set**: the operator input after per-tick deduplication (SEM-007).
- `carried_o` is state that o's Dedalus expansion defines with `@next` rules. It is part of the node state, so it is
  covered by hashing (ENG-120), checkpoints (ENG-030) and provenance. The engine may not carry any other state that
  affects outputs.
- `seeds` are defined in §4.3.
- `overrides_o` is an input relation, only in simulation and replay (§5.6).
- `f_o` is defined by a Dedalus expansion over the canonical order and the PRF. Naive evaluation of the expansion *is*
  the reference.

### 4.2 The tick and the location are always in the determinant

A `choose((X̄),(Ȳ))` in node n's rule at tick t is read as `choose((n, t, X̄),(Ȳ))`. There are three candidate
readings, and only this one is sound:

- **Tick omitted.** The FD becomes X̄ → Ȳ over *all ticks*. SV(P)'s `chosen(X̄, Ȳ)` would then have no time column,
  so one Ȳ would be fixed per X̄ for the whole run. Worse, a stable model may fix a Ȳ that becomes a candidate only at
  tick 100. Then the head is empty for X̄ at ticks 0–99 even though candidates existed. This is Krishnamurthy–Naqvi
  *static* choice lifted to time, with GPSZ91's anomalies, and it is **non-causal**: a choice at tick k is constrained
  by facts from later ticks. The compiler rejects any attempt to express it (ANA-011: explicit time variables are only
  available under entanglement, LANG-072).
- **Tick included, which we adopt.** One choice per (n, t, X̄) among that tick's candidates. This is what DL11 does for
  async rules, and it is the only reading under which each tick is an independent stratified choice program (LDLPP's
  iterated choice fixpoint per stratum, applied per tick).
- **Choice carried across ticks.** This is not a reading of the FD at all. It is additional state, so it must be
  written as state: `choose sticky` (§5.5) expands to explicit `@next` rules.

### 4.3 Seeds, sites and the PRF (SEM-084)

- **Root seed ρ** (u128).
  - In simulation, the run seed (TEST-001).
  - In production, the deployment seed. It is drawn from OS entropy when the deployment is created and stored in the
    deployment config (DIST-033). It is not drawn per process.
- **Choice seed** σ_c = PRF(ρ, "choose"). It is *shared by all nodes* (see ODD-38).
- **Node seed** σ_n = PRF(ρ, "node", n).
- **Incarnation** ι(n) = (durable restart counter, boot nonce). The counter is incremented durably at every restart.
  - In simulation, the boot nonce is PRF(ρ, n, counter).
  - In production it is drawn from OS entropy and written into the trace and the WAL header.
  - The nonce prevents repeated random sequences when a node rejoins with an empty disk (FLAG-025).
- **Site id** = PRF over (module path, rule label (LANG-068), operator ordinal within the rule). Unlabeled rules get a
  label derived from a hash of their normalized IR. Renaming a rule changes its site ids. Replay detects this through
  the program digest (TEST-010).
- **PRF.** A fixed, versioned, platform-independent keyed function `F_k : bytes → u64`.
  - Recommendation: SipHash-1-3 with a 128-bit key.
  - Its inputs are the concatenated 64-bit **canonical fingerprints** of the values. A fingerprint is xxh3-64 of the
    canonical encoding, computed once when a value is interned and cached next to the intern id (ENG-032). So a
    priority costs one short PRF call.
  - The PRF and the encoding carry version numbers, which are recorded in every trace header.
- **Collisions only affect ties.** Every priority is paired with the canonical order of the candidate, so a
  fingerprint or PRF collision cannot make a result nondeterministic.

### 4.4 Canonical order is over values, never over intern ids (SEM-088)

ENG-020 interns strings, records and locations into ids assigned in *arrival order*. If `<`, sorting, `index()`,
tie-breaking or `min` compared intern ids, results would depend on arrival history, and naive and incremental runs
would differ. Rules:
- LANG-024's order compares *values*.
- Intern ids may be used only for equality, hashing and joins.
- For types whose ids are not order-preserving (strings, ADTs), the value comparison is done through the intern table.
  The planner can cache "rank of id in value order" per epoch if it needs speed.
- **Every** output whose order is observable (list-valued aggregates, host callbacks, `stdio`, dumps and traces) is
  emitted in canonical order.

### 4.5 No persist-pullup through non-distributive operators (ENG-069)

ENG-004's rewrites move persistence across operators, e.g. `Join(P,P) → P(Δ(Join))`. They are valid only for operators
that distribute over union and are time-invariant (DBSP lifting). `choose`, `index`, `sort`, `topk`, `fold_ordered`
and every non-lattice aggregate are not distributive:

- `Choose(P(x)) ≠ P(Choose(Δx))`. The right-hand side *is* Hydro's first-seen sticky behavior.
- `Index(P(x)) ≠ P(Index(Δx))`. The right-hand side is arrival numbering.

The rewrite engine must refuse these, and implement each such operator as a *stateful maintained operator* over its
full per-tick input (ENG-068, ENG-072, ENG-073).

## 5. Operator-by-operator specification (deliverable 1)

**Notation** (SKETCH, ours).
- `cand_s(W̄)` is the set of distinct valuations of the operator's variables W̄ over rule body B at the current tick.
  Time and location are implicit, as in TPLP's user-level syntax.
- `prio_s(X̄,Ȳ) := (F_{σ_c}(site_s, fp(X̄), fp(Ȳ)), Ȳ)` is ordered lexicographically, with Ȳ compared by the
  canonical order `≤c`. It is injective within a group, so a group minimum is unique.
- `rprio_s(X̄,Ȳ) := (F_{σ_self}(site_s, ι, tick(), fp(X̄), fp(Ȳ)), Ȳ)` is the version used for randomness.

### 5.1 `choose((X̄),(Ȳ))`: single FD, per tick (LANG-108; SEM-085)

**Surface.** `H(ū) :- B(Z̄), choose((X̄),(Ȳ)).` Well-formedness:
- X̄ ∩ Ȳ = ∅, and X̄, Ȳ ⊆ vars(B) (GZ01 Def 3.1).
- Ȳ is non-empty ("The right side of a choice goal cannot be empty", LDLPP §2). X̄ may be empty, meaning one global
  choice per tick.
- Lattice-typed variables may not occur in Ȳ, because their priority would change as they grow. Use `reveal`
  explicitly.
- At most one choose goal per rule in this form; §5.2 covers several.

**Dedalus expansion** (reference semantics):

```
cand_s(X̄, Ȳ)   :- B(Z̄).
pmin_s(X̄, min<P>) :- cand_s(X̄, Ȳ), P := prio_s(X̄, Ȳ).
chosen_s(X̄, Ȳ)  :- cand_s(X̄, Ȳ), pmin_s(X̄, P), P == prio_s(X̄, Ȳ).
H(ū)            :- B(Z̄), chosen_s(X̄, Ȳ).
```

**Faithfulness.** `chosen_s` is a reduced version in SZ90's sense: maximal, FD-respecting, one Ȳ per non-empty group.
It is the result of GZ01's least-choice fixpoint with cost `prio_s` (Thm 5.3). So it is a stable model of foe(P).

**Properties.**
- Deterministic given (in, σ_c).
- Non-monotone: a new candidate with lower priority retracts the old choice, so the site is a negative edge (SEM-021).
- Order- and batching-independent *within* a tick.
- Classified *seed-dependent* (SEM-087).
- With the shared σ_c, nodes whose candidate sets agree make the same choice. That is HRW agreement, useful for
  routing (`msg@choose<N>(…)`, LANG-107).

**Incremental algorithm** (ENG-068).
- Per site, keep a map `X̄ → ordered set of (prio, Ȳ)` over candidates with positive support. `cand_s` is maintained
  as a Z-set with support counts (ENG-062).
- Keep the materialized output `chosen_s: X̄ → Ȳ`.
- On Δcand, update the ordered set. If a group's minimum changed, emit `−(X̄, old)` and `+(X̄, new)` using the
  *materialized* old value (SHARR §5.3).
- Cost: O(|Δ| log g).
- If lifetime analysis (ENG-060) proves `cand_s` never shrinks, keep only the current minimum per group. That is
  GZ01 §7.3's "unique key" optimization, valid here because there is a single FD. If `cand_s` is tick-local, nothing
  is kept across ticks.

**Edge cases.**
- An empty group gives no output (CR-08).
- Duplicate derivations of the same (X̄,Ȳ) are one candidate.
- Dropping Ȳ in the head makes the output seed-independent (§6, D3).
- If X̄ → Ȳ already holds on `cand_s`, the site is deterministic, and ANA-038 reports it as redundant.

### 5.2 Several choose goals in one rule (LANG-116)

**Surface.** `H :- B, choose((X̄1),(Ȳ1)), …, choose((X̄k),(Ȳk))`, with W̄ = ∪(X̄i ∪ Ȳi). Examples are bipartite
matching and the successor chain (GZ01 Ex 4.1, 4.2).

**Semantics.** A greedy scan in priority order, i.e. GZ01 Algorithm 7.2 restricted to one non-recursive choice rule,
written with `fold_ordered` (§5.11):

```
acc_s  := fold_ordered(∅, step_s, cand_s(W̄) order by (F_{σ_c}(site_s, fp(W̄)), W̄))
step_s(A, W̄) := if ∃ W̄′ ∈ A, ∃ i: W̄[X̄i] = W̄′[X̄i] ∧ W̄[Ȳi] ≠ W̄′[Ȳi] then A else A ∪ {W̄}
chosen_s(W̄) :- W̄ ∈ acc_s.
H :- B, chosen_s(W̄).
```

The result is FD-consistent and maximal: every rejected candidate conflicts with an accepted one. So it is a choice
model (GZ01 Thm 5.3). With one FD this reduces to §5.1's argmin.

**Incremental algorithm** (ENG-075). The greedy result on one *conflict component* does not depend on any other
component. A conflict component is a union-find class of candidates linked by sharing some X̄i value. On Δcand,
recompute greedily only the affected components. This is exact, and for matching-like workloads it is usually small.
GZ01 §7.3 gives the priority-queue implementation within a component.

### 5.3 `choose<Y>` aggregate and `argagg(:choose)`

- `r(Ḡ, choose<Ȳ>) :- B.` ≡ `r(Ḡ, Ȳ) :- B, choose((Ḡ),(Ȳ)).`
- Bud's `argagg(:choose, [G], c)` returns the whole exemplar tuple, so it is `choose((Ḡ),(rest of tuple))`.
- Other head aggregates in the same head apply to the same group independently.
- The Bud frontend maps `group([..], choose(x))` and `argagg(:choose, ..)` here. The Hydro frontend maps `choose(x)`
  here. Both frontends document that the *resolution* differs from the original systems (§3.7–3.8).

### 5.4 `choose_least` / `choose_most` (LANG-114)

`choose_least((X̄),(C))` is GZ01's `choiceleast`:
- declaratively it is the FD X̄ → C;
- operationally it picks the least C;
- ties in C are broken by `prio_s`, then by canonical order;
- at most one per rule;
- combined with other choose goals, the greedy order of §5.2 is (C, prio, W̄).

With a single FD it is `argmin<C>` returning exactly one exemplar. By contrast, LANG-103's `argmin` returns *every*
tied exemplar. The site is deterministic whenever C is unique within each group (§6, D5).

Prim and Dijkstra need this inside a recursion. That is P2 (LANG-099); until then they are written across ticks or with
`lmin` lattices.

### 5.5 Sticky choice: decision and revocation (LANG-115)

**Decision.** Over persistent inputs, the default `choose` is **per tick**. Stickiness is opt-in with
`choose sticky((X̄),(Ȳ))`, `choose sticky<Y>` or `choose_rand sticky<Y>`.

Reasons:
1. Per-tick is the Dedalus reading (§4.2), and its incremental form is a pure argmin (no hidden state).
2. With HRW priorities, per-tick choice is *already* stable while the candidate set's minimum is unchanged, so most
   programs do not need stickiness.
3. Stickiness makes outputs depend on the schedule (first-come wins across ticks), which is a real CALM cost. It
   should be visible in the source.
4. Protocols that need a choice to be *permanent* (a Raft vote, a Paxos promise) must persist it as protocol state
   anyway, often durably. The sticky operator is not a substitute for that (FLAG-002, FLAG-007; §12 T5).

**Expansion** (reference semantics):

```
keep_s(X̄, Ȳ)   :- held_s(X̄, Ȳ), cand_s(X̄, Ȳ), notin forced_s(X̄).     // still a candidate
kept_s(X̄)      :- keep_s(X̄, _).
fresh_s(X̄, Ȳ)  :- cand_s(X̄, Ȳ), notin kept_s(X̄), notin forced_s(X̄),
                  pminf_s(X̄, P), P == prio_s(X̄, Ȳ).
pminf_s(X̄, min<P>) :- cand_s(X̄, Ȳ), notin kept_s(X̄), P := prio_s(X̄, Ȳ).
chosen_s(X̄, Ȳ) :- keep_s(X̄, Ȳ).
chosen_s(X̄, Ȳ) :- fresh_s(X̄, Ȳ).
chosen_s(X̄, Ȳ) :- ovr_s(X̄, Ȳ).                                      // §5.6
held_s(X̄, Ȳ)@next :- chosen_s(X̄, Ȳ).
```

**Revocation.** A held choice for X̄ is revoked exactly when one of these holds at tick t:
- (i) Ȳ ∉ `cand_s(X̄)` at t, because its support was deleted (`<-`), expired, or stopped being derived;
- (ii) an override for X̄ at t selects something else.

After revocation, a fresh choice is made *in the same tick* if X̄ still has candidates. When a group has no candidates
at t, `held_s` for X̄ is dropped at t+1. **There is no memory across gaps.** If the group later regains candidates, the
choice is fresh.

**Multi-FD sticky.** Seed the greedy fold of §5.2 with `held_s ∩ cand_s`. Held tuples are mutually consistent, since
they satisfied the FDs at t−1. Then add the rest in priority order.

**Properties.**
- If `cand_s` only grows, `chosen_s` only grows. This is GPZ01's monotone multi-valued mapping, realized
  deterministically.
- The result depends on which tick each candidate first appeared in, so it is schedule-dependent (SEM-087).

**State and durability.**
- `held_s` is node state keyed by X̄.
- It is **not durable** unless declared `durable`. After a crash-restart (SEM-071) sticky choices are re-made by
  priority. They usually come out the same, unless candidates changed while the node was down.

**Incremental algorithm.**
- A hash map from X̄ to the held Ȳ.
- An insertion into a group that is already held is a no-op.
- Deleting the held Ȳ makes the group take the minimum of its ordered set, as in ENG-068.
- DD can express this directly because its `reduce` logic receives the tentative output (DDR).

### 5.6 Choice overrides (simulation and replay only)

The input relation is `__choice(site, X̄, Ȳ)` for the current node and tick. It is recorded as `ChoiceOverride`
(TEST-010) and is rejected in production builds unless `--allow-choice-overrides` is set.

Precedence is **override > sticky keep > priority**:

```
ovr_s(X̄, Ȳ)   :- __choice(site_s, X̄, Ȳ), cand_s(X̄, Ȳ).
forced_s(X̄)   :- ovr_s(X̄, _).
error("ChoiceOverrideNotCandidate") :- __choice(site_s, X̄, Ȳ), notin cand_s(X̄, Ȳ).
```

The §5.1 rule gains `notin forced_s(X̄)`. An override that names a non-candidate is a **hard error**, never a silent
fallback: it means the replay has diverged. For multi-FD sites, overrides are applied first, in priority order, and
must be mutually FD-consistent; otherwise it is a hard error.

A test-only variant, `priority_table(site, X̄, Ȳ, rank)`, replaces `prio_s` wholesale, so tests can enumerate every
permutation of a small group (TEST-012).

### 5.7 `choose_rand` (LANG-108)

Semantics are §5.1 with `rprio_s` in place of `prio_s`:
- re-drawn **every tick**;
- uniform over the group's candidates, since each candidate is equally likely to hold the minimum of i.i.d. PRF
  outputs;
- independent across groups, sites, nodes, incarnations and ticks, up to PRF quality.

**Deterministic given** (ρ, ι, the tick number). It reads `tick()`, so it is *time-varying* (LANG-170). The tick count
depends on the schedule (event-driven ticks, SEM-009), so it is also schedule-dependent.

**Incremental algorithm** (ENG-074). The site's stratum is dirty in every tick in which `cand_s` is non-empty. Every
non-empty group is re-evaluated: O(|cand_s|) per tick. That is inherent in fresh sampling. ANA-011 warns when
`choose_rand` runs over a large persistent candidate set, and suggests `choose_rand sticky`, which draws once when a
group first appears and keeps the draw while it remains a candidate.

**Bud parity.** Bud's reservoir sample is sticky under insert-only growth and is re-drawn after any deletion (§3.7).
We do not reproduce the reservoir. The Bud frontend maps `choose_rand` to ours (per tick) and documents the
difference.

### 5.8 `random()` and `rand(k̄)` (LANG-174, LANG-175)

- `rand(k̄) : u64 := F_{σ_self}("rand", ι, tick(), fp(k̄))` is a pure built-in. The same key gives the same value
  within a node and tick. Callers separate independent streams with a tag, e.g. `rand("election", Term)`. Helpers:
  - `rand_float(k̄)` in [0,1): the top 53 bits × 2⁻⁵³;
  - `rand_range(lo, hi, k̄)`: unbiased, using Lemire multiply-shift with rejection, where the j-th retry uses
    `F(…, k̄, j)`, which is deterministic.
- `random()` ≡ `rand(())`: one value per node per tick. This keeps LANG-174 and CR-18.
- **Persistent consumers.** `x(A, R) :- p(A), R := rand(A)` over a persistent `p` changes *every tick*. That is what
  Dedalus says, and the engine must do it too: it treats `rand` as a tick-local input that invalidates its dependents.
  When a value must stay fixed, it is **captured into state** with `@next`. That is the Dedalus idiom, and R07's Raft
  sketch already uses it:

  ```
  deadline(N, D)@next :- start_election(N), D := rand_range(150, 300, ("election", N)).
  deadline(N, D)@next :- deadline(N, D), notin start_election(N).
  ```

  ANA-011 lints rand/random over persistent inputs whose results are not captured.
- **Recording.** Nothing is recorded per draw. ρ and ι are in the trace. This replaces DIST-032's "the values drawn
  are recorded in the trace".
- **Cryptographic randomness** (keys, nonces that must be unpredictable) is *not* `rand`. It comes from an async
  service (LANG-184), and its results are recorded as host inputs.

### 5.9 `index()` / `enumerate` and `seq()` (LANG-093, LANG-097, LANG-098)

**Surface.**
- `r(Ā, index())`, `r(Ā, index() by (K̄ [asc|desc]))`, `r(Ā, index() per (Ḡ) by (K̄))`.
- `enumerate` is a dataflow-level synonym for `index()` over a tick's batch.

**Semantics** (per tick):
- Deduplicate the head *first*: h_s is the set of distinct head tuples without the index column. This differs from
  dfir-datalog, which numbers body rows (§3.8).
- The index of Ā is |{Ā′ ∈ h_s : same group, Ā′ ≺ Ā}|, where ≺ is (K̄ order, then `≤c` on Ā). The result is 0-based,
  dense and consecutive.

**Dedalus expansion:**

```
h_s(Ā)       :- B.
r(Ā, I)      :- h_s(Ā), I = count<Ā′> default 0 { h_s(Ā′), grp(Ā′) == grp(Ā), Ā′ ≺ Ā }.
```

This uses LANG-106's count-with-default, driven by h_s.

**Incremental algorithm** (ENG-072).
- **Tick-local h_s**, the common case (client batches, FLAG-021): sort the batch, O(n log n), with no state.
- **Persistent h_s**: an order-statistic tree per group. Inserting or deleting at rank r changes the index of every
  later element, so the output diff has size (group size − r). That cost is inherent. ANA-011 lints `index()` over
  persistent input: "ranks shift on insertion; use `seq()` for stable numbers".

**`seq()`: stable arrival numbering.** Every distinct Ā gets the next number in the first tick it appears. Within a
tick, numbers follow ≺. Numbers are never reused, and Ā keeps its number after it disappears and if it reappears. This
is LIB-064's "persistent high-water mark", made an operator. Expansion:

```
assigned_s(Ā, I)@next :- assigned_s(Ā, I).
has_s(Ā)              :- assigned_s(Ā, _).
new_s(Ā)              :- h_s(Ā), notin has_s(Ā).
nrank_s(Ā, J)         :- new_s(Ā), J = count<Ā′> default 0 { new_s(Ā′), Ā′ ≺ Ā }.
ncount_s(count<Ā>)    :- new_s(Ā).
hwm_s(0)              :- bootstrap.
hwm_s(H + C)@next     :- hwm_s(H), ncount_s(C).
hwm_s(H)@next         :- hwm_s(H), notin ncount_s(_).
r(Ā, I)               :- h_s(Ā), assigned_s(Ā, I).
r(Ā, H + J)           :- nrank_s(Ā, J), hwm_s(H).
assigned_s(Ā, H + J)@next :- nrank_s(Ā, J), hwm_s(H).
```

`per (Ḡ)` adds Ḡ to `hwm_s` and the counts. The incremental form is a hash map plus a counter.
- If a `seq` number can reach an async head or an output, `assigned_s` and `hwm_s` must be `durable`, or numbers are
  reused after a crash. ANA-011 makes that an error.
- `seq() release` drops Ā's number when Ā leaves h_s. The released number is still never reused.

**FLAG-021 idiom.** Autocomp's rules become:

```
indexed(P, index()) :- client_in(P), is_leader().
p2a(A, P, S + I)@async :- indexed(P, I), next_slot(S), acceptors(A).
n(count<P>) :- client_in(P).
next_slot(S + N)@next :- next_slot(S), n(N).
next_slot(S)@next     :- next_slot(S), notin n(_).
```

Slot assignment is now deterministic: canonical order of P within the tick. **Requirement:** a client payload carries
`(client_id, request_id)`. Otherwise two identical payloads in one tick are one fact under set semantics (SEM-007) and
get one slot.

**Frontend mapping** (LANG-222). Hydro's `index()` over a non-persisted body maps to per-tick `index()`. Over a
persisted body with no aggregate it maps to `seq()`. With an aggregate it maps to per-tick `index()` over the groups.
All three use canonical instead of iteration order, which is a documented deviation.

### 5.10 `sort`, `topk`, `limit`, `percentile` and list-valued aggregates (LANG-118)

Every order-sensitive aggregate orders by (user key, then `≤c` on the whole tuple). So each one is a deterministic
function of its input set.

- `sort<X̄ by K̄>` returns a list sorted that way.
- `topk<k, X̄ by K̄ [desc]> per Ḡ` returns the tuples whose §5.9 index is below k. `limit<k>` is `topk` by `≤c`.
- `percentile<p, X>` is nearest-rank: the element at rank ⌈p·n⌉ − 1 in `≤c` order.
- `collect_vec`, `accum` and `mklist` return **canonically sorted** lists, never hash or insertion order. `set` is an
  `lset` lattice.
- `argmin`/`argmax` return all tied exemplars (LANG-103), which is deterministic.

**Incremental algorithm** (ENG-072).
- `topk` keeps an order-statistic tree. An insert or delete changes the output by at most one entering and one
  leaving tuple. This is the classic incremental top-k (Materialize's TopK, DD's `topk`).
- `sort` over a persistent input emits a new list value on every change, O(n). ANA-011 lints it.

### 5.11 `fold_ordered`, `reduce` and user-defined aggregates (LANG-110, LANG-109, LANG-105)

**Semantics.** `fold_ordered(init, step, R(ū) order by K̄ [per Ḡ])` left-folds the pure function `step` over the
*distinct* rows of R at the tick, in (K̄, `≤c`) order, starting from `init`.

**Dedalus definition.** It uses §5.9's index plus positive recursion over a bounded counter. There is no negation on
the cycle, so SEM-020 accepts it.

```
rk_s(Ḡ, ū, I)       :- R(ū), I = index() per (Ḡ) by (K̄).
acc_s(Ḡ, 0, S)      :- drive_s(Ḡ, S0), S := S0.              // init per group
acc_s(Ḡ, I + 1, S′) :- acc_s(Ḡ, I, S), rk_s(Ḡ, ū, I), S′ := step(S, ū).
n_s(Ḡ, count<ū>)     :- R(ū).
out_s(Ḡ, S)          :- acc_s(Ḡ, N, S), n_s(Ḡ, N).
out_s(Ḡ, S0)         :- drive_s(Ḡ, S0), notin n_s(Ḡ, _).      // empty group, carried form only
```

**Two forms.**
- *Aggregate form*: `r(Ḡ, fold_ordered(init, step, …))`. `drive_s` is "some row exists", and an empty group gives no
  row (CR-08).
- *Carried-state form*: `state(S2)@next :- state(S), S2 = fold_ordered(S, step, D order by K̄)`. `drive_s` is the
  current state, and an empty D gives S2 = S.

  **The carried form re-applies every row of D every tick**, because Dedalus demands it. If D is persistent, that is
  almost always a bug: re-applying a whole log. ANA-011 lints it, and it is an error under `--strict`. The correct
  pattern derives the *new* rows each tick, as in Raft's `to_apply`, which is `last_applied < I ≤ commit_index`
  (§12 T6).

**Incremental algorithm for a persistent R in the aggregate form** (ENG-073).
- Keep R's sorted index and checkpoints `(key_j, S_j)` every c rows, plus the final state.
- On Δ with smallest affected key k*, resume from the last checkpoint below k* and re-fold the suffix.
- If keys arrive in increasing order (log indices), a tick costs O(|Δ|).
- The worst case is O(n): a deletion or insertion at the front. ENG-064's elastic recompute bounds it.
- `step` is pure, so the result equals naive evaluation exactly.

**`reduce` and UDAs.**
- If `f` is declared commutative *and* associative (LANG-105, LANG-182), the engine may combine in any order and merge
  deltas.
- Otherwise the operator **is** `fold_ordered` by `≤c`, which is deterministic.
- Declarations are trusted by the engine but *checked* by the oracle (TEST-015: evaluate in shuffled orders, as in
  Hydro's "commutativity proofs are hooked, not trusted"). VER-014 proves them where the SMT fragment allows.

### 5.12 Keys, relation-level resolution and retraction (SEM-050/051; LANG-117)

- **Choose into a keyed relation.**
  - If r has key K and the choose rule's X̄ ⊆ K, the rule alone can never violate SEM-050: two chosen tuples with the
    same K agree on X̄, hence on Ȳ, hence on every column.
  - If X̄ ⊄ K, ANA-007 warns, because conflicts are possible.
  - Different rules writing the same key with different values are still a SEM-050 error.
- **Relation-level resolution** (ODD-02's option (c), made concrete): `table r(k̄, v̄) key(k̄) resolve <policy>`, where
  `<policy>` is one of `choose`, `choose sticky`, `choose_rand`, `choose_least(c)`, `choose_most(c)`, or a lattice
  merge. The candidates for key k̄ at t+1 are *every tuple that would be present at t+1*:
  - persisted tuples that are not deleted;
  - `<+` insertions;
  - `<+-` upserts. An upsert removes the old tuple, so it does not compete.

  The policy selects one per k̄, and conflicts become resolutions instead of SEM-050 errors. Choices:
  - `resolve choose sticky` is a *first-writer-wins register*, because the old tuple is held.
  - `resolve choose_least(ts)` with a tie-free `(ts, node)` column is an LWW register (compare LANG-131).
  - Same-tick deductive derivations (`:-`) into r are resolved in r's stratum, over `r_cand`.

  In every case r cannot sit on a same-tick recursive cycle (SEM-086).
- **Conflicting upserts** (SEM-051): `<+- resolve choose|…` applies the same policy to the tick's conflicting upserts.
- **Retraction.** A choose output is *derived*. When candidates are retracted (`<-`, loss of support, TTL expiry
  under SEM-060), the output changes per §5.1 and §5.5 in that tick. No tombstone is left behind. The only
  choice-specific persistent state is `held_s` (sticky) and `assigned_s`/`hwm_s` (`seq`).

### 5.13 Stratification and CALM classification (SEM-086, SEM-087)

- Every choice and order-sensitive site is a **negative edge** (SEM-021). A site may not be on a same-tick recursive
  cycle. The error shows the cycle as a witness (ANA-002).
  - This matches SZ90's condition (c) and the "stratified modulo choice" class of GSZ95/LDLPP.
  - Across `@next` it is fine. A BFS spanning tree built one layer per tick is §12 T8.
- **Nondeterminism classes** (SEM-087), recorded per relation and per output:
  - **deterministic**: argmin/argmax/topk/sort/index/fold_ordered, choose proven forced (§6), and every
    order-insensitive operator;
  - **seed-dependent**: stateless `choose`, multi-FD choose, and `choose_least` with possible ties. Same seed and
    same inputs give the same output everywhere;
  - **schedule-dependent**: `choose sticky`, `choose_rand`, `rand`/`random`, `seq`, `tick()`, `now()`. The output
    depends on tick boundaries, arrival ticks or tick counts.
- **CALM.**
  - Stateless `choose` behaves like `min`: a non-monotone aggregate whose final value needs sealed input
    (ANA-028, ANA-046).
  - Sticky choice is monotone in time over insert-only candidates, but it is not confluent. It is a point of order
    for Blazes (ANA-042) and for TEST-003's schedule pruning: deliveries feeding it must be permuted *across tick
    boundaries*.
  - ANA-029 gains the certificate "deterministic given seed" for seed-dependent outputs. Seed sweeps test it
    (TEST-014).

### 5.14 Crash and recovery

| Operator | After a restart (SEM-071) |
|---|---|
| Stateless `choose` | Recomputed. σ_c is unchanged, so the same candidates give the same choice |
| `choose_rand`, `rand` | ι changes, so draws differ, as intended (e.g. election timeouts) |
| `choose sticky` | `held_s` is lost unless durable, and the choice is re-made by priority |
| `seq` | `assigned_s`/`hwm_s` must be durable if their numbers escape the node (ANA-011) |

### 5.15 Provenance and LDFI (ENG-116, TEST-040)

**Firing log** (Tier C, ENG-112). A choose site records `(site, tick, X̄, chosen Ȳ, |cand(X̄)|, reason ∈
{priority, sticky, override})`.

**Lineage.**
- *Default*, as TEST-024 does for aggregates: `chosen_s(X̄,Ȳ)` depends on *all* candidates of its group.
- *Refined*: positive support on `cand_s(X̄,Ȳ)`, plus a negative dependency on the absence of every lower-priority
  potential candidate. TEST-025's negative support resolves the latter through why-not provenance (TEST-051).

**Choice stability across LDFI runs.** Every hypothesis run uses the failure-free run's ρ. A choice (X̄, t) in a
faulty run is identical to the failure-free one whenever the chosen candidate survived and no lower-priority candidate
appeared. With first-seen or RNG-stream resolution, a fault anywhere perturbs all later choices. LDFI would then blame
the fault for divergence that the RNG caused. HRW prevents this.

**Whynot** (TEST-050). "Why was Ȳ′ not chosen for X̄ at t?" is answered with one of:
- "Ȳ′ was not a candidate", with a why-not proof;
- "Ȳ had lower priority";
- "Ȳ was held (sticky) since tick t₀";
- "an override selected Ȳ".

## 6. When a choice or order is actually deterministic (deliverable 2)

The general question is undecidable (GSZ95 §3). We therefore use **sound sufficient conditions**, all decidable in
PTIME from the rule text and the schemas (ANA-038).

**FD set of a rule body, F(r).** It is generated from these sources:
1. declared keys: a body atom `p(ū)` with key K gives vars(K) → vars(ū); a keyless relation, whose key is all
   columns, gives nothing;
2. singleton relations (`key()`): ∅ → all columns;
3. `X = Y` gives X ↔ Y, and a constant gives ∅ → X;
4. `X := f(Ȳ)` with f pure gives Ȳ → X, and a declared `injective` f also gives X → Ȳ (LANG-182);
5. lattice relations: non-lattice columns → lattice column (LANG-121);
6. aggregate or choose outputs in body atoms: group key → aggregate or chosen columns;
7. channel keys checked at the sender (LANG-042).

Closure is ordinary attribute closure under Armstrong's axioms (linear time). ANA-080 already infers FDs; this reuses
it.

The conditions:

- **D1 (forced choice).** `choose((X̄),(Ȳ))` is deterministic if Ȳ ⊆ closure(X̄) under F(r). ANA-038 reports it as
  *redundant*.
- **D2 (total order).** For `index`, `sort`, `topk`, `percentile` and `fold_ordered` with key K̄ over input columns
  C̄: if closure(K̄) ⊇ C̄, the order is tie-free. Otherwise the lint is "ties broken by canonical order". The output is
  still deterministic, and the lint only says the order is partly arbitrary. This is the new meaning of LANG-093's
  flag.
- **D3 (locally resolved choice**, in Hydro's terminology). A choose site is *seed-independent at output O* if every
  dataflow path from `chosen_s` to O begins with one of:
  - a projection that drops every column derived from Ȳ;
  - an existence test `chosen_s(X̄, _)`.

  The reason is maximality: π_X̄(chosen_s) = π_X̄(cand_s) for stateless, sticky and multi-FD choose alike. This is
  checked by column-level taint propagation (ANA-032) from Ȳ.
- **D4 (choice-invariant consumers).** `count<*>` per X̄ of `chosen_s` is 1, and any function of π_X̄(chosen_s) is
  seed-independent. This is a special case of D3, listed for the analyzer's pattern table.
- **D5 (unique preference).** `choose_least((X̄),(C))` is deterministic if Ȳ ⊆ closure(X̄ ∪ {C}) and C is unique per
  X̄. That second part holds if (X̄, C) is a superkey of the candidate relation, i.e. X̄C → W̄.
- **D6 (commutativity claims).** Undecidable in general. They are proven by VER-014 where the SMT fragment allows, and
  otherwise tested (TEST-015). The certificate says "tested, not proven".

**What the analyzer reports** (LANG-093 and LANG-108 as amended):
- order-sensitive operators are *always* deterministic, with a lint when D2 fails;
- a choose site is *deterministic (forced)* when D1 or D5 holds, *seed-independent at O* when D3 or D4 holds, and
  otherwise *seed-dependent* or *schedule-dependent* (SEM-087);
- the class propagates to ANA-029's per-output certificate and to TEST-003's pruning.

## 7. Record and replay (deliverable 3)

### 7.1 What must be recorded

Under SEM-083, a node's tick is a function of the following. Nothing else is recorded:
- the delivered batch;
- timer firings;
- host inputs;
- the `now` sample;
- the seeds;
- the node's incarnation;
- the override relation;
- its own state.

Choices, `rand` draws and `index` values are **recomputed** during replay. The trace carries digests of them so that
divergence is caught in the tick where it happens.

### 7.2 Trace format (TEST-010)

The container is length-prefixed records in a schema-versioned compact binary encoding: the same canonical encoding as
DIST-003 (e.g. postcard). Files are append-only, one per run in simulation, or one per node in production flight
recording.

```
Header {
  format: "bloom-remake-trace", format_version: u32,
  program_digest: [u8; 32],            // hash of normalized IR incl. site ids and rule labels
  compiler_version, prf_version, canonical_encoding_version,
  root_seed: u128,                     // simulation; production: deployment-seed id (the seed itself stays in config)
  mode: Simulation { network: Fair | Lossy | Sync, fault_spec: Option<FaultSpec> } | Production { node },
  nodes: [NodeId], constants: map (LANG-010), static_facts_digest,
  level: Minimal | Digests | Full,
}

Event =
  | SchedStep   { step: u64, node }                                   // simulator: which node ticks next
  | TickBegin   { node, incarnation: (u64, u64), tick: u64, now: Timestamp,
                  trigger: Message | Timer | Host | Staged }
  | Deliver     { node, tick, channel, from, send_tick, fact }        // SEM-007 identity: (from, send_tick, node, fact)
  | Drop        { from, to, send_tick, channel, fact, cause: Omission | Crash | Partition }   // fault record
  | TimerFire   { node, tick, timer, fire_id }
  | HostInput   { node, tick, relation, fact }
  | ChoiceOverride { node, tick, site, group: Value, chosen: Value }   // only when forced by explorer or script
  | PriorityTable  { node, site, table: [(group, candidate, rank)] }   // test-only (TEST-012)
  | Crash       { node, tick } | Restart { node, incarnation }
  | TickEnd     { node, tick,
                  state_digest,         // ENG-120, modulo time        (Digests, Full)
                  outbox_digest,        // canonical order of sends     (Digests, Full)
                  choice_digest }       // H over (site, group, chosen) in canonical order (Digests, Full)
  | ChoiceLog   { node, tick, site, group, chosen, n_candidates, reason }   // Full
  | Send        { node, tick, channel, to, fact }                           // Full; LDFI message log (TEST-023)
```

**Recording levels.**
- `Minimal` has only inputs. It is enough to replay.
- `Digests` adds `TickEnd` digests. It is the default in simulation and CI.
- `Full` adds choice logs and sends, for LDFI, the replay viewer (TEST-064) and debugging.

**Production.** Flight recording is optional (P1). It logs inputs per node, with FLAG-132's CALM minimization: only
inputs that reach points of order need exact batch boundaries.

### 7.3 How each tool consumes the trace

**Replay** (TEST-011).
1. Check `program_digest`, `prf_version` and `canonical_encoding_version`. A mismatch is a hard error: "trace recorded
   with a different program or PRF; replay would diverge". There is no best-effort mode.
2. Re-derive σ_c, σ_n and ι.
3. Feed the recorded inputs and overrides per tick, in `SchedStep` order.
4. At every `TickEnd`, compare digests. The first mismatch stops replay with a *divergence report*: node, tick, and
   the first differing component. The report gives the relation and the choice site, found by recomputing `Full` data
   for that tick.

**Simulator** (TEST-001/002).
- The scheduler's decisions *are* the recorded events: `SchedStep`, `Deliver` batches, `Drop`, `TimerFire`, `Crash`.
- A run is reproducible from ρ alone, because the scheduler is seeded. The trace also supports delta-debugging over
  events, because each shrunk event list is a replayable input.
- Choice exploration (TEST-012) adds `ChoiceOverride` or `PriorityTable` events. Sticky and seed-dependent sites can
  be enumerated exhaustively for small groups, as Hydro's exhaustive mode does for its hooks.

**LDFI** (TEST-020..029, TEST-040).
- The failure-free run is recorded at `Full`.
- `Send` and `Deliver` give the message log (TEST-023).
- `ChoiceLog` gives the chosen candidate for lineage (§5.15).
- Hypotheses run with the same ρ and **without** overrides, so choices are recomputed. HRW keeps them stable unless
  the fault removes the chosen candidate.
- Omissions and crashes appear as `Drop` and `Crash` events, so a counterexample is itself a replayable trace.

**Oracle** (§8). The engine and the naive evaluator both consume the same trace and must produce identical `Full`
records.

## 8. Differential-testing oracle (deliverable 4)

ENG-067 already requires every incremental path to be tested against naive re-evaluation. For the operators here, the
strategy is:

- **A. Exact equality (P0).**
  - The naive oracle evaluates the *Dedalus expansions of §5* by recomputing every relation from scratch each tick,
    from the recorded inputs, seeds and overrides.
  - The incremental engine runs the same trace.
  - At every tick, compare the full contents of every relation (not only digests), the outbox and the choice log.
    Any difference is a bug.
  - There is no "modulo choices" here. Choices are functions of the seed, so both sides must agree bit for bit.
- **B. Choice validity (P0, TEST-013).** Independently of both implementations, a checker verifies at every site and
  tick:
  - chosen ⊆ cand;
  - every FD holds;
  - maximality (every group with a candidate has a choice; for multi-FD, every rejected candidate conflicts with an
    accepted one);
  - priority minimality (the chosen candidate has the least `prio_s` among non-held candidates);
  - the sticky rule (the held choice was kept iff it was still a candidate);
  - override adherence;
  - `index` density and order, and `seq` monotonicity and non-reuse.

  This catches bugs that the engine and the oracle share, such as a mis-keyed PRF.
- **C. Equivalence modulo choices (P1, TEST-014).** Used for external or alternative implementations: Bud programs,
  Hydro programs through LANG-222/223, Soufflé choice-domain programs, and a future second backend.
  1. Extract the external run's choice per site, tick and group from its outputs.
  2. Validate those choices with B. An invalid external choice is reported as a *semantic difference*, not accepted.
  3. Replay our oracle with the extracted choices as `ChoiceOverride` events.
  4. Compare everything else exactly.

  This is the precise meaning of "compare engine and naive evaluation modulo recorded choices".
- **D. Seed sweeps (P1).** Run the same inputs under N seeds.
  - Outputs certified seed-independent (§6, D1/D3/D4/D5) must be identical across seeds. This tests the analyzer's
    soundness.
  - For other outputs, the program's spec rules (`violation`, `pre`/`post`) must hold for every seed. This tests that
    the *application* tolerates every choice, which is what "nondeterministic by design" should mean.
- **E. Shuffle checks (P1, TEST-015).**
  - The naive oracle evaluates every UDA and `reduce` declared commutative/associative in k random orders and
    compares the results.
  - The engine's delta-order evaluation must also agree.
  - Any mismatch is a false declaration and a hard error that names the aggregate.
- **F. Incremental stress schedules (P0).** Generated input sequences that exercise:
  - insert, then delete the chosen candidate;
  - delete a non-chosen candidate (the Bud case);
  - re-insert after a gap;
  - idle ticks;
  - growth to a new group minimum;
  - crash and restart with and without durable sticky state;
  - `index()` insertions at the front;
  - fold inserts before the current prefix.

  Each schedule runs through A and B.
- **G. Priority-permutation exhaustiveness (P1).** For small groups, TEST-012's `PriorityTable` enumerates every
  priority permutation. The expected outputs of §12 T1 and T7 are stated for *all* of them.

## 9. Proposed amended CR-26, and two new conflict resolutions

**CR-26 Replay of persistent state (amended).**
- *Positions.*
  - DFIR `'static` joins replay their full output every tick.
  - In Dedalus, persisted facts exist at every tick, so derivations from them recur.
  - Bud caches results and invalidates the caches. Its `choose`/`choose_rand` state survives insert-only ticks and is
    rebuilt in storage order after any deletion (R12 §3.7).
  - Hydro's Datalog `choose` over a persisted body keeps the first value it saw, forever. Its `index()` over a
    persisted body is arrival numbering (R12 §3.8).
  - Soufflé keeps the first tuple in evaluation order (R12 §3.6).
- *Adopted.*
  - The **semantics** is Dedalus: every derivation recurs at every tick in which its body holds.
  - The **implementation** maintains deltas (ENG-004), and must be **observationally identical** to naive
    re-evaluation of the program's Dedalus expansion, tick by tick (ENG-067). **No observable difference is
    permitted.**
  - Four mechanisms make this achievable:
    1. Every nondeterministic or order-sensitive operator is defined by a Dedalus expansion over the canonical order
       and a seeded PRF (SEM-083/084). Its output is a function of the tick's input set, its explicitly carried state
       and the seeds, never of iteration, arrival, interning or cache order.
    2. `choose` and `index()` are per tick; the tick is in the FD's determinant (SEM-085). Carry-over exists only as
       the explicit `choose sticky` and `seq()` forms, whose state is part of their expansion (LANG-115, LANG-098).
       Persist-pullup rewrites never cross these operators (ENG-069).
    3. Async sends derived from persistent state are re-sent every tick (ODD-05). Suppression is allowed only where
       ARM proves it equivalent (DIST-007). Host callbacks declare full-contents or delta delivery (LANG-185). In both
       cases the engine implements the literal semantics, and any optimization must be proven equivalent.
    4. Replay needs only the recorded inputs, seeds, incarnations and overrides. Choices and draws are recomputed, and
       per-tick digests detect divergence (TEST-010, TEST-011).
- *Why.*
  - Only functions can be maintained incrementally with retractions (DBSP; Feldera: "assumes that all computations
    are deterministic").
  - DD stores its produced output "to avoid potential non-determinism" in user logic (SHARR §5.3).
  - Making choice a function of the seed keeps choice in the language (Dedalus, Bloom) without giving up exact replay,
    exact oracles or LDFI comparability.

**CR-45 Resolving choice.**
- *Positions.*
  - Declaratively, choice denotes *any* stable model (SZ90, GZ01).
  - Bud: first value pushed. Soufflé: first in evaluation order. Hydro: first in dataflow order, sticky over
    persisted bodies.
  - Bud's `choose_rand`: a reservoir over a process-global RNG.
  - Greedy choice (GZ01): least cost, with arbitrary ties.
- *Adopted.*
  - `choose` picks the least seeded priority `(PRF_{σ_c}(site, X̄, Ȳ), Ȳ)` among the tick's candidates, with a
    deployment-wide choice seed (SEM-085).
  - `choose_least`/`choose_most` order by cost first.
  - `choose_rand` and `rand` add node, incarnation and tick to the key.
  - Stickiness is explicit.
- *Why.*
  - It selects a genuine choice model (GZ01 Thm 5.3).
  - It is deterministic and replayable from the seed.
  - It is independent of plan and iteration order.
  - Its incremental form is an argmin index.
  - It gives HRW agreement across nodes and choice stability under fault injection.

**CR-46 Numbering and folding over persistent inputs.**
- *Positions.*
  - Hydro `enumerate::<'tick>` restarts at 0 every tick. `enumerate::<'static>` counts up for ever, in arrival order.
  - Bud warns that `each_with_index` is undefined by the language.
  - DD offers hash-based identifiers (`identifiers.rs`).
- *Adopted.*
  - `index()` is a dense per-tick rank in `(key, canonical)` order, after head deduplication.
  - `seq()` is stable arrival numbering with an explicit high-water-mark expansion.
  - `fold_ordered` is a per-tick pure left fold in the same order.
  - Carried folds over persistent inputs are linted.
- *Why.* Each operator is a function of its input set (plus explicit state for `seq`). The two numbering needs, "rank
  within this tick's batch" (Paxos slots) and "permanent id" (LIB-064), are both served, and neither is silently
  substituted for the other.

## 10. Known limitations and risks

1. **Per-tick `choose` is not monotone.** A new lower-priority candidate retracts the old choice. Programs that
   observed the old choice must tolerate that, or use `sticky`, or persist the choice. The analyzer marks such outputs
   seed-dependent, and ANA-028 never lets them be emitted as final.
2. **`index()` over large persistent inputs** produces O(n) output diffs per front insertion. **`choose_rand` over
   large persistent inputs** costs O(n) per tick. Both are linted. `seq()` and `choose_rand sticky` are the cheap
   alternatives.
3. **Tick numbers enter `rand`/`choose_rand`.** Two schedules that produce different numbers of idle ticks give
   different draws. This is correct (the output is schedule-dependent), but tests that compare across schedules must
   compare invariants, not values.
4. **Replay across program edits is impossible by design.** Site ids and the program digest change, and replay stops
   with an error. Traces are tied to a program version.
5. **The PRF and the canonical encoding are frozen per version.** Changing either invalidates golden outputs and
   traces, so both carry version numbers.
6. **In-tick recursive greedy choice** (Prim, Dijkstra, Soufflé-style spanning trees) is deferred to P2 (LANG-099).
   Until then those algorithms run across ticks or with lattices.
7. **The Bud and Hydro frontends are not behavior-identical** for choice and numbering (§3.7, §3.8). The difference is
   documented, and TEST-014 checks equivalence modulo choices.
8. **Unverified literature.** I could not read Giannotti–Manco–Nanni–Pedreschi's TKDE 2001 treatment of choice with
   stage arguments (§0.2). If it contradicts §4.2, the design phase should revisit.
