# S10: the Kafka comparison, and performance (working notes)

Slice 10 of `docs/design/SLICES.md`: the same workload against Apache Kafka on the same machine, with the same client
and durability, reported honestly as the etcd comparison was. Branch `slice-10`, worktree `.worktrees/s10`, from main
after S9 (9b1347b).

The user's direction (2026-10-03): Redpanda is not needed ("if you have Kafka and it's already faster than us, that's
all we needed to know"); with correctness in place, the work is performance. On durability: keep it, and follow best

## Setup

- **Machine:** computer.jimmyhmiller.com: AMD Ryzen AI Max+ 395 (32 threads), 125 GB, two WD SN7100 NVMe, Ubuntu
  24.04, Linux 7.0. Every broker and the client on the one machine.
- **Blossom:** `examples/kafka/broker.bls`, three `blossom run` processes (release build) on localhost.
- **Apache Kafka 4.0.0:** three KRaft nodes, each broker and controller, `log.flush.interval.messages=1` (every
  append fsynced on every replica before it is acknowledged or fetched further).
- **Client:** Kafka's own `kafka-producer-perf-test` (Java 4.0: idempotent, `acks=all`, `batch.size` 16 KiB,
  `linger.ms` 5), one topic of 6 partitions replicated 3 times, 1 KiB records.
- **Script:** `scripts/bench-kafka.sh up blossom|kafka`, `produce …`, `down`.

## Durability: are we at best practice? (asked 2026-10-03)

- At best practice: a WAL of checksummed records; group commit (one sync for every tick's records in a batch);
  pipelining (the next tick computes while the fsync runs); record batches travel in the WAL record (no fsync per
  blob); no send before the state behind it is durable (a Raft vote must survive a crash once sent).
- Not: (1) `strict` tail certification, the default, syncs three times per commit (the data, then an atomic receipt
  file: write, fsync, rename, directory fsync). etcd, Kafka and Postgres sync once per group commit and take a damaged
  tail as torn: our `crc`. (2) WAL segments are not preallocated, so a sync also commits the file's growth (etcd
  preallocates 64 MB, Postgres 16 MB). (3) A Raft leader cannot send entries before its own fsync (every send waits
  for its tick's sync); the Raft paper lets a leader write and send in parallel, counting itself only once synced.
  That needs a runtime feature (sends that may leave before the sync, and a "synced" event), not a setting.
- Measured on this machine: `crc` against `strict` changes throughput by 2% (Linux NVMe fdatasync is cheap; macOS's
  F_FULLFSYNC made it 4x in the etcd comparison). The engine thread was at 100% and the committer idle: the bound
  is CPU, not the disk.

## Found on the way

- **The language had no loop that ends early.** Functions iterate only with bounded combinators, so a decoder that
  stops at the end of its input walked the worst case. `v.scan_while(init, |acc, x| e)` (`e: Option<A>`) stops at
  the first `None`; over a `range` it is a bounded loop.
- **A `per` driver decides which groups exist.** My first decode-once change drove `part_producers` by the new
  `append_producer` view instead of `appends`; partitions whose appends carry no producer id (non-idempotent
  producers) then had no driver tuple, so no default row, so their entries were never sequenced (`kafka_cluster`:
  "an entry has no answer"). I first took it for an unenforced BLS0511 rule and wrote a check, which also refused
  sound drivers in the existing program (`per fetch_head(c, …, _req)`: an extra driver variable is projected away);
  the check was reverted. LANGUAGE §10.2's sentence that other driver variables "must be functionally determined" by
  the grouping columns is therefore not enforced, and the programs do not follow it literally: an open language
  question, not a bug found here.
- **Older clients:** S7 implemented exactly the versions the target clients send (Produce 10-12, Fetch 16-17,
  ListOffsets 7-10, Metadata 13). Ubuntu 24.04's kcat (librdkafka 2.3) finds no common version and refuses ("Required
  feature not supported by broker"); Kafka 4.0 serves it. Not in this slice; recorded as a compatibility item.
- **Server tools:** the full tier on the server had been skipping the stock-client checks (no Kafka distribution,
  no kcat, Go off the PATH): `SKIPPED` lines in passing tests. The server now has Kafka 4.0 (`~/bloom-tools`, linked
  into each checkout's `.tools`), kcat 1.7.1 with librdkafka 2.15.1 built into `~/bloom-tools/kcat`, and Go on the
  tier scripts' PATH.
