## Expectation vocabularies used and introduced

PLAN §5.1 names the `[expect_analysis]` keys but not their contents. The corpus uses these shapes; M5.2 (lint), M6.6,
M7.3 (P1 analysis backend) and M7.5 should read them as the contract, or change them together with the cases.

- `points_of_order = { complete, edges = [{from, to, kind[, reason]}], clusters = [[...]], crossing = [{from, to}],
  free = [...] }`; `calm_labels = { outputs = {rel = label}, paths = [{from, to, label}], races = [{channels, meet,
  guarded}] }`; `certificates = { rel = [kinds] }`; `confluent` and `fair_consistency = { rel = verdict }`;
  `finality = { rel = [classes] }` (ANA-120 classes; a list when a relation is final early one way and at a seal the
  other, e.g. `["THRESH", "SEALED"]`); `strata = { count, of = {rel = n} }`.
- `strata.count` is the number of strata of SEM-022's stratification **including** its final temporal pseudo-stratum
  (SEM-022 step 5, which holds every `next` and async rule), because Bud's `stratified_rules.length`, which BENCH-100
  ports, counts its temporal stratum the same way (R03 §4.3 step 4: "every temporal rule goes into a final stratum
  top+1"). So BENCH-100 has count 2 (one deductive stratum plus the pseudo-stratum) and BENCH-083a count 3 (reach in
  0, garbage in 1, plus the pseudo-stratum). `of` gives the 0-based stratum of each listed relation and is not
  exhaustive: relations it leaves out are not compared.
- `blazes` (BENCH-094), a table with: `paths` (array of `{component, from, to, annotation, gate?}`: components are
  module instances, ARCHITECTURE §7.2; `from`/`to` are the instance's input and output interfaces; annotation CR/CW/OR/OW
  with the gate as sorted column names); `streams` (channel name → label); `sinks` (program output → label);
  `coordination` (array of `{at, mechanism = "ordering" | "sealing", key?}`); `cycles` (the collapsed components);
  `collapsed` (`{members, annotation, gate}`). Labels are NDRead, Taint, `Seal(k1, …)`, Async, Run, Inst, Diverge.
- `reclaimable` (BENCH-095), a table with: `reclaimed` (relation → `dr_plus` | `dr_minus` | `join_seal` |
  `join_pullup` | `join_semijoin` | `join_keys`); `kept` (relation → reason code: `negated_input_deleted`,
  `negated_scratch_not_inflationary`, `negated_scratch_not_monotone`, `negated_scratch_not_grounded`,
  `negated_scratch_from_channel`, `reaches_output`, `aggregated`, `negated_by_non_candidate`,
  `negated_with_predicate_block`, `downstream_table_deleted`, `quals_not_positive_keys`, `unsealed_join`, `range`,
  `no_negation`, `not_reclaimable`, `dominance_by_transitive_closure`); `channels` (channel → `arm`); `storage` (array of
  `{node, rel, tick | final, rows}`: the contents of the relation **in the Edelweiss-rewritten program** in the case's
  run); `ranges` (array of `{node, channel | rel, tick | final, buckets}`: the buckets of the ARM approximation of a
  channel, or of a `range(col)` table, as `[other columns…, lo, hi]`). The `storage` and `ranges` entries are run-time
  facts of the rewritten program; they are checked where M7.5 runs original and rewritten programs side by side.
  `[[expect]]` rows are always about the program as written, and for outputs they must also hold after the rewrite
  (ANA-066), which is why output assertions appear in both places.
- `[expect_verify] result = "fails"` in BENCH-150 (b) means "not proved because the VC is outside EPR" and in (c) "a
  counterexample to induction"; schema v1 has no key to tell the two apart (see Follow-ups). Both manifests say which.
- Sim cases whose scenario is written as spec facts say so in `notes` (BENCH-090x, 094k, 098, 099b); their `[[input]]`
  list is empty. `[[expect]]` rows may name views (for example `live`, `view`, `read_view`): the harness observes every
  relation of a node, not only outputs.
- `quiescent_from = q` is written as a tick from which, on every node, no relation (persistent or tick-local) differs
  from the previous tick and no message is in flight. That implies ARCHITECTURE §4.11's condition (the state digest,
  which covers persistent state and staged changes only, equals the previous tick's, with no pending input) at every
  tick from q on, so every value holds under the digest definition, since PLAN §5.1 reads "quiescent from that tick
  on". It can be later than the first digest-quiescent tick. BENCH-100 keeps no persistent state, so its digest never
  changes and the digest reading makes it quiescent as soon as nothing is pending (after tick 7). The case says 9
  instead: tick 7 still received messages, and tick 8, the first empty tick, is repeated by tick 9. BENCH-084a/d (8),
  085a (3), 101 (44) and 102a (4) were computed the same way. BENCH-082e's 1 is the first quiescent tick under both
  readings: its program keeps nothing tick-local and sends nothing, so tick 1 repeats tick 0.
- **Row values of `Node` columns** name deployed nodes (PLAN §5.1 decodes a string in a `Node` column as a node name;
  ARCHITECTURE §2 and §5.9 assign `NodeId`s from the deployment directory), in `[[input]]`, `[[expect]]` and the
  `reclaimable` entries, and so do the `Node` values of a program's `fact`s. Every M1.4 case was checked for this. A
  `.ded` case's rows omit the location column, which the frontend strips (ARCHITECTURE §13.12), so their string
  values are data, not nodes. Analysis-only cases of multi-role programs whose facts and rows name no node
  (BENCH-094a-j) carry no `[deploy]`: static analyses need no deployment, and PLAN §5.1's default (one node of the
  only role) does not apply to them.
- **Diagnostic matching.** PLAN §5.2 says the `compile` backend expects no diagnostics when `[[expect_diag]]` is empty,
  and says nothing about the `analysis` backend. The cases are written against this convention, which M5.2 should
  adopt or replace (a PLAN §5 decision; see Follow-ups):
  - `compile` runs the frontend only (PLAN §5.2; ARCHITECTURE §13.1 lists each phase's codes) and compares **every**
    frontend diagnostic, warnings included, with `[[expect_diag]]`. BENCH-102c is the only M1.4 compile case; its
    program draws BLS0400 at line 27 and nothing else (below).
  - `analysis` compares the diagnostics of blossom-analysis (ARCHITECTURE §13.1: stratification, CALM, determinism,
    finality, lints) **exhaustively for the codes of the ANA features the case lists**, and ignores the other
    analyses' diagnostics. Listing ANA-008 makes BLS1002 exhaustive (BENCH-093e: exactly two; BENCH-093g: none);
    listing ANA-120 does the same for BLS0705 (BENCH-099c: exactly one; every other case that lists ANA-120 declares
    `final output` only for accepted classes); ANA-002 for BLS0502/0503 (none of its cases is unstratifiable).
    Comparing every analysis diagnostic of every case would make each case depend on the precision of every lint
    (BLS0802 sender binding, BLS1003 key conflicts, and so on). The cart programs of BENCH-093b/c, for example,
    reply to a `client` payload column, which ANA-106 (BLS0802) may flag, and no literature source says what such
    lints report.
  - `line` is the line of the construct the diagnostic's primary span names: the statement for a statement-level
    error (BLS0400), the relation's declaration for a relation-level report (BLS1002, BLS0705).
  - Every program of the corpus was checked with the design-phase checker (patched to model `node_dir`, `c.payloads`
    and LANGUAGE §8.5's rule that only a handler's header makes its statements event-driven): no program draws
    BLS0504 (`on` without an event literal) or BLS0505 (`while` with one); see "Review fixes".

### BENCH-150 (Paxos Made EPR)
- The program transliterates EPR Fig. 3: one role, every message broadcast to every replica, rounds u64 with 0 as ⊥,
  a static `owns` for "each round has a unique owner", a static `value` domain for proposable values, and the owner's
  proposal chosen as the max over all acknowledgements received (a superset of a quorum), else the host's value.
- Tick batching: a replica may join several rounds and vote in one tick; a vote waits for no round above it joined in
  or before the tick (`joining`), so a tick equals an EPR interleaving (joins in increasing round order, then votes).
  A throwaway randomized model of this tick semantics (20,000 runs, 3 nodes, 4 rounds, 2 values; not our
  implementation) found no violation of (4)–(11), (13)–(15) or the representation lemmas, and it did find violations of
  (8)/(10) without the `joining` guard and of (13) when the proposer ignores reports.
- The spec states EPR's vocabulary as views over the network (message relations without the fields EPR does not have)
  and the derived relations over the program's own `joined` table, so program guards and invariants use the same
  derived relation, then states eqs. (4)–(15) verbatim; ∀ over rounds and values is written with range generators
  (`r1 in 0..r2`) and the static `value` domain to stay range-restricted. Representation lemmas tie the program's local
  copies (voted, acks, votes, owned, proposed, owns) to the network.
- FEATURES says "With equation (15) omitted, the Fig. 6 counterexample to induction is reproduced." In the paper Fig. 6
  belongs to the first rewrite attempt (before the propose max is rewritten to vote_msg); omitting (15) from the final
  invariant gives §6.2's "similar" CTI (an acknowledgement for r2 without joined_round(n, r2), letting n vote below r2,
  breaking eq. (8)). BENCH-150c pins "a counterexample to induction" and describes the CTI; this holds as long as the

  LANGUAGE §17.5 defines no options for `smt` (bounds belong to `bmc`, `sim` and `asp`), so there is nothing to put

### Event classification of handlers (review fix)
LANGUAGE §8.5 classifies a relation as an event relation by the **greatest** fixpoint: a `scratch` or `output` is an
event relation if every statement that writes it is event-driven. An output persisted by its own `next` loop
(`collect: on addr(a) … { emit garbage(a); }` plus `keep: … garbage(a) { next garbage(a); }`) is therefore an event
relation, like a loopback that re-sends itself, even though it holds in every tick after the first event. A handler
whose header reads it must be `on`: with `while` it draws BLS0505 ("write `on`"), and both keywords lower
identically. The first corpus version wrote `while` there (recorded then as a LANGUAGE bug). The programs now follow
LANGUAGE and write `on`, each with a comment saying why:
- `keep` in BENCH-083a, 083b, 085a, 085b, 085c, 086b, 086c, 088a, 088b, 088c, 088e, 089f, 089g, 089h, 091a, 091b;
- `carry` and `dequeue` in BENCH-084a and 084b (`b` is persisted by `carry`);
- `first` and `extend` in BENCH-087c and 087e: `keep` is a view over `new`, which reads the loopback `m`, so these
  headers are event-driven through the loopback itself, not only through a `next` loop.
If LANGUAGE is ever amended to classify `next`-self-persisted relations as standing (Bugs, item 1), exactly these
handlers must go back to `while`, or they become BLS0504 errors.

## Bugs

Problems found in documents and code this WP does not own. None blocks this WP.

1. **LANGUAGE §8.5: is a `next`-self-persisted relation an event?** (owner: LANGUAGE, M4.5 `front::classify`; a spec
   question, not a defect). Under the greatest fixpoint, an output or scratch persisted by its own `next` loop is an
   event relation: `garbage` in BENCH-083a is written by `collect: on addr(a), …` and by
   `keep: on garbage(a) { next garbage(a); }`, both event-driven. So `keep` must be `on` (with `while` it draws
   BLS0505), although `garbage` holds in every tick after the first event, which is what `while` ("fires at every
   tick in which the header holds") describes. This is consistent with loopbacks, which are events even when they
   re-send themselves, and the corpus follows it (see "Event classification of handlers"). An amendment would have to
   treat `next` self-loops as standing (as LANG-065 treats explicit persistence) without switching to a least
   fixpoint: a least fixpoint would wrongly make a same-tick recursive scratch fed by a channel standing. If one is
   made, the handlers listed there go back to `while`.

  backend's key, because schema v1 has no place for "expectations about the rewritten program". The cases use them

  are and has the analysis backend run the rewrite through the oracle harness when these keys are present. Another
  adds a `[[expect_rewritten]]` table (the `[[expect]]` shapes plus `rewrite = "edelweiss"`) to schema v2 and moves
  them there. The owner is M5.2 (schema and lint), with M7.5 as the consumer.
- **PLAN §5 decision needed: diagnostic matching for the `analysis` backend** (M5.2). The cases assume the convention

  diagnostic instead, each analysis case must first be audited for the P1 lints of M6.6 (BLS0802 sender binding,
  BLS1003's receive-side channel extension, BLS0601-0605), and BENCH-093g's "no BLS1002" becomes "no analysis
  diagnostic at all".
- **M7.2 / M8.2: run BENCH-090x with equal delays** (TEST-003). The CALM-pruning regression tells sound pruning from
