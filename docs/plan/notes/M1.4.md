## Expectation vocabularies used and introduced

PLAN §5.1 names the `[expect_analysis]` keys but not their contents. The corpus uses these shapes; M5.2 (lint), M6.6,
M7.3 (P1 analysis backend) and M7.5 should read them as the contract, or change them together with the cases.

- `points_of_order = { complete, edges = [{from, to, kind[, reason]}], clusters = [[...]], crossing = [{from, to}],
  free = [...] }`; `calm_labels = { outputs = {rel = label}, paths = [{from, to, label}], races = [{channels, meet,
  guarded}] }`; `certificates = { rel = [kinds] }`; `confluent` and `fair_consistency = { rel = verdict }`;
  `finality = { rel = [classes] }` (ANA-120 classes; a list when a relation is final early one way and at a seal the
  other, e.g. `["THRESH", "SEALED"]`); `strata = { count, of = {rel = n} }`.
- `blazes` (BENCH-094), a table with: `paths` (array of `{component, from, to, annotation, gate?}`: components are
  module instances, ARCHITECTURE §7.2; `from`/`to` are the instance's input and output interfaces; annotation CR/CW/OR/OW
  with the gate as sorted column names); `streams` (channel name → label); `sinks` (program output → label);
  `coordination` (array of `{at, mechanism = "ordering" | "sealing", key?}`); `cycles` (the collapsed components);
  `collapsed` (`{members, annotation, gate}`). Labels are NDRead, Taint, `Seal(k1, …)`, Async, Run, Inst, Diverge.
- `reclaimable` (BENCH-095), a table with: `reclaimed` (relation → `dr_plus` | `dr_minus` | `join_seal` |
  `join_pullup` | `join_semijoin` | `join_keys`); `kept` (relation → reason code: `negated_input_deleted`,
  `negated_scratch_not_inflationary`, `negated_scratch_not_monotone`, `negated_scratch_not_grounded`,
  `negated_scratch_from_channel`, `reaches_output`, `aggregated`, `negated_by_non_candidate`,
  `negated_with_predicate_block`, `downstream_table_deleted`, `quals_not_positive_keys`, `unsealed_join`, `range`,
  `no_negation`, `not_reclaimable`, `dominance_by_transitive_closure`); `channels` (channel → `arm`); `storage` (array of
  `{node, rel, tick | final, rows}`: the contents of the relation **in the Edelweiss-rewritten program** in the case's
  run); `ranges` (array of `{node, channel | rel, tick | final, buckets}`: the buckets of the ARM approximation of a
  channel, or of a `range(col)` table, as `[other columns…, lo, hi]`). The `storage` and `ranges` entries are run-time
  facts of the rewritten program; they are checked where M7.5 runs original and rewritten programs side by side.
  `[[expect]]` rows are always about the program as written, and for outputs they must also hold after the rewrite
  (ANA-066), which is why output assertions appear in both places.
- `[expect_verify] result = "fails"` in BENCH-150 (b) means "not proved because the VC is outside EPR" and in (c) "a
  counterexample to induction"; schema v1 has no key to tell the two apart (see Follow-ups). Both manifests say which.
- Sim cases whose scenario is written as spec facts say so in `notes` (BENCH-090x, 094k, 098, 099b); their `[[input]]`
  list is empty. `[[expect]]` rows may name views (for example `live`, `view`, `read_view`): the harness observes every
  relation of a node, not only outputs.

## Judgement calls and deviations

- BENCH-082e: a static `party` domain relation makes MAR Example 4's first rule range-restricted.
- BENCH-083c: the program is MAR Appendix C's published output of the coordination rewrite; that ANA-047 synthesizes
  an equivalent one is M7.5's to check.
- BENCH-084a/b/d: each element is sent once from a host input instead of from an EDB relation re-sent every tick; as

- BENCH-090: the programs are written from the papers' descriptions (Keeping CALM gives no code; JACM Example 10 is

### BENCH-094 (Blazes)
- Components are module instances (ARCHITECTURE §7.2). PLAN M6.6's `#[component]` groups are not in LANGUAGE's
  attribute list (BLS0210), so they are not used.
- The Bloom ad-reporting source (~125 LOC) is unpublished; it is re-derived from the paper's description and Fig. 5
  queries (`derived = true`). The cache forwards every request, answered or not, so its request → request path is the
  confluent read the paper annotates CR (the paper's "otherwise forwards" would be an antijoin). Answers from other
  caches are stored, not passed on again, so the self-edge does not loop.
- Report's click path is CW, as in the paper's white-box extraction: a click only writes the log that the query path
  reads; order-sensitivity is on the request path (OR_gate), and R05 §4.4.1 resolution 1's `protected()` looks at the
  streams feeding write paths.
- `#[replicated]` (LANGUAGE §14.1: "its producers are replicas that emit the same stream") is put on the output streams
  of Report and of Cache: both are replicated components, and the paper's POOR derivation reconciles Cache with Rep.
- WINDOW uses Fig. 5's threshold (< 100); the text of §4.1.1 says 1000.
- BENCH-094i pins the antijoin gate {x} and the seal on x. Blazes footnote 5's other case (a seal on the selected
  partition y = 'Yahoo!') is outside the formal compatible() predicate (y determines no gate column) and is not pinned.
- BENCH-094k (not in FEATURES' list, from R05 T14 "the runtime shows replicas disagreeing without coordination") checks
  POOR's disagreement in simulation; the ordered variant belongs to M7.5's rewrite checks.

### BENCH-095 (Edelweiss)
- Reclamation verdicts come from the artifact's published rewrites (`*_rewrite_src.rb`, deletion rules `X < -…`) and
  from R05 §5; bud-gc unit-test expectations are bud-gc's assertions.
- Timeline mapping for the unit tests: Bud's n-th `tick` is our tick n; rows the test inserts with `<+` before it are
  host inputs at tick n copied into the table in that tick; an assertion after it is an expectation at tick n. Tables the
  tests write directly get an `input X_in` and a copy rule; scratches the tests write are `input` relations; Bud's
  `seal_<rel>_<col>` tables are the local seals of a table declared `sealed by (col)`, driven by an `input X_seal`; Bud's
  unread scratches are `output`s (Bud regards them as potential outputs); read scratches are views.
- Several fixtures share one program with prefixed relation names, because a case directory takes one letter and
  BENCH-095 needs 26 cases for 10 programs, 2 variants, range compression and 67 unit tests.
- **Not ported: `test_rse_self_join_diff_preds_partial_seal`.** It seals one relation on two columns (x and y), which
  LANGUAGE does not allow (one `sealed by` clause per relation). Its expected result is also unsound: for
  `(t1 * t1).pairs(:x => :y)` (left.x = right.y), bud-gc's `create_self_join_del_rules` reclaims t1(1, 2) after seals on
  x = 1 and y = 2, matching each seal against the tuple's own column. The partners of t1(1, 2) are tuples with y = 1 (it
  as the left input) and x = 2 (as the right input); a later t1(5, 1) is allowed by those seals and joins it, and its
  result would be lost. The sound rule is pinned by the whole-relation variant and by RseSelfJoin.
- Split or adapted because of the one-seal-key rule: JoinReclaimMultiplePreds becomes two fixtures (mpa seals t2.a, mpb
  seals t2.b); JoinReclaimIntersectSeal's final whole-relation seals of t2 and t4 become seals on the one remaining value
  (11), which rules out the same partners.
- Key adjustments so the unrewritten program does not hit a key violation where the rewritten one relies on duplicate
  suppression: the negative-side relations y (ReclaimOuter), t3 (ReclaimOuterIntersect) and t2, t3
  (ReclaimOuterIntersectInverse) are keyed on all columns (DR- only needs the positive input's keys); in
  ReclaimOuterPending the re-inserted row is the reclaimed tuple [6, 11] instead of Bud's [6, 12].
- Type adjustments: JoinRseTlistConst mixes "foo" and 99 in one Ruby column; the port uses a String column and "99".
  JoinRseTlistIpPort and JoinRseTlistConstQual use `self` for Bud's ip_port and constants for its ports.
  JoinReclaimMultiplePreds' one-column rows into a two-column t4 become a one-column t4.
- Node sets: rules may not build node names from strings (LANGUAGE §2.4), so Bud's `sealed :node` holding addresses is a
  `static` relation with `fact`s in the broadcast programs (closed in the same way); where node names are plain strings
  (JoinRse*), `sealed table` with bootstrap is kept.
- BENCH-095b/x: in the rewritten broadcast programs the log is reclaimed once delivered to every node (the artifact's
  BroadcastAll rewrite does this: nothing reads the log), so storage ends empty while the unrewritten logs keep every
  message. The broadcast space test's shuffled order is fixed (seed 1234).
- BENCH-095c uses synchronous rounds so the host's epoch seals come after every delivery and acknowledgement; under
  random delays a local seal could precede a delivery and turn it into an "insert after seal" violation.
- BENCH-095e: the duplicate-request hazard of R05 T22 arises from the client's own resends arriving after reclamation,
  which the rewritten program suppresses; the observable check is one answer per read.
- BENCH-095m pins contents (oracle) and buckets (`ranges`). R05 item 27's compile-time checks (a non-integer range
  column; a non-key column on a range) are not pinned: LANGUAGE §20 has no diagnostic code for them (see Bugs).
- `RseJoinRhs`: the storage row for safe_log at tick 4 is derived (dominated = {1, 3} at tick 4 needs write 1 at tick 3).
  `SimpleCausalAtNext`: the rest of the test after bud-gc's `skip` is not ported.
- The SealedCollection test's second half (inserting into a sealed collection after bootstrap raises CompileError) is
  LANGUAGE's BLS0401 and is not a separate case here.

### BENCH-098 (finality soundness)
- Each BENCH-097 query runs at two replicas fed by one source (three nodes; seven for the tally), so "replicas never
  finalize different values" is observable; the spec's facts are BENCH-097's inputs moved to the source. Queries whose
  class allows it are declared `final output` so TEST-088 checks their own marks; MIXED queries (q, q_c, 2P-set
  membership) stay plain outputs (LANGUAGE §7.6 accepts `final output` only for POS/NEG/TOP/THRESH/FINITE/SEALED).
- Besides the TEST-088 oracle, each spec pins instance facts from the literature (which tuples may and may not become
  final, both ways) and monotonicity of finality at the reporting replica.

### BENCH-099 (batch completion)
- Counts use LANGUAGE E6's LSet of occurrence ids, not R13 T16's bag: ARCHITECTURE §7.1 makes weighted relations OPEN
  for ANA-120 unless sealed, so a bag-based `hot` would not be classified POS-final there (see Bugs).
- The host's end-of-split is an `input split_end` (a manifest cannot seal a host input); the mapper seals the channel
  then. Mapper and reducer both keep only splits of the static `split_of` plan, so the four seals close the reducer's
  state (without that guard a tuple of an unplanned split could change a "final" count).
- HOT stays 1000 (inputs are ten 50-word lines per split for 1000 occurrences of "the").
- The retracting variant's corrections travel on an unsealed channel: with sealed corrections `hot` would be SEALED and
  a `final` annotation accepted, contradicting R13 T16's compile error.

### BENCH-150 (Paxos Made EPR)
- The program transliterates EPR Fig. 3: one role, every message broadcast to every replica, rounds u64 with 0 as ⊥,
  a static `owns` for "each round has a unique owner", a static `value` domain for proposable values, and the owner's
  proposal chosen as the max over all acknowledgements received (a superset of a quorum), else the host's value.
- Tick batching: a replica may join several rounds and vote in one tick; a vote waits for no round above it joined in
  or before the tick (`joining`), so a tick equals an EPR interleaving (joins in increasing round order, then votes).
  A throwaway randomized model of this tick semantics (20,000 runs, 3 nodes, 4 rounds, 2 values; not our
  implementation) found no violation of (4)–(11), (13)–(15) or the representation lemmas, and it did find violations of
  (8)/(10) without the `joining` guard and of (13) when the proposer ignores reports.
- The spec states EPR's vocabulary as views over the network (message relations without the fields EPR does not have)
  and the derived relations over the program's own `joined` table, so program guards and invariants use the same
  derived relation, then states eqs. (4)–(15) verbatim; ∀ over rounds and values is written with range generators
  (`r1 in 0..r2`) and the static `value` domain to stay range-restricted. Representation lemmas tie the program's local
  copies (voted, acks, votes, owned, proposed, owns) to the network.
- FEATURES says "With equation (15) omitted, the Fig. 6 counterexample to induction is reproduced." In the paper Fig. 6
  belongs to the first rewrite attempt (before the propose max is rewritten to vote_msg); omitting (15) from the final
  invariant gives §6.2's "similar" CTI (an acknowledgement for r2 without joined_round(n, r2), letting n vote below r2,
  breaking eq. (8)). BENCH-150c pins "a counterexample to induction" and describes the CTI; this holds as long as the
  verifier does not add (15)-shaped lemmas on its own (R10's VER-011 send invariants use the rule body, not co-heads).

## Bugs

Problems found in documents and code this WP does not own. None blocks this WP.

1. **LANGUAGE §8.5, event classification by greatest fixpoint** (owner: M4.5 `front::classify`, LANGUAGE). An output or
   scratch persisted by its own `next` loop is an event relation under the greatest fixpoint, so a correct `while` over
   it draws BLS0505 ("write `on`"), although the relation holds in every tick after the first event. Reproducer:
   `tests/corpus/async/BENCH-083a-gc-uncoordinated/program.bls`, handler `keep: while garbage(a) { next garbage(a); }`
   with `garbage` also written by `collect: on addr(a), …`. A least fixpoint (or treating `next r` self-loops as
   standing, as LANG-065 treats explicit persistence) would classify it standing.
2. **One `sealed by` clause per relation** (owner: LANGUAGE §3.2 `RelClause`, M6.4). Edelweiss and bud-gc seal one
   relation on several columns and as a whole (tc_gc: seal_t1_x and seal_t1_y; seal_t2_a and seal_t2_b; seal_t2 with
   seal_t2_val2). Blossom cannot express that; three fixtures were adapted (above).
3. **Reclamation from sealed tables** (owner: M7.5; LANGUAGE §7.10's sealed tables have no `$del`). Edelweiss reclaims
   from sealed collections (JoinRseNotinPullup's ref; BroadcastAll's node once log is sealed). The rewrite needs a
   reclamation path for sealed relations that is not a user `delete` (which LANGUAGE §12 forbids there).
4. **`#[ordered]`** (owner: ARCHITECTURE §9.4 vs LANGUAGE Appendix C; M10.4). ARCHITECTURE makes `#[ordered]` types EPR
   sorts with order axioms, but LANGUAGE does not list the attribute (BLS0210). BENCH-150 relies on R10's alternative,
   "types that only use comparisons become ordered sorts".
5. **`#[component]`** (owner: PLAN M6.6 / ARCHITECTURE §7.2 vs LANGUAGE Appendix C). Not a LANGUAGE attribute.
6. **Range-table diagnostics** (owner: LANGUAGE §20, M6.4). No code for `range(col)` on a non-integer column or for a
   `key(…)` clause on a range table (Bud rejects both).
7. **E6 finality** (owner: `examples/e06_wordcount.bls`, M6.6 ANA-120). `word_count` is `final output`, but the reducer
   keeps occurrences of any split, sealed or not; unless ANA-120 bounds the split column by `split_of`, a tuple of an
   unplanned split could change a count reported final. BENCH-099 guards both sides with `split_of`.
8. **R13 T16 vs ARCHITECTURE §7.1** (owner: M6.6). R13 T16 makes counts a bag and `hot` POS-final; ARCHITECTURE makes
   weighted relations OPEN for ANA-120 unless sealed. One of the two needs amending (an insert-only bag proved by ANA-030
   could count as INFL).
9. **FEATURES BENCH-150 wording** (owner: FEATURES; M10.4). "Fig. 6" is the paper's first-attempt CTI, not the result of
   omitting eq. (15) (above).
10. **LANGUAGE §7.6 / §14.5 on MIXED** (owner: LANGUAGE, M6.4/M6.6). §7.6 accepts `final output` only for POS, NEG, TOP,
    THRESH, FINITE and SEALED; §14.5 says "MIXED needs the runtime gate", which reads as either accepted or rejected.
    BENCH-097 and 098 never declare MIXED outputs `final`.

## Follow-ups

- Schema v1 `[expect_verify]` cannot say why a check fails. BENCH-150b (outside EPR) and 150c (counterexample to
  induction) both say `fails`; a `reason` key (`outside_fragment` | `counterexample`) would let the runner check it
  (M5.2; a PLAN §5 change).
- M10.4 constraints from BENCH-150 (VER-006–010): compute the quantifier-alternation graph after miniscoping (EPR's own
  footnote 4 needs it); treat projections of the network and "exists-greater" views over program state as derived
  relations (VER-009); establish the propose action's max over reported votes as EPR §6.2 does (a rewrite checked under
  eqs. (5), (6), (8)–(11)); translate range generators and static domains to order guards and relation guards; do not
  generate co-head lemmas such as (15) automatically, or BENCH-150c stops producing its CTI.
- M7.5: the `reclaimable.storage` and `ranges` expectations need the Edelweiss rewrites to run on the corpus programs in
  the case's own run (sync rounds or seeded simulation), next to the unrewritten program.
- Port `test_rse_self_join_diff_preds_partial_seal` with the sound expectation once a relation can carry several seal
  keys (Bug 2); the sound result with Bud's seals is "nothing reclaimed".
- BENCH-099: add the bag-typed variant of R13 T16 once Bug 8 is decided (ANA-120, M6.6).
- Blazes footnote 5 case (a), a seal on an antijoin's selected partition, if ANA-043 grows a selection-aware
  compatible() (ANA-043, M6.6).
- Range-table compile errors of R05 T27 once LANGUAGE assigns codes (Bug 6; LANG-050).
