# S19 — engine constant factors and incremental saving

The user (2026-10-06), after S18 brought TodoMVC to 52.8 ms (React 20.5): "Keep pushing perf". User-defined
lattices move to S20.

## What was built

- **Tick-scoped relations** (`Regime::Scoped`, `engine::tick_scoped`). A relation all of whose deductive rules on the
  node read an event (or another such relation) positively, aggregate nothing and are in no recursive stratum, with
  no facts and no lattice, holds rows only in a tick with an event. The engine empties it at the start of every tick
  (`Store::retract_all`) and evaluates its rules from scratch while one of their event atoms holds a row: the quiet
  tick after an event does no work for the event's handlers, instead of retracting their rows one by one. Readers that
  are not scoped see the emptying as a change. `engine_scoped` checks it against the oracle (an alternative of a view
  that is not scoped, a negation, a chain, a join with a table, an aggregate, a `next`) and that a scoped rule does no
  work without its event; a mutation (no emptying) fails it.
- **Hashed supports.** A store's supports are a `DetMap`: a write costs one hash, not a row comparison per tree level.
  The readers whose output shows an order sort (`Store::present_sorted`: observed rows, carried rows; the first
  violation is the least row).
- **Incremental saving in the browser.** One localStorage entry per durable row and the tables' schema hashes;
  `App::save_changes` gives the rows added and removed since the last save (all of them after a start). A restore
  assembles the old JSON from the entries; the older one-entry form is read once and rewritten (a Playwright test).
- `RuleWork` counts evaluations (`examples/todomvc_work` prints them, and with `BY_EVALS=1` the rules evaluated most);
  the term buffers are kept across evaluations.

TodoMVC in the browser: 52.8 → about 40–49 ms (the machine's load moves it; React 22–23); with saving 64 → 45 ms.
Natively 20.7 → 17–18 ms.

## Decisions made on the way

- Hashing the stores' per-tick change sets (`ins`, `del`) was tried and measured: no gain within the noise, so it was
  not kept.

## Known limits

- The engine now does about the work its design needs per event (two rounds, ~40 rule evaluations of ~1 µs); what is
  left is spread over store writes, expression evaluation and per-evaluation overhead. Under React would take compiled
  rule plans (`blossom-codegen`) or another value representation (interned strings, columnar rows).
