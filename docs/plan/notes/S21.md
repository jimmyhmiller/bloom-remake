# S21 — the browser as a node of the program

The user (2026-10-06): "Yes, I want to do it. Let's do this. This sounds amazing." Choices (AskUserQuestion): a new
`client` role kind holding rules; a resumed identity (a token the page keeps across reconnects and restarts, the server
replaying what was missed); both demos, a shared TodoMVC first and then a chat room; `blossom run --web` serves the
page and its WebSocket. Design: docs/design/CLIENTS.md.

## What was built

- **Language (sub-slice 1).** `role R: client;` holds rules and no static members; `p in R`, `R.size()` and
  `majority` over a client role are BLS0404, as is a channel between two client roles. Link events
  `Q.connected(n, resumed)` / `Q.disconnected(n)` are readable only across a client link (BLS0404) and never
  writable (BLS0400). Client node ids are minted by the server they connect to (`NodeId::client`), printed
  `Role#serial@server`, and encoded by the server's name on disk (`#serial@name`). The simulator models links as up
  from the first round, down on a crash, up again on a restart.
- **The link (sub-slice 2).** `blossom_wire::link` holds the handshake both ends share. A member's `HELLO` names its
  role, its token (none the first time), the last server batch it took and the last of its own the server acked; the
  server answers `HELLO`, `HELLO_OK` and `WELCOME{member, token, resumed, floor, seed}`. Each direction numbers its
  `MSG` batches; a batch is acknowledged (`ACK`) once taken — by the server only once the tick that took it is durable
  (`ReleasedTick.taken`). The server keeps a bounded replay buffer per member (8192 frames / 32 MiB); a link resumes
  iff the identity survived, the server still holds everything after what the page took, and the page did not claim
  more than was sent. Identities live in `blossom_store::ClientRegistry` (the CLIENTS file: serial and the BLAKE3 hash
  of a 16-byte secret; the token is serial ++ secret). Each member gets a seed derived from the root seed and its
  name; the root seed is never sent to a page.
- **Serving (sub-slice 2).** `blossom run --web ADDR [--web-root DIR]`: a small hand-written HTTP/1.1 server (static
  files from the root, `/blossom/app.json`, the WebSocket at `/blossom/link`, RFC 6455).
- **The page as a member (sub-slice 3, native half).** `blossom_web::link::Link` is the page's side of the protocol
  with its offline queue; `LinkState` is what the page stores to survive a reload. `compile_client` compiles the
  program for the deployment app.json names; `App::member` runs the page as a member (rounds as its own node id, the
  link events raised on `WELCOME` and on loss of the connection, sends collected into frames).

## Decisions made on the way

- **No seed in app.json.** The first version put the deployment's root seed in the page; every member could then
  predict every node's random draws. Each member's seed is now derived per member and sent in its `WELCOME`.
- **Acknowledgement after durability.** Acknowledging on receipt would let a crash of the server lose a line the page
  already dropped from its queue.
- **Tables a member's history needs must be `durable`.** The chat's `log` is; without it a restarted server greets a
  resumed member with nothing.

## New dependencies

- `sha1` 0.10.7 (blossom-runtime): the WebSocket accept key, which RFC 6455 defines with SHA-1. Recorded in
  docs/design/DEPENDENCIES.md.
- `serde_json` (workspace) in blossom-runtime and blossom-cli, for app.json.
