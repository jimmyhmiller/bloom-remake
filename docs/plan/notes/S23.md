# S23 — a Datalog database behind each node

The user (2026-10-07): "what would it take to get us a real proper persisted database instead of just a write-ahead
log so that we could really have a datalog database behind all of this that can do datalog queries". Chosen
(question tool): queries and on-disk storage as one slice, after S22; our own LSM over our VFS. Design:
docs/design/DATABASE.md.

## What was built

- **S23.1 The LSM tree** (`blossom-store::lsm`): versioned byte keys (`(key, version, op)`), a memtable, SSTables
  (CRC32C per block, a first/last-key index, a checksummed footer), an atomically written manifest, size-tiered
  compaction keeping every version above the history horizon and the newest at or below it (deletes dropped only
  where nothing older survives elsewhere), as-of prefix scans, a read-only open.
- **S23.2 The node's database** (`blossom-runtime::db`): each released tick's durable delta (now in `ReleasedTick`)
  is applied at its tick; rows are keys (`DurableCodec::row_key`: a relation tag, then the row); a database thread
  flushes and compacts; recovery applies the WAL records after the tables (`Opened.wal_deltas`); the committer
  truncates the WAL only behind the database's flushed tick (`TruncationGate`); a store without a database gets one
  from its recovered rows; at boot the database must equal the recovered rows or the node refuses to start.
  `storage.history_ticks` (default 65 536).
- **S23.3 Queries**: `blossom query` compiles `name(columns) = body` with the deployed program and cuts it down
  (`ValidatedProgram::query`); `blossom run --admin ADDR` answers `POST /query` from the database as of a released
  tick (newest, or `--as-of`), reading by prefix where every read binds the leading columns.
- **S23.4 Offline queries**: `blossom query --store DIR` reads a stopped node's store in place.

- **Later the same night:** `Lsm::get` and a shared block cache (groundwork for §7); order-preserving row keys
  (`blossom-node::keycode`) with range scans, the key format recorded and an older one rebuilt from the recovered
  rows; queries read ranges where one atom's rule compares the next column with constants; a query's view has a
  name of its own (`__query_<name>`) and its diagnostics name `<query>.bls`.
- **An independent review** (a subagent reading the diff) found three bugs, fixed with tests: a durable write at
  tick 0 was skipped on replay (version 0 meant both "nothing flushed" and "flushed through 0"), so the node refused
  to restart; a bootstrap a crash cut short looked complete (the manifest is now written by the first flush); a
  rebuilt database answered as-of reads before the rebuild with nothing (its floor is now the rebuild's tick). Also
  from it: queries run as the node at the as-of tick, the cut-down keeps only the node's role's rules, walks
  construct kinds and refuses `@next` rules, prefix pushdown needs a relation read by atoms alone, a blocked WAL
  truncation asks for a flush, and manifests are written outside the state's lock.

## Decisions made on the way

- **Checkpoints stay for now.** The engine holds every relation in memory and recovers from checkpoints; the
  database is a second, queryable copy, checked against the recovered rows at every boot. Moving the engine onto the
  database (DATABASE.md §7) is the next step, and retires checkpoints.
- **The node never compiles a query.** The CLI sends the small IR program; the node evaluates it with the oracle.
- **Keys carry both an order-preserving encoding and the codec row.** The ordered part sorts and prefixes; the codec
  suffix is what decodes, so no type-directed decoder of the ordered encoding is needed.
- **The admin plane is `insecure-dev` only** until it has authentication (DIST-066).

## What it costs

The Kafka benchmark (three brokers of examples/kafka on computer.jimmyhmiller.com, `kafka-producer-perf-test`,
300 000 records of 1 KiB, acks=all, unthrottled), main (S20) against S23, run twice in alternating order:

| build | records/s (run 1) | records/s (run 2) | disk after |
|---|---|---|---|
| main (no database) | 5 374 | 5 546 | 1.1 GB |
| S23 (database) | 5 432 | 5 645 | 1.9 GB |

Throughput is unchanged within noise (the database's applies run on the engine thread but cost far less than a
tick; its flushes and compactions run on their own thread). Disk is not: the database is a third copy of the durable
rows (beside the checkpoints and the engine's memory), and the WAL is kept until the database flushes. Moving the
engine onto the database (DATABASE.md §7) retires the checkpoints.

## Tests

- `blossom-store/tests/lsm.rs`: against a model at every version kept (6 seeds), reopening, and a crash at every
  operation of flushes and compactions with lost, surviving and torn writes; mutation-checked.
- `runtime_db`: as-of and prefix reads through a real node, flush, restarts (tables plus WAL replay); prefix
  pushdown on a compiled query.
- `blossom-cli/tests/it/query.rs`: end to end against e01 (as-of before a delete, prefix and computed views, the
  non-durable refusal, a tick outside the history, offline queries refused while running and answered after).
- The kill -9 suites pass with the boot consistency check.
