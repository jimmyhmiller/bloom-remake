# S5 — the fast engine

Step 3 of the flagship goal: "An incremental, indexed evaluator replaces the naive reference oracle for execution, and
must agree with it on the whole corpus. It comes before the benchmark, because running the naive oracle on the
network would make the etcd comparison meaningless."

## Why the oracle is slow

Each tick, the oracle:
1. builds a fresh database from the carried state and the statics, re-indexing everything;
2. evaluates every stratum by naive iteration;
3. re-derives every persistent table through its frame rule (`t(x̄)@next :- t(x̄), notin t$del(x̄)`);
4. returns the full instance and the full next state.

So a tick costs O(state), whatever changed. For the Raft KV the log grows without bound, and so does every tick.

## Design

The engine is a value-level evaluator (`blossom-engine`) behind the node's `Evaluator` seam. Like the oracle, it
works on `Value` rows. The architecture's word-level kernel and code generation remain later work. Its principles:

- **State lives across ticks.** Every relation is stored once, with its indexes, and updated in place from changes,
  never rebuilt.
- **Everything is a change.** Across ticks, each relation is a Z-set (a set with signed multiplicities, as in
  DBSP), and a tick's work is the change to every relation. The change of a tick-local relation (events, channel
  receives, ingress, the tick's derived scratch) is its new content minus its old one. The change of a carried
  relation is what its inductive rules derive for the next tick, minus what they derived last time.
- **Rules are maintained, not re-derived.** A deductive rule's output changes by the delta query of its body:
  `Δ(A ⋈ B) = ΔA ⋈ B_old + A_new ⋈ ΔB`, with negation as a counted antijoin, and guards and bindings as maps and
  filters. Derivation counts keep set semantics exact under deletions (DBSP's distinct). Each regime is chosen per
  rule and per stratum:
  - **Counted** (delta queries): a non-recursive stratum with plain insert heads.
  - **Aggregates**: per-group state (value counts); a change touches only its groups. Covers count, sum, min, max,
    `argmin!`/`argmax!`, and choice (min over the seeded priority).
  - **Lattice cells**: per-cell contribution counts, with the cell's value recomputed as the join of its live
    contributions when they change.
  - **Recompute**: a recursive stratum, or a rule that reads a time-varying scalar (`$now`, `$tick`, `rand`,
    `choose_rand!`). It is re-evaluated in full, semi-naively, when its inputs changed or a time-varying scalar is
    read, and its output is diffed to produce the change.
- **Indexes.** Hash indexes serve equality probes and ordered (BTree) indexes serve ranges. A join keyed by an
  expression, such as `log(j, …) where j + 1 == i`, probes with the key computed from bound variables.
- **Outputs.** The outbox (async heads) and egress are the full contents of their head relations for the tick, which
  are small tick-local sets. The next-state change is the change of the inductive heads.

## The seam changes

- The tick's inputs and outputs (`Row`, `Instance`, `Delivery`, `Send`, `Ingress`, `Egress`, `TickInput`,
  `TickOutput`) move from `blossom-oracle` to `blossom-ir`, so the engine can share them without depending on the
  oracle (ARCH-16: the engine and the oracle share no evaluation code).
- The `Evaluator` becomes stateful: `reset(carried)` at boot, and `tick(&mut self, input)`. `TickOutput` gains the
  next state's change (`next_changes`). The node keeps its durable image with those changes instead of diffing whole
  instances, and asks for the full instance only when capturing (simulation, LDFI, tests).
- The oracle stays stateless: its `Evaluator` implementation diffs `carried` against `next` (O(state), as it always
  was).

## The gate

- **Differential:** the engine's instance, next state, outbox, egress and program errors equal the oracle's at
  every tick. This holds on every corpus case the oracle runs (the corpus runner's `interp` backend), and on every
  example program under random inputs.
- **Execution:** the node runs on the engine in `blossom run` and in the cluster simulator. The S3 and S4 tests
  (kill -9, the Raft KV in simulation and as three processes) pass on it.
- **Speed:** a tick costs O(change × fan-out × log n), not O(state), and the Raft KV's tick time stays flat as its
  log grows.


## What was built

| Component | Where |
|---|---|
| The engine: stores with counted support (set relations) and per-cell contributions (lattices), a per-tick change with an old-version read, delta queries per driver (atom rows, negation flips, lookup cell changes), aggregates per group, recursive strata to the fixpoint and diffed, keys, invariants, `Next`/`Async` stores | `blossom-engine` |
| The join planner: per evaluation, a greedy order by estimated rows (store sizes and index fan-outs); checks hoisted as early as their inputs allow but never reordered; a hoisted `let` feeds a later probe; a guard `v > e` narrows a probe to a range of an ordered index, unless a check before it can fail; a hoisted check's error is raised once per complete valuation, as the reference does | `blossom-engine::rule` |
| Lazily built ordered indexes, existence probes that do not materialize rows, min/max from the ends of the ordered support | `blossom-engine::store`, `engine` |

## Evidence

- **Differential, corpus.** The engine agrees with the oracle at every tick (instances, deliveries, replies,
  messages, and the same error at the same node and tick) on every runnable case: core 189, async 35, lattices 47,
  lprov 26, net 3. The lprov failures are programs that do not compile (BENCH-309a/c, 311a–c), on the oracle too.
  With `--engine`, the ldfi area's Molly programs also run on the engine against the oracle, in Molly's crash view:
  failure-free, under every counterexample LDFI found, and under eight seeded schedules within the case's bounds. All
  92 cases that reach a verdict agree.
- **Differential, examples.** Every example that compiles (e01, e03, e04, e07, e09, e11, e12) agrees under random
  small-domain inputs and 10% message loss, six seeds each (`engine_examples.rs`). e05, e06 and e08 need
  unimplemented features (BLS0908).
- **Planner.** `engine_planner.rs` covers a hoisted `let` whose error needs a complete valuation, a range guard
  after a check that can fail, and range probes as rows come and go. It is mutation-checked: reporting a hoisted
  error at once, and narrowing past a fallible check, are both caught.
- **Execution.** The cluster simulator and `blossom run` run the engine. The S3/S4 suites pass on it:
  - `node_kvs`, `runtime_server`;
  - `raft_kv`: safety observers, the directed stale-leader scenario, five nodes, power loss;
  - the kill -9 demo;
  - raft3 (three processes under kill -9 and partitions).

  `raft_kv` takes 3 s on the engine against 21 s on the oracle.
- **Speed.** The Raft KV's join work per tick is flat as the log grows: about 31 rows examined per tick over 2, 4
  and 8 simulated seconds. `join_work_per_tick_is_flat_as_the_log_grows` asserts it, counted in rows, not time. It
  is mutation-checked: without range probes the work grows from 600 to 2,620 rows per tick.

  Wall time per tick, three nodes, six clients, constant 1 ms latency:

  | Simulated seconds | Engine, first version | Engine, final |
  |---|---|---|
  | 2 | 771 µs | 95 µs |
  | 4 | 1,668 µs | 110 µs |
  | 8 | not measured | 146 µs |
  | 16 | not measured | 291 µs (measured before the existence-probe fix) |

  For comparison, the S4 review measured the oracle at 11 s wall for 5 simulated seconds and 665 s for 20.

  The wall time that still grows is the simulator's periodic full checkpoints (about a third of the time at 8 s),
  which encode the whole durable image. That is a storage cost, not the evaluator's.

## e11 for an indexed evaluator

These three changes keep the Raft KV's work per tick independent of the log:
- **Commit.** Raft's own rule: the majority-th follower `match_idx`, then the term check (`support`, `quorum`). This
  is O(servers²) per acknowledgement. The old rule counted acknowledgements per log index, which is O(log). The two
  are equivalent because terms never decrease along the log.
- **Predecessor terms.** Each entry stores its predecessor's term (`prev`), so replication reads it from the row
  instead of joining the log with itself. It stays true: an entry is stored only after its predecessor matched, and
  replacing the predecessor truncates it too.
- **Follower chains.** The consistency check joins on `let j = if i > 0 { i - 1 } else { 0 }`, an indexed equality.
  The `if` keeps a malformed index 0 from underflowing.

## Bugs found on the way

- The resolver rejected writes to an interposition's `inside` (BLS0406). The alias exemption meant for reads also
  applied to writes. Fixed: a write is rejected only for a module's own input.
- e09 never forwarded its host inputs into the instance, so the instance's inputs had no writers and were standing.
  The example now declares root inputs and forwards them.

## Deviations

- The engine is value-level. The architecture's word-level kernel and code generation remain later work.
- The join order's cost model is a greedy estimate from sizes and index fan-outs. A range is assumed to keep a
  sixteenth of its probe's rows. There is no statistics collection.
- Recursive strata are recomputed from their seed when they are dirty, not maintained incrementally (the oracle's
  naive fixpoint is inflationary, so its intermediate rows are part of the semantics).
