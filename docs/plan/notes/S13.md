# S13: the asynchronous fault model

**Goal (user, 2026-10-05):** LDFI and enumeration see only the synchronous world (a message sent in round `t`
arrives in round `t + 1` or is lost), so timing bugs are invisible to them: the full tier, not LDFI, found the
broker's quiescence bug (two `quiesce` messages of one sender delivered in one round). The asynchronous model adds
delays, and with them reordering.

The design docs specify only the synchronous LDFI (ARCHITECTURE §8.3, "Molly round k is tick k"); the closest
precedent is the ASP encoding's "a message arrives in (s, s+Δ] or is lost" (§9.2). This slice defines the rest.

## Decisions (user, 2026-10-05)

- **A delay delays a round batch:** `D(from, to, send, d)`: everything `from` sends `to` in round `send` arrives in
  round `send + d`, `d` in `2..=delay` (the spec's `delay: Δ`), like an omission loses one. Batches of different
  rounds arriving out of order are the reordering.
- **Refined (user, 2026-10-05, after the finding below): per channel.** `D(from, to, send, path, d)`: one channel's
  batch (or the pair's stream traffic) delayed, independently of the other channels.
- **Streams are delayed too:** a stream's flight delayed holds back what follows it on that connection (TCP keeps
  order).
- **A budget:** `delays: k` in `faults`, default 1.

## Plan

1. The round world delivers each batch at its arrival round (channels; stream flights in connection order).
2. The spec's `model: async`, `delay`, `delays`; `FailureSpec` and fault schedules with delays; `blossom sim`.
3. Enumeration over delays (the stepped certifier refuses the asynchronous model).
4. LDFI: delay atoms; lineage with arrival rounds; a delay falsifies an arrival on time, and makes a tuple appear
   later (channels and streams).
5. Validation: a fixture race found by both oracles; the broker's quiescence bug, its fix reverted, found.
6. `check sim` (TEST-001: seeded random schedules) and e10's RaftElectionSafety.

## Done

1. **The round world delivers at arrival rounds** (c882d64): channel batches queue by arrival round; a stream's
   delayed flight is held, and a later flight on its connection never overtakes it (a dial delayed opens the
   connection later; one sent by a node that went down meanwhile is lost with it).
2. **The spec language** (bde61d3): `faults { model: async, delay: Δ, delays: k }` (`delay` at least 2; `delays`
   default 1; BLS0900 for a missing or misplaced one); `FailureSpec::with_delays`, `delay_allowed`, admits and
   canonical forms with delays (a lost batch is not also delayed; a crashed sender delays nothing); labels
   `D(from,to,send,path,+d)`; `blossom sim --delay FROM:TO:TICK:CHANNEL:ROUNDS`.
3. **Enumeration over delays**: every way to delay at most `delays` of the batches, on every path (each channel of
   the program, and its streams), counted exactly before any runs. The stepped certifier refuses the model.
4. **A program error is a counterexample** (af33a1d): a run that ends in a runtime hard error (BLSRnnn) under faults
   is a verdict of its own (ARCHITECTURE §6.6), reported with the error; the failure-free run's error stays an error.
5. **LDFI under delays** (22ba3df, 2f8f0e4): a premise `Arrives { from, to, send, via, by }` ("what was sent then
   arrives by then") on every delivery and stream event (a stream event also on every earlier flight on its
   connection, which held back holds it back), falsified by delays past `by`; delay atoms (one length per batch, a
   budget); a channel tuple appears through a send `d` rounds earlier delayed by `d` (one the run delivered on time,
   or a new one), and stream events through delayed flights. Agrees with enumeration on every asynchronous fixture.

## Results

- `fixtures/ldfi/race.bls`: a server keeping the latest value it received holds in order and fails when the first
  write is delayed past the second (`D(C,S,1,put,+3)`, both oracles); a versioned server holds. With `EACH` two
  writes arriving together are a key conflict (BLSR002), a program-error counterexample (`D(C,S,1,put,+2)`).
- `fixtures/ldfi/stream_store.bls`: an eager client's write delayed past the run is lost (`D(C,S,1,streams,+6)`, both
  oracles); the acknowledging client holds (LDFI 11 runs, enumeration 31 schedules).
- **Kafka, three brokers, any one batch delayed** (no losses or crashes): holds for delays up to 2 rounds (6 613
  schedules, 44 s) and up to 12 rounds (72 733 schedules, 8 min; server, 14 workers).
- **The quiescence bug is not reproduced.** With its fix reverted, no single delay breaks the broker: the stale
  `quiesce` a delay brings together with the next one always arrives with something that marks it stale (the entries
  sent in its round, under per-batch delays; under per-channel delays, entries sent with the later `quiesce`). In
  this scenario a leader sends only two `quiesce` messages per group, the second with entries; the full tier's run
  (consumer groups, a coordinator failover) has more re-quiesce cycles.

## Known gaps

- **LDFI does not anticipate program errors.** Its hazards cover the outcome spec; a key conflict or another
  runtime error caused by a new tuple is found only when a run it makes hits one. Enumeration finds them all.
- Invariants and `check sim` (e10's RaftElectionSafety) are not built: invariants are reported as not run.
