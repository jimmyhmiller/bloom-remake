# S24 — the engine on the database

The user (2026-10-07): "Let's do it", after choosing (question tool) that the database moves into `blossom-node`'s
durability path, so the simulator covers it, before the tiered engine store and the retirement of checkpoints.
Design: docs/design/DATABASE.md §4, §7.

## Step 1: the database is the durable state (checkpoints retired)

- **The WAL truncates behind a flush.** `Flushed`'s fields are private (only `Lsm::flush` makes one).
  `FileWal::truncation(&Flushed)` gives the token for the older segments whose every record the flush covers;
  `FileWal::covered(&Flushed)` the position past the records it covers, below which logged blobs become files.
- **`blossom-node::database::Database`**: the tree, the durable codec, apply, bootstrap, flush (with compaction),
  reads (`rows`, `rows_range`, `image`), `info`, and a read-only open for tools that applies the WAL tail in memory.
  The runtime keeps only the flush thread (`blossom-runtime::db`).
- **Recovery** opens the database and starts from its tables, replaying the WAL after them into the recovered rows
  and the database. A store from before the database (no `db/`, or an older key format) recovers from its checkpoint
  chain and the WAL after it, bootstraps the database from those rows, flushes it and removes `ckpt/` and `CURRENT`.
  `StoreSpec.database` carries the tree's options; `recovery::open` takes the `ValidatedProgram`.
- **The manual driver** applies each released tick to the database before handing it on, flushes when the memtable
  is full or when asked (`flush`, which replaces `checkpoint`), syncs the logged blobs the flush covers, truncates
  the WAL and collects blobs. The simulator runs nodes with a small database (4 KiB memtable) and flushes at random,
  so its crashes land inside flushes and compactions.
- **The runtime**: no checkpoint thread. The engine applies each released tick, asks the database thread for a flush
  when the memtable is full or the WAL has grown past `storage.checkpoint_wal_bytes`, and on the flush's result hands
  it to the committer (which syncs the covered blobs and truncates) and collects blobs. The boot consistency check
  went: there is one copy now. Stat `checkpoints` became `db_flushes`; `checkpoint_nanos` went.
- **The node** lost its checkpoint-delta machinery (`since_checkpoint`, `take_checkpoint_delta`,
  `checkpoint_failed`, `Boot::at_checkpoint`); blob collection is `collection_candidates` / `blob_garbage(flushed)`.

Tests: `blossom-store/tests/truncation.rs`; `node_database` (exact recovery after flushes through restarts and
compactions; a legacy store moves onto a database, proven by a row only its checkpoint held); `runtime_db`
rewritten against the node's database; the node, runtime, simulator (`sim_streams`, `sim_livelock`, `kafka_sim`,
`kafka_cluster`, `raft_kv`, `raft_groups`, `kafka_retention`) and kill -9 suites pass.

`blossom-store::ckpt` stays: recovery reads legacy chains with it.

## Step 2: one copy of each durable row in memory

Before this step a durable row was held three times: the engine's `Main` store (the rows now), its `Next` store (the
rows the next tick starts from) and the node's released image (for admission). Step 2 removes the extra copies; the
tiered `Main` (cold rows read from the database) comes after.

- **2a: the node keeps no copy of the released rows.** `Node::released_image` went. An ACL's `principal in REL` over
  a durable table reads the database as of the newest released tick (`Database::committed`, a prefix scan on the
  principal); `admits` is fallible, and its callers (the runtime's engine and member links, the simulator) pass the
  lookup. The manual driver gives the released image from the database (`released_image`). Test:
  `node_database::an_acl_over_a_durable_table_reads_the_database` (fixture `db/gate.bls`), before and after the
  boot tick fills the table and after a restart.
- **2b: a table's next state is a delta over its rows.** A set table carried by its frame (`FramePlan`: the rows
  not deleted, and kept) is in `Engine::framed`. Its frame rule writes nothing; its `Next` store holds only the
  other next-state rules' support (the rows inserted this tick: `r(x)@next :- add(x)`). The tick's change to its
  next state is computed where the outputs are built (`framed_change`): a row can change only where it changed in a
  store the frame reads or in `Next`, and its membership before reads each store as it was at the start of the tick
  (`contained`), which is the frame's own incremental rule. The whole next state (`carried_rows`,
  `carried_instance`, after a reset) reads the frame's part from `Main`. A lattice table keeps its full `Next`
  store: its next state joins the frame's rows with the other contributions, which a membership test cannot.
  `Engine::carried_rows` / `carried_instance`, `Executor::carried_rows` / `carried`, `Node::carried_rows` /
  `carried` and `Cluster::state` are fallible now (they read stores, and a missing one is an internal error, not
  an empty state). `Engine::held_rows` counts the rows the stores hold. Test:
  `engine_deletes::a_table_carried_by_its_frame_is_held_once` (20000 rows held as 20000; 40000 before).
