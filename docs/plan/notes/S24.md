# S24 — the engine on the database

The user (2026-10-07): "Let's do it", after choosing (question tool) that the database moves into `blossom-node`'s
durability path, so the simulator covers it, before the tiered engine store and the retirement of checkpoints.
Design: docs/design/DATABASE.md §4, §7.

## Step 1: the database is the durable state (checkpoints retired)

- **The WAL truncates behind a flush.** `Flushed`'s fields are private (only `Lsm::flush` makes one).
  `FileWal::truncation(&Flushed)` gives the token for the older segments whose every record the flush covers;
  `FileWal::covered(&Flushed)` the position past the records it covers, below which logged blobs become files.
- **`blossom-node::database::Database`**: the tree, the durable codec, apply, bootstrap, flush (with compaction),
  reads (`rows`, `rows_range`, `image`), `info`, and a read-only open for tools that applies the WAL tail in memory.
  The runtime keeps only the flush thread (`blossom-runtime::db`).
- **Recovery** opens the database and starts from its tables, replaying the WAL after them into the recovered rows
  and the database. A store from before the database (no `db/`, or an older key format) recovers from its checkpoint
  chain and the WAL after it, bootstraps the database from those rows, flushes it and removes `ckpt/` and `CURRENT`.
  `StoreSpec.database` carries the tree's options; `recovery::open` takes the `ValidatedProgram`.
- **The manual driver** applies each released tick to the database before handing it on, flushes when the memtable
  is full or when asked (`flush`, which replaces `checkpoint`), syncs the logged blobs the flush covers, truncates
  the WAL and collects blobs. The simulator runs nodes with a small database (4 KiB memtable) and flushes at random,
  so its crashes land inside flushes and compactions.
- **The runtime**: no checkpoint thread. The engine applies each released tick, asks the database thread for a flush
  when the memtable is full or the WAL has grown past `storage.checkpoint_wal_bytes`, and on the flush's result hands
  it to the committer (which syncs the covered blobs and truncates) and collects blobs. The boot consistency check
  went: there is one copy now. Stat `checkpoints` became `db_flushes`; `checkpoint_nanos` went.
- **The node** lost its checkpoint-delta machinery (`since_checkpoint`, `take_checkpoint_delta`,
  `checkpoint_failed`, `Boot::at_checkpoint`); blob collection is `collection_candidates` / `blob_garbage(flushed)`.

Tests: `blossom-store/tests/truncation.rs`; `node_database` (exact recovery after flushes through restarts and
compactions; a legacy store moves onto a database, proven by a row only its checkpoint held); `runtime_db`
rewritten against the node's database; the node, runtime, simulator (`sim_streams`, `sim_livelock`, `kafka_sim`,
`kafka_cluster`, `raft_kv`, `raft_groups`, `kafka_retention`) and kill -9 suites pass.

`blossom-store::ckpt` stays: recovery reads legacy chains with it.

## Step 2: one copy of each durable row in memory

Before this step a durable row was held three times: the engine's `Main` store (the rows now), its `Next` store (the
rows the next tick starts from) and the node's released image (for admission). Step 2 removes the extra copies; the
tiered `Main` (cold rows read from the database) comes after.

- **2a: the node keeps no copy of the released rows.** `Node::released_image` went. An ACL's `principal in REL` over
  a durable table reads the database as of the newest released tick (`Database::committed`, a prefix scan on the
  principal); `admits` is fallible, and its callers (the runtime's engine and member links, the simulator) pass the
  lookup. The manual driver gives the released image from the database (`released_image`). Test:
  `node_database::an_acl_over_a_durable_table_reads_the_database` (fixture `db/gate.bls`), before and after the
  boot tick fills the table and after a restart.
- **2b: a table's next state is a delta over its rows.** A set table carried by its frame (`FramePlan`: the rows
  not deleted, and kept) is in `Engine::framed`. Its frame rule writes nothing; its `Next` store holds only the
  other next-state rules' support (the rows inserted this tick: `r(x)@next :- add(x)`). The tick's change to its
  next state is computed where the outputs are built (`framed_change`): a row can change only where it changed in a
  store the frame reads or in `Next`, and its membership before reads each store as it was at the start of the tick
  (`contained`), which is the frame's own incremental rule. The whole next state (`carried_rows`,
  `carried_instance`, after a reset) reads the frame's part from `Main`. A lattice table keeps its full `Next`
  store: its next state joins the frame's rows with the other contributions, which a membership test cannot.
  `Engine::carried_rows` / `carried_instance`, `Executor::carried_rows` / `carried`, `Node::carried_rows` /
  `carried` and `Cluster::state` are fallible now (they read stores, and a missing one is an internal error, not
  an empty state). `Engine::held_rows` counts the rows the stores hold. Test:
  `engine_deletes::a_table_carried_by_its_frame_is_held_once` (20000 rows held as 20000; 40000 before).
- **The node's computed image went.** `Node.image` (the durable rows after the last computed tick, applied every
  tick) was written and never read: a fourth copy.

## Step 2c: tiered tables (the engine on the database)

Design: DATABASE.md §7, "How S24 builds items 1–7".

- **Store**: `Lsm::amend` (keys at the newest applied version, no version applied) and `Lsm::scan_page` (a range a
  bounded page at a time; `Page`). Tested against the model with pages of every size from one key.
- **Codec**: `DurableCodec::tagged_key` / `tagged_prefix` / `tagged_range` / `tagged_row` generalize the row keys
  to any tag and column list (indexes, blob keyspaces); `row_key` and the rest are those over the relation's tag.
- **Database**: derived keyspaces (`Derived`: indexes per relation, the blob keyspaces), definition keys loaded at
  open, `keep_index` (built at the applied version by `amend`), `keep_blobs` (at open), `expand` on every apply and
  bootstrap, `blob_counts`, and `impl blossom_engine::ColdTables`.
- **Engine**: `ColdTables` (crate `cold`), `EvalError::Storage`, `Store::tiered` (`Tiered`: overlay, staged change,
  first tick), `Engine::reset_on`, `tierable` / `tiered`, the end-of-tick carry, the baseline restricted to the other
  relations, fallible `contains` / `contained` / `present`.
- **Node**: `Boot::database`, `Executor::reset_on` (default: the whole instance, `whole_instance`), recovery without
  an image unless it starts a database, carried blob counts from the database, `Executor::resident_rows`,
  `Backend::Checked` (`CheckedExecutor`) and `BLOSSOM_EVALUATOR`.
- **A bug the checked backend found**: a tiered table began with no change after a reset, so the views over it
  stayed empty after a restart (kafka_sim's client saw no Metadata). Its first tick now shows every row as new and
  compares its next state with the database, as the in-memory baseline does; a mutation of that fix, and one that
  stops index maintenance, both fail the checked tests.

Tests: `node_tiered` (the checked executor through restarts, flushes and compactions with index and range probes,
a view, a guarded table and blobs; a 5000-row table of which the engine holds under 500 rows, before and after a
restart); the simulator suites under `BLOSSOM_EVALUATOR=checked`; `blossom-store` lsm (paging, amend).

Known limits: the first tick after a boot reads each tiered table whole (its rows are that tick's change); an index
build holds its keys in memory once; lattice and sealed durable tables, the views over durable tables and the
node's per-blob counts stay in memory.

### 2c performance: the hot tier

The Kafka produce benchmark (scripts/bench-kafka.sh, three brokers on computer.jimmyhmiller.com, 200000 records of
1 KiB, acks=all) against the build before tiering (e295abb): 6846 and 6964 records/s, end-to-end p50 4 ms. Tiered,
first cut: 724 and 811 records/s, p50 50 ms, falling over the run. `perf` showed `Lsm::scan_page`: a row's key is
the whole row, so an update leaves a delete and a new key under the same prefix, kept for `history_ticks` (65536);
every probe of a hot prefix walked them.

- The overlay is indexed by the columns probes ask for (a probe's correction costs its prefix's overlay rows), and
  hashed; corrections find the cold rows by binary search instead of hashing every row: 3522 records/s.
- **The hot tier** (`Hot` in `store.rs`): recent probes' answers and memberships, bounded (`EngineConfig::hot_rows`,
  `Executors::with_hot_rows`), kept equal to the database's newest version by applying each overlay entry the
  database catches up with: 4420, then 4687 with two-level keys and no per-row hashing.
- A range probe on the column after a leading run is cut from its prefix's kept rows by binary search; prefixes too
  large to keep are known (`ColdTables::probe_at_most` stops reading past the limit) and read ranges from the tree;
  `any` on a tiered table stops at the first live row: 6228 records/s, p50 5 ms.

Over 300000 records the rate still fell off a cliff past ~200000 (to ~1500 records/s): `any` (negation) read whole
large prefixes twice, and range probes re-read partition-sized prefixes the hot tier kept and then evicted (a probe
could keep a quarter of the budget). Now `any` on a large prefix reads only its first rows
(`ColdTables::probe_some`: one more than the overlay's absences and the tick's inserts), "large" markers are kept
apart from the row budget, and a probe keeps at most 1/64 of the budget (256 rows): a larger prefix's ranges read
the tree's range, which costs the range.

Final, 300000 records of 1 KiB (two rounds each, same machine): in-memory 6678 and 5789 records/s, end-to-end p50
4 ms, RSS ~500 MB per broker; tiered 5571 and 5546 records/s, p50 9 ms, RSS ~455 MB, ~330000 resident rows per
broker (the hot tier: 16384 rows for each of ~20 tiered tables). At this size the state fits in memory either way;
tiering costs ~10% throughput and ~5 ms of single-record latency, and pays off when the state outgrows memory. Tests: `node_tiered`
runs the checked backend with the default hot tier and with one of 8 rows (trimmed all the time); a mutation that
skips applying caught-up entries to the hot tier fails it.
