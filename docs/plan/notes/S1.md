# S1 — Molly parity (LDFI end to end on `.ded` programs)

Slice 1 of docs/design/SLICES.md: Molly's programs, run unchanged, from source text through the `.ded` frontend,
the oracle, the synchronous-round simulator, provenance and SAT-based LDFI.

## What was built

| Component | Where |
|---|---|
| Molly-dialect lexer and parser, with recovery at `;` | `blossom-syntax::ded` |
| The compiled form of a `.ded` program for one deployment | `blossom-artifact::ded` (`DedArtifact`) |
| The `.ded` frontend: `include` loading behind a `DedLoader` trait, the dialect's static rules, the protocol/spec split, type inference, lowering to validated IR | `blossom-front::ded` |
| Loading `.ded` files from disk; rendering diagnostics with source snippets | `blossom-driver::{ded, render}` |
| The oracle: its own stratifier, per-rule join plans, naive fixpoints, checked arithmetic, `count`/`sum`/`min`/`max`, Tier C firing capture | `blossom-oracle` |
| The synchronous-round world over an `Evaluator` (TEST-006), Molly's and the frozen crash views, message fates | `blossom-sim::sync` |
| The `.ded` profile: running a compiled program under a fault schedule; the spec engine that judges `pre`/`post` at EOT; Molly's `isGood` | `blossom-sim::ded` |
| Provenance graphs of runs, with rendering | `blossom-prov::graph` |
| LDFI: lineage conversion, reachability for negative support, the hazard encoding, seeded minimal enumeration, the seeded and accumulating searches, falsifier enumeration, reports | `blossom-ldfi` |
| `blossom sim` and `blossom ldfi` for `.ded` programs | `blossom-cli` |
| The corpus runner with the status ratchet for the `oracle` and `ldfi` backends of `.ded` cases | `xtask corpus` |

Results: every failure-free `.ded` case (19) matches its expected rows; 72 of the 77 `[backend.ldfi]` cases give the
published verdict with the seeded search; all 13 stated falsifier sets are exact; every BENCH-136 run count is at
most the published one for nine of the twelve cases that state one (the other three, BENCH-130q, Kafka 6/4/1 and
ack-deliv 8/7/1, list the P1 search reductions they need and stay `unimplemented`; Kafka 6/4/1 went from 34 to 101
runs with the review's soundness fixes, which widen the search).

## Deviations

1. **Layer amendments** (`xtask/layers.toml`): `blossom-front` may depend on `blossom-artifact` (the frontend
   produces a `DedArtifact`), and `blossom-sim` on `blossom-oracle` (until the engine exists, slice 5, the oracle is
   the simulator's evaluator; the `Evaluator` trait in `blossom-sim::sync` is the seam the engine will be put
   behind, provisional until that second implementation exists).
2. **IR additions** (additive): `ConstructKind::DedRelation { rel }` groups the generated channel (`r$async`) or input
   (`r$in`) of a Molly relation with the rule that feeds it; `blossom-ir::obs` gains `FiringRecord`, `FiringKind`,
   `PosRead` and `NegRead`. ARCHITECTURE puts Tier C records in `blossom-kernel::prov`, which the oracle may not
   depend on (ARCH-16); the IR is the lowest crate both the oracle and the future engine share.
3. **The implicit spec is a one-tick global IR program**, not a `SpecProgram` over interval trace relations (which
   has no evaluator yet, WP M8.2). Its inputs are every node's protocol tuples at EOT (node prefixed), snapshots for
   `p(…)@k` atoms, and the crash oracle. Molly's `isGood` reads `pre` and `post` only at EOT, so this is exact.
4. **Which relations are spec relations.** A relation belongs to the spec only when it must: `pre`, `post`, a relation
   with a rule that cannot run at one node (non-local body or head, `_` location, `crash`, `p(…)@k`), or one that
   reads a spec relation. Every other relation runs at the nodes at every tick (so failure-free cases can observe
   helpers such as `turnout`, BENCH-135m). An `@next`/`@async` rule that would have to be spec is an error
   (BLS0901 or the placement diagnostic).
5. **Types.** Integers are `i64` (Molly's INT), `count<X>` included: the IR's `AggFunc::Count` may now target any
   integer column (validator amended; the oracle converts the count, BLSR004 if it does not fit). `pre` and `post`
   columns are unified, since Molly's oracle compares their tuples. A column nothing constrains (a relation that is
   read and never written) holds no values and is typed `String`. 0-ary relations are rejected (no location).
6. **A `.ded` program is compiled for a deployment**: node names are resolved to `NodeId`s at compile time, and a
   string literal in a `Node` position that names no node of the deployment is BLS0200.
7. **`blossom sim`, not `blossom run`,** simulates `.ded` programs: `run` is the production runtime (WP M7.4).
8. **Crash reads are exact premises, relative to the run's own crashes.** `notin crash(_, n, t)` is falsified by a crash
   of `n` at `t` (at any time when `t` is open); a positive read of `crash(_, n, c)` is falsified by crashing `n`
   earlier; appearance and removal of crash tuples in tuple-level support follow the same rules; since hypotheses
   extend the run's faults, a run's own crash can only move earlier. Relations the crash oracle reaches get the
   crash-appearance hazard in relation-level support. (M1.5's Bugs 1 proposed `K(n, EOT−1)` for every crash read,
   which ignores times and the run's own crashes; the slice review found counterexamples it missed.)
9. **No merged-lineage accelerator.** R06 §10 (9) suggests merging lineage across runs. A fault set that lacks one of
   a run's faults may deliver a message the run lost, and the facts that brings are no removal a hazard can express,
   so a run's hazard constrains only supersets of its own faults: exactly the seeded search's argument. An
   accumulating search with that (sound) restriction was built and measured: it needed more runs than the seeded
   search on every case tried (Kafka 7/4/1: no counterexample within 100,000 runs, seeded: 101), and was removed.
10. **Tuple-level negative support is the default** (`NegSupport::Precise`; `--negative-support conservative|off`
    keep CR-31's relation-level rule and a Molly-like mode). A negated read is falsified only if a tuple matching its
    pattern can appear: a rule deriving such a tuple must gain a valuation, so a positive body atom gains a matching
    tuple (one with no matching tuple in the run must), or a tuple blocking a negated body atom is lost; channel
    tuples appear only through new sends; inputs never appear. It is sound for supersets of the run's faults, which
    is what the seeded search explores. Every counterexample that needs negative support is still found (3PC, Kafka,
    Figure 3, BENCH-137i), and Paxos 7/6/1 certifies in 260 runs (published 173; CR-31: 33,776). This is TEST-051's
    why-not provenance in the form LDFI needs; the user-facing `whynot` command is still WP M5.7's.
11. **Exhaustive certification** (`blossom-ldfi::certify`). When the lineage-driven search spends its run budget
    without a verdict, every admissible fault schedule is explored tick by tick with equal states merged (the
    reference checker's exhaustive mode, which the corpus used to validate these verdicts). It is sound and complete
    for the failure spec, and the report says which search decided. Bully 10/9/1 and Raft 12/6/1 and 10/7/1, whose
    lineage-driven searches exceed 100,000 runs (the reference checker's also exceed 20,000), certify this way
    (231,568, 29,016 and 28,152 states, equal to the reference checker's counts plus one tick-0 state per crash
    schedule). `--no-exhaustive` reports the budget error instead.
12. **Aggregates: contributors that can join.** Besides Molly's conjunctive encoding (losing any contributor kills an
    aggregate firing), an aggregate firing's group is a premise: its row changes if a contributor can join, which
    tuple-level support encodes as a matching body tuple appearing or a blocking one being lost (relation-level:
    the supports of the body relations). The earlier caveat (new contributors through upstream negation) is closed.
13. **`pre` tuples that come back.** A good run that loses a failure-free `post` tuple together with its `pre` tuple
    yields hypotheses that make the `pre` tuple appear (its tuple-level appearance, or relation-level support of
    `pre`), since a larger fault set that brings it back while the `post` tuple stays lost is a counterexample.
14. **Incomplete lineage is not a certificate.** A target whose hazard already holds under the run's own faults (the
    encoding may weaken a hazard: a derivation met again on its own path counts as falsified) gives the search no
    guidance; the lineage-driven search then records that it is incomplete, and a "no counterexample" from it hands
    over to exhaustive certification (or, with `--no-exhaustive`, is reported inconclusive).
15. **The `.ded` profile starts at tick 1**: Molly has no round 0, and a rule whose body is only negations would
    otherwise fire at tick 0 with sends that no omission can touch.
16. **Published run counts are expectations.** `xtask corpus` fails a case whose lineage-driven run count exceeds its
    `runs_max` (or that needed exhaustive certification); the ratchet had flipped BENCH-136i to `pass` at 10,140
    runs against a published 673, which was reverted.

## Slice review

An adversarial review of the slice diff found seven ways to get a wrong verdict outside the corpus, each with a
reproducer: `pre` tuples that more faults bring back (13), crash reads with times and crash-derived relations (8),
aggregates over negated inputs (12), `pre`/`post` literal types (5), tick 0 (15), and the silent skip of goals whose
hazard held under the run's own faults (14); plus `count` as `u64`, `crash(…)@k`, dropped 0-ary facts, clause
swallowing in parser recovery, run budgets reported as state budgets, `u32::MAX` id fallbacks and a worker panic
that could hang the committer. All are fixed; the reproducers are regression tests
(`tests/integration/tests/ded_ldfi.rs`), and 668 random programs (negation, wildcards, protocol-dependent `pre`,
crash-dependent specs, aggregates, up to 2 crashes) agree with the reference checker's exhaustive verdict in every
mode (lineage-only precise and conservative, exhaustive, default).
