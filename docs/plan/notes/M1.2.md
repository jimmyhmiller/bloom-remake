# M1.2 — Golden corpus I: core semantics (BENCH-001–049) and the corpus README

## What was built

- **`tests/corpus/core/`**: 123 cases for the 47 P0/P1 ids BENCH-001–048 (BENCH-025 is P2 and skipped; BENCH-049,
  the replay and oracle harness itself, is delivered by M7.3). Every case is a self-contained program written to
  LANGUAGE.md (no `std::` imports) or, where the source is a Dedalus program, a Molly-dialect `.ded` twin. The
  expectations come from the cited literature: FEATURES §11.1, the papers, and the research reports R01, R02, R03,
  R05, R08, R09 and R12. Nothing was taken from an implementation, because none exists yet. Every backend starts
  `unimplemented`, with `unimplemented` = the case's features plus the backend's placeholder feature (Deviation 10),
  and `until` computed by PLAN §5.4 from plan.json.
- **`tests/corpus/README.md`**: a reader's guide. It covers the layout, where expectations come from, the schema
  (PLAN §5 verbatim), the status ratchet, the backend floors, and the conventions the M1 cases rely on and the
  runner (M5.2) must implement. Those conventions cover: `.ded` node sets and inputs, deployment, run-length margins,
  host-input ticks, restart semantics (a commit point, no message lost), row encodings, `// expect:` lines, compile
  cases being otherwise clean (and the three cases that rest on a reading LANGUAGE leaves open), level-triggered
  ports, validity as invariants, canonical-priority mode, `strata` tables, `unimplemented` lists and `features`
  (including when SEM-012, LANG-190 and LANG-100 are listed).

**Verification done in this WP.** Every case was reviewed against its source and against the LANGUAGE.md rules that
most often decide a case: syntax, legality (§12), event/standing classification, range restriction, keys and
stratification. That review missed a rule outside that list: LANGUAGE §14.6 makes a compiler-localized body that
mirrors a relation with a `delete` or `upsert` BLS0805, and the first BENCH-026c read P2's overwritten `pred`
through `@ si`. The adversarial review found it. The fix (BENCH-026c now reads an insert-only record, and BENCH-026f
pins the rejection) came with a re-check of every `#[localize]` handler in the corpus against §14.6: BENCH-026a
mirrors only the insert-only `path`, and BENCH-026c only `succ` and `pred_seen`. Expected results were recomputed
by hand tick by tick. The larger ones were also recomputed by independent Python scripts, written from the
published rules and not from Blossom:
- the routing timelines of BENCH-024a/b/c: a synchronous-round simulation of the three programs, reproducing every
  per-tick expectation, including 024c's count to infinity (5, 13, 21 at ticks 13, 21, 29);
- the four BENCH-030 fixpoints (TC, SG, Andersen, CSPA), by naive evaluation;
- the three BENCH-037a stages (28, 64 and 53 reachable pairs) and the BENCH-037b retraction (six facts removed);
- every `until` and `unimplemented` list, recomputed from plan.json;
- every `// expect:` comment against its `[[expect_diag]]` line;
- every `[[input]]`, `[[expect]]` and `[[expect_send]]` relation against the program's declarations, including arity
  and the declared roles of `[deploy]` nodes;
- every `.bls` program's use of `fact`, `bootstrap`, `static`, head aggregates, `emit`, `next`, `send`, `delete`,
  `upsert` and `#[localize]` against the construct ids its `features` lists.

## Deviations from the spec and why

1. **`.ded` twin letters.** PLAN §8 says a twin gets the suffix `d`. Items with more than one Dedalus-sourced case
   give their other twins the next free letter (BENCH-001e, BENCH-007e, BENCH-015f), and `.bls` scenarios skip `d`
   (so BENCH-023, 026, 030, 035, 038, 039 and 041 go from `c` to `e`). The README documents this, and the manifest's
   `program` field decides the frontend.
2. **Canonical-priority mode** (R12's test-only priority table) cannot be selected from a manifest. The exact-answer
   choice cases write the choice as `choose_least!`, `least v` or, for a multi-FD site, `least (x, y)`. That is
   canonical mode's choice under every seed because the cost is unique per candidate (ANA-038 D5). The seeded
   `choose!` is checked separately through invariants.
3. **BENCH-041e** (`resolve`): R12 T2 resolves a same-tick conflict with `resolve choose`. LANGUAGE §10.7 and §22.2,
   which take precedence, apply relation-level policies to t+1 candidates only. The writers therefore use `next`
   into a keyed table, and R12's answer (sel(a) = m) appears one tick later.
4. **BENCH-016b**: Bud's "`<=` from outside a tick" is a host-API check. Blossom's host API cannot express a
   same-tick write, because host inputs always land in a future tick (LANG-067). The case pins the in-program
   counterpart, a write into the program's own `input` (BLS0406). The host half is a follow-up (below).
5. **BENCH-047a** drops the negation of R12's rejected program. The choice then is the cycle's only point of order,
   and the case checks the choice-stratification verdict (BLS0503) instead of mixing in a BLS0502.
6. **BENCH-044a/b/c**: the voter's initial state (R12 T5: term 4, last entry (7, 3)) is static configuration written by
   `bootstrap fresh` in the boot tick, not a host input. The simulator may deliver a RequestVote in the boot tick's
   batch, before a host input could arrive. With a host-input load, the `emit current_term(4)` one tick later then
   conflicts with the carried `current_term(5)` (BLSR001). The sync-harness expectations are unchanged.
7. **BENCH-003d** adds a safe second rule for `p`. It gives `p`'s third column a type, so the unsafe rule's range
   restriction (BLS0500) is the only error rather than an untypeable column. The `.bls` twin annotates the column
   type for the same reason.
8. **BENCH-045b** keeps the carried state in a `table` replaced by `upsert` (R12 carries it in a scratch with
   `@next`). A table is standing, so no `while` header can be classified as an event relation (BLS0505), and BLS0601
   is the case's only diagnostic.
9. Several item parts cannot be stated in manifest schema v1 (performance, derivation counts, statistics over many
   seeds, counterfactual runs, lints with no code). Each is listed under Follow-ups with its owner.
10. **`unimplemented` lists.** The WP rule says `unimplemented` = the case's `features`. The `interp` and `sim`
    backends also list their placeholder ids, SEM-002 and TEST-001 (the "Unimplemented as" column of PLAN §5.2).
    Until M7.3 and M7.2 implement them, those backends fail with `Unimplemented` naming exactly that id, and the
    ratchet (PLAN §5.3) fails an `unimplemented` backend whose reported id is not listed. The README states it.
11. **BENCH-026c is not the literal P2 program.** FEATURES BENCH-026 asks that Chord sb1-sb3 give the same results
    before and after the rewrite. LANGUAGE §14.6, which takes precedence, makes the compiler's localization of
    P2's sb1 and sb3 BLS0805, because they read `pred`, which P2 overwrites (keys(1)). BENCH-026f pins that
    rejection. BENCH-026c therefore localizes a reformulation whose remote atoms read `pred_seen`, an insert-only
    record of every predecessor a node has had. P2's `pred` is kept, and only its own node reads it. sb3 plus
    `set_pred` update `pred` exactly as P2's sb3 does. sb1 adopts every recorded predecessor in (N, S), not only
    the current one, which differs from P2 only when an earlier predecessor of S also lies in (N, S); the scenario
    has no such predecessor. The final `succ` and `pred` equal BENCH-026e's, the hand localization of P2's own
    rules. See Bugs 5.

## Judgement calls (for the triage WPs M6.7 and M8.8)

- BENCH-001b/e: the insert-wins tick uses an inductive insertion (`next` / `p_pos(…)@next :- p_next(…)`) against a
  same-tick deletion. A deductive insertion at the deletion tick is pinned as the contrast (present at t, absent
  from t+1).
- BENCH-002: the scenario (inputs and the re-insertion at tick 8) is ours, derived from the program.
- BENCH-003d: BLS0500 is assumed to be the code the `.ded` frontend uses for validator failure V1 (ARCHITECTURE
  §13.12 renders V1–V4 as user diagnostics; LANGUAGE §20 has no separate `.ded` code).
- BENCH-004: the temporal-safety warning is not asserted (no diagnostic code; follow-up).
- BENCH-005: R02's seed `state(0)@1` is used, and `announce` is a `loopback` (a self-addressed async head).
- BENCH-006/006d: `successor` as data is `a + 1`. The `.ded` twin starts `seq` at tick 1, because tick 0 has no
  events (CR-13).
- BENCH-007: R02's reading that the paper's input facts belong in `m_priority_queue`.
- BENCH-008/008d: the requesters of the `.ded` twin are location constants that occur only as a fact's second
  column. The README states how the runner derives a `.ded` case's node set.
- BENCH-009a/009d: the mocked clock (10·t) is program state; the `soft table` sugar reads the harness clock, which
  schema v1 cannot mock. BENCH-009b therefore pins only the sugar's refresh and eviction, assuming the harness clock
  advances by less than 1000 days over 8 ticks and never goes backwards.
- BENCH-015b: `glass` is a table (Bud's example does not say).
- BENCH-015c/d: `!state(X)` with X unbound elsewhere is read as the emptiness test `not state(_)`. In the `.ded` twin
  a persisted `node(N)` binds the rule's location.
- BENCH-015a/e: `#[allow(self_negation)]` silences BLS0506, so the stratifier's BLS0502 is what the case checks.
- BENCH-016b: BLS0406 (the specific code for writes into an own input) rather than BLS0400. See Bugs.
- BENCH-018: t3 (a table-only rule) is P2's insertion-delta trigger, `on inserted t_counter(i)`. The per-event
  `a_count<*>` is a `per` driver with the count's identity 0 (CR-08, LANG-106). tSoftCounter's TTL is declared but
  not asserted.
- BENCH-019: the periodic events are host inputs at chosen ticks, and the figure's unspecified initial `sequence` is 0.
- BENCH-022b, 023b, 024: SP2 and the DV/DSR rules are localized by hand (compute at the link's far end, ship the
  result back). `path`/`hop` are recomputed each tick from that tick's advertisements (CR-26). The BENCH-024 topology
  (the line a–b–c–d, link c–d failing at tick 10) is ours, as the thesis gives none; RIP's 16 is "infinity".
- BENCH-023b: the distributed program is stable per tick only under synchronous rounds. R01 T3's "with reordering"
  half is covered by the centralized reordered and bursty cases (023c/e), which exercise the engine's maintenance
  under reordered update streams.
- BENCH-023a/c/e: Loo's thesis Figs. 5.7 and 3.9 use small networks of their own, which R01 T3 describes only by
  their changes ("not the SIGMOD06 one"). The cases apply the changes to the SIGMOD06 Fig. 2 network of BENCH-022
  instead, whose links and from-scratch answers are known. Fig. 5.7's update (a->b from 5 to 1) is kept. Fig. 3.9
  deletes c->d, which this network lacks, so the cases delete b->d, the last hop into d. That leaves d unreachable,
  where in Fig. 3.9 a falls back to another path. Every stage's expectation is the from-scratch answer on that
  stage's links.
- BENCH-026c/e/f: `bestSucc` and node ids are static configuration (the n-rules are not part of the test). A single
  stabilization runs at a time, so the quiescent result does not depend on the localization's hop count. The
  statements of a localized handler are taken to run at the handler's own node (the rewrite returns there, "two
  hops per derivation"), so `pred_update`'s sender is the stabilizing node. BENCH-026c's `pred_seen` reformulation
  is Deviation 11. See Bugs 5.
- BENCH-026f: BLS0805 is expected once per rejected localized body (sb1, sb3), on its header line, as §20 words the
  code ("a localized body that ... mirrors a relation with deletions"). BLS1005 is expected only on sb2, the body the
  compiler rewrites: §14.6 names it together with the rewrite, and a body rejected with BLS0805 is not rewritten.
  The overwrite of `pred` is written as `delete` plus `next` over key-less relations, so that no key-conflict lint
  (BLS1003, "may insert or upsert different values for one key") can accompany the expected diagnostics.
- BENCH-027a: the stratifier's verdict is asserted directly, because the LANG-202 catalog relations have no fixed
  schema in LANGUAGE §7.15.
- BENCH-028b: soft state in the DI §3.3.1 TTL form over a mocked clock; the head is derived at each body refresh.
- BENCH-030: the inputs are pseudo-random graphs and programs fixed in the source, and the expected relations are
  the least fixpoints of the published rules.
- BENCH-033: the parity lattice is encoded as `LSet<String>` over {"odd", "even"} (isomorphic).
- BENCH-035c/e: the `start` seed of the bipartite check is ours.
- BENCH-036d: R09 §16 T11's rules are ported verbatim to Molly's dialect. The inserts are timestamped facts of `p`
  itself, because the `.ded` program has no insert event of its own.
- BENCH-037a/b: DDlog's firewall data and DOOP are not reproduced by the sources, so the cases use a network of the
  same shape and Andersen's analysis.
- BENCH-038/039: every dfir test that snapshots a graph gets inputs and outputs of ours, derived from its rules. DFIR's
  arrival-order folds become canonical order (CR-46), and bag inputs become sets (CR-03). BENCH-039j pins LANGUAGE
  §10.1's count over distinct valuations, because dfir-datalog's own `count(*)` semantics is not stated.
- BENCH-040-047: R12's choice, numbering and fold tests are written in a Dedalus-style notation with extensions
  (`choose`, `index`, `fold_ordered`, `min<C>` as a choice) that Molly's dialect does not have, so they get no
  `.ded` twin. Every case ported from a program in Molly's dialect has one (the `d` letters above, BENCH-036d
  included).
- BENCH-040a/b, 041: R12 T1/T2 as written; Bud's sequence is TEST-014's reference, not an expectation.
- BENCH-042a: R12's `next_slot(0) :- bootstrap` is the boot tick.
- BENCH-043a: only validity is asserted. The golden values need the frozen PRF, and R12 says they are not
  hand-computable.
- BENCH-044a: R12's `min<C>` is written as `choose!(c per t least id)` over a numeric candidate id carried in the
  request.
- BENCH-044c: the final `current_term` of n1 is 6 in every run, which makes the case non-vacuous (a simulator that
  delivered no request would leave it at 4). That needs every request to reach n1 and n1's state before its
  scripted restart to survive the restart. The README states both as the reading of a scripted restart: a commit
  point that drops no message. SEM-071 and SEM-072's losses are left to omission, partition and storage faults.
  `[run] ticks` is 30, above n1's worst case of 23 ticks (0-6 up to the restart, at most two per request for 8
  requests).
- BENCH-045a: the host's commit index is the maximum commit value reported so far.
- BENCH-045c: FEATURES and R12 T6 say a false commutativity declaration "fails TEST-015", the oracle's runtime
  shuffle check, whose mismatch has no BLSR code in LANGUAGE §20. LANGUAGE makes a function's algebraic attributes
  claims checked by TEST-087 (§16.1, §10.8), and a refuted claim is BLS0704 (§20). step(1, 2) = 4 differs from
  step(2, 1) = 5, so the claim is refuted at compile time, and the case pins BLS0704 on the `fn` line.
- BENCH-046c: R12 §5.4's greedy order (cost, priority, tuple) is what a `least` cost on one literal of a multi-FD site
  means. LANGUAGE §10.4 does not contradict it and does not spell it out. See Bugs.
- BENCH-047a: BLS0503 rather than BLS0502 (see Bugs).
- BENCH-048: `percentile!` ranks the body's valuations, so the tied 9s count twice (a named `_u` keeps them apart).
- `features` and SEM-012: facts and `bootstrap` blocks are listed by their construct id LANG-190, whose definition
  includes their evaluation at tick 0, and `static` relations by LANG-045. SEM-012 (the engine's boot tick, M6.1) is
  listed only by BENCH-011, the case written to pin it. 29 other cases check tick-0 contents that come from facts,
  `static` relations or a `bootstrap` block. Listing SEM-012 on each would move the oracle `until` of 18 of them from
  M5 to M6 by PLAN §5.4, although the oracle runs those rules in the boot tick through LANG-190's lowering (M5.3)
  and the sync-round harness (M5.2). (The adversarial review expected no `until` to change, which holds for the
  interp backend, whose floor is M7, but not for the oracle.) The README now states the convention. The same pass
  added LANG-190 to the 29 cases that declare facts without having listed it, and LANG-100 to the six cases whose
  views have a head aggregate (BENCH-038g, 039f, 042b, 045b, 045c and 048). Neither changes an `until`.

## Bugs

No code exists in the milestone base, so these are gaps and contradictions in the normative documents that a
later owner must settle. Each names its reproducer case and the WP that meets it first.

1. **LANGUAGE §7.2 vs §8.5 (BLS0505 on the explicit-persistence idiom).** §7.2's sanctioned Dedalus form
   `while p(x), not p_del(x) { next p(x); }` over a `scratch p` makes `p` an *event* relation under §8.5's
   greatest-fixpoint classification whenever `p`'s other writers are event-driven, so the idiom draws "BLS0505: write
   `on`". Reproducer: BENCH-006, BENCH-010, BENCH-036a (runtime cases, so no expectation depends on it). Owner:
   M4.5 (event/standing classification): exempt the self-carrying `next` rule, or amend §7.2 to say `on`.
2. **No diagnostic codes for two FEATURES-required lints.** ANA-003's temporal-safety warning (BENCH-004: "accepted
   with a temporal-safety warning") and ANA-038's D2 lint "ties broken by canonical order" (BENCH-048) have no code
   in LANGUAGE §20, so no manifest can assert them. Owners: M6.6 (ANA-003) and M5.6 (ANA-038). A LANGUAGE amendment
   should assign codes (for example BLS1009, BLS1010), and the corpus cases then gain `[backend.compile]`
   expectations.
3. **BLS0400 vs BLS0406 overlap.** A write into a program's own `input` is forbidden by the §12 matrix ("BLS0400")
   and is also named "BLS0406" in §7.6 and §20. Reproducer: BENCH-016b expects BLS0406 only. Owner: M4.5 (legality):
   report only the specific code.
4. **BLS0502 vs BLS0503 overlap.** A choice site on a same-tick cycle is a negative edge (§13.2), so the cycle is
   BLS0502 by §13.3 and BLS0503 by §13.4. Reproducer: BENCH-047a expects BLS0503 only. Owner: M4.2 (stratification):
   report BLS0503 when the cycle's negative edges are all choice or order sites.
5. **LANGUAGE §14.6 (localized handlers) and FEATURES BENCH-026.**
   - FEATURES BENCH-026 asks that "Chord sb1–sb3 and SP2 give the same results before and after the rewrite". §14.6
     makes the rewrite exact only for insert-only relations: "a mirrored relation with a `delete` or `upsert` is
     BLS0805". P2's sb1 and sb3 read `pred`, which P2 overwrites (keys(1)), so no faithful port of them can be
     localized by the compiler. The literal program is rejected (BENCH-026f). The runtime equivalence holds only for
     a reformulation that reads an insert-only record of predecessors (BENCH-026c, Deviation 11). The first
     BENCH-026c missed this; the adversarial review caught it. LANGUAGE takes precedence, so the corpus follows it.
     Either FEATURES BENCH-026 should say that the Chord half uses an insert-only reformulation, or LANGUAGE should
     give localization a form that is exact for overwritten relations (a request–reply chain that reads the remote
     node's current state, as BENCH-026e does by hand).
   - §14.6 does not say whether BLS1005 accompanies a body rejected with BLS0805. BENCH-026f expects it only on the
     rewritten body.
   - §14.6 does not say where a localized handler's statements execute. BENCH-026c assumes the handler's own node,
     so `from` is the stabilizing node.
   - §14.6's example `on query(d), link(x) @ s, path(d) @ x` uses `s` before anything binds it, contradicting its
     own well-connectedness rule (BLS0805).

   Reproducers: BENCH-026c, BENCH-026f. Owner: M6.4 (LANG-095).
6. **LANGUAGE §10.4 (multi-FD choice with a cost)** does not say how a `least`/`most` cost on one literal of a
   multi-FD site orders the greedy scan. BENCH-046c relies on R12 §5.4's (cost, priority, tuple). Owner: M6.4, with
   the ENG-075 implementer (M8.6).
7. **PLAN §5 gaps the README fills.** Schema v1 does not say:
   - how a `.ded` case's node set is formed (no roles, so no `[deploy] nodes`);
   - whether the `compile` backend compares the reported diagnostics with `[[expect_diag]]` exactly or by inclusion;
   - how the simulator reaches a scripted node-local tick when the node would otherwise be idle (BENCH-043c idles
     after tick 2 before its restart at tick 4; BENCH-044c's c3 idles before its input at tick 6);
   - what a scripted `restart` loses under the simulator: unsynced writes and in-flight messages, which SEM-071 and
     SEM-072 allow, or nothing.

   The README states the readings the M1 cases use. Nodes are the location-typed constants of the facts. Compile
   cases hold under either comparison, except where Bugs 3–5 leave a choice open. The simulator runs empty ticks up
   to a scripted tick, which SEM-009 makes observationally neutral. A scripted restart happens at a commit point and
   drops no message; losses come from omission, partition and storage faults (BENCH-044c's final `current_term`
   depends on this). Owners: M5.2 (the corpus runner and `xtask corpus --lint`) and M7.2 (the simulator harness).
