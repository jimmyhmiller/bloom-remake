## S27.1: the link over plain HTTP requests (CLIENTS.md §3a)

- **Same link, other transport.** The frames, their numbers and acknowledgements, the replay buffer, the offline queue
  and `resumed` are the WebSocket link's. A session stands for the connection: `POST /blossom/http/open` (the HELLO;
  the answer carries `Blossom-Session`), a long-polled `GET …/recv` (only receives bring the node's frames, so they
  arrive in order), `POST …/send`, `POST …/close` (a beacon on `pagehide`). Bodies are length-prefixed frames.
- **When a session ends**: closed by the page; its waiting receive's connection closes (checked twice a second); no
  request for 30 s; the page not keeping up (4096 frames or 32 MiB); a newer session of the member. Then `410`, and
  the page opens another session, which resumes the link like a reconnect.
- **Server**: `blossom-runtime::http_link` (sessions, a pump thread per session from the engine's writer, a reaper);
  `members.rs` factors the handshake (`admit`, `hello_answer`, `member_event`) and ends a link through a `Closer`
  (a socket or a session). The web listener now keeps HTTP/1.1 connections for further requests.
- **Choosing it** (S27.4, the user's choice): the deployment's `[web] link = "http" | "websocket"`, plain requests by
  default (app.json's `transport`; the node serves both; a page's `?link=` overrides, for tests). The program does not
  say: it means the same over either, so where it runs decides. Trade-offs, for the record: a WebSocket needs proxies
  and load balancers that pass upgrades and holds a connection per tab, and cannot be served from a function; plain
  requests work through anything, cost a request per page send, and notice a closed tab within half a second while a
  receive waits (30 s at worst).
- **Page**: `HttpConnection` in `web/host.js`, the same interface as the WebSocket `Connection`.
- **Tests**: `runtime_members.rs` runs its scenarios over both transports (admitted, heard, acknowledged, resumed
  within and after a restart; a replaced connection closed; a stale page refused) and the session's ends (closed,
  a waiting receive gone, the lease, full tier); keep-alive. The Playwright client suite runs twice (WebSocket and
  HTTP); over HTTP it asserts the pages opened no WebSocket: two tabs syncing, offline then catching up after a node
  crash, a stale page reloading, the chat's presence when a tab closes.

## S27.2: an HTTP API written in Blossom

`examples/http/notes.bls`: a notes service on a `listen` byte stream that parses HTTP/1.1 itself (requests in pieces,
pipelined requests answered in order, kept or closed connections, 400 for what is not HTTP), answers from a durable
table, and writes a `201` only once the note is durable (stream writes are released after the tick's sync).
`http_notes.rs` runs it on a real node with the checked backend, through a restart. `curl` works against it
(`examples/http/notes.deploy.toml`).

It needed Appendix B built-ins this build lacked: `split`, `replace`, `starts_with`, `ends_with`, `contains`,
`to_uppercase`, `parse_u64` on strings and `sort` on vectors, on both evaluators; an empty separator or pattern is
BLSR004. `bls_functions.rs` checks them against an independent Rust computation.

## S27.3: serverless (docs/design/SERVERLESS.md)

Research (Neon, Aurora, SlateDB, Turso, Litestream/LiteFS, Durable Objects, WarpStream, Netherite, S3 conditional
writes) and a plan: Blossom as an embedded library first (the SQLite shape), then a store on a bucket (SlateDB-style
epochs and fencing with conditional PUTs, WAL objects with group commit), then a node in a function (durable client
outboxes, a next-wake schedule for timers, peer inboxes), with Durable Objects as the closest platform fit.
