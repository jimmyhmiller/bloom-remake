# S12: a faster LDFI

**Goal (user, 2026-10-05):** reuse the hazard encoding across runs so LDFI's pruning pays off on fault spaces beyond
enumeration. S11 measured the problem: on the Kafka specs a run costs 0.1–0.3 s, encoding its lineage 2–10 s, and
under crash-restarts the lineage pruned nothing, so enumeration (`--enumerate`) was the faster oracle.

## What a run's encoding is made of (measured on `TripleTwoLosses`)

- ~22 000 goals but ~443 000 distinct appearance entries per run: tuple-level negative support asks whether a tuple
  can appear at a place, chained back through every tick, across hundreds of relations (no relation dominates).
- Entries are spread evenly over the ticks; cycle cuts are rare (~150 per run, all among appearances).
- A lost message that matters changes ~20–30% of the goals at each later tick; **161 of the 348 single lost
  messages change nothing** (no stream crosses between the two nodes in that round).

## Done

- **Hazards as a circuit** (bb1a365): the encoder builds immutable shared nodes over fault atoms
  (`blossom_ldfi::circuit`), and each solver is given the nodes it needs (`FaultVars::emit`); `single_hitters`
  walks the circuit. Same hypotheses; encode 0.99 → 0.82 s per run (building nodes is cheaper than solver
  variables).
- **Precise stream hazards:** the run records every round a stream carried something between two nodes (bytes, a
  close, a dial; `SyncRun::dials` is new), and a lost message counts as able to reset a connection only on such a
  crossing (or when faults can make the sender issue new requests, as before). `TripleOneLoss`: 217 → **188** runs,
  exactly the 187 lost messages that change the run plus the failure-free one.
- **Hazards shared across runs and workers** (`blossom_ldfi::shared`): a hazard at tick `t` depends on the graph up
  to `t` and, of the run's faults, which nodes crash, crashes up to `t` and omissions sent before `t`; two runs that
  agree on that agree on the hazard. Only contexts that name no fault tick are shared (they recur: "no fault yet",
  "node n crashes later"), each tick once (a frontier per context), and only values computed as the root of their
  own search (fixpoints, traversal-independent); a run whose cycles mix goals and appearances shares nothing.
  `TripleRestart`: 88 s → 58 s (2 workers, same 157 runs); `TripleTwoLosses` run 12: encode 0.77 → 0.62 s.
  Results do not depend on it (`ldfi_restart::sharing_hazards_across_runs_and_workers_changes_no_result`, which a
  context that forgets crashes fails). `--shared-hazards N` bounds the entries (default 4M; 0 turns it off).
- **Interned patterns** (`blossom_ldfi::patterns`): place keys were tuples holding a row pattern (Kafka's rows carry
  byte strings), hashed, compared, allocated and dropped on every lookup: about a third of the encoder's time. A
  pattern is now a number, interned once per search (the shared hazards are keyed by it too), and a rule's body
  patterns for a head pattern and location are computed once (a `Plan`) instead of at every tick of the chain.
  `TripleTwoLosses` run 12: encode 0.77 → **0.46 s** (no sharing), same hypotheses; since the start of S11,
  1.25 s → 0.46 s.

## Kafka specs under S12 LDFI (server, 14 workers)

Same verdicts and counterexamples as S11 (and as enumeration) on every spec.

| spec | S11 LDFI runs | S12 LDFI runs | S12 time | enumeration (8 workers) |
|---|---|---|---|---|
| TripleRestart | 157 | 157 | 18 s | 157 schedules, 4 s |
| TripleRestartAcks1 | — | 61 (fails) | 12 s | 61, 3 s |
| TripleOneLoss | 217 | **188** | 19 s | 349, 8 s |
| TripleTwoRestart | 197 | 197 | 41 s | 197, 6 s |
| TripleRetry | — | 165 (fails) | 31 s | 230, 8 s |
| TripleRetryIdempotent | 264 | **244** | 38 s | 469, 13 s |
| TripleCommitRestart | 337 | 337 | 165 s | 337, 17 s |
| TriplePartitionsRestart | 377 | 377 | 284 s | 377, 22 s |
| TripleTwoCrashes | 9 283 | 9 283 | 731 s | 9 283, 148 s |
| TripleTwoLosses | 23 581 (~70 min) | **17 637** | **30 min** | 60 727, 17 min |
| TripleLossRestart | 34 275 (~1.6 h, 20 workers) | **29 302** | **45 min** | 53 785, 15 min |

(The first six ran on cffdea6, the rest on 4fd237d with interned patterns.)

- Lost messages: the precise stream hazards cut runs by a quarter, and the encoder is ~3× cheaper per run than at
  S11's start; `TripleTwoLosses` 70 → 30 min. Enumeration still uses ~3× less worker time there.
- Crash-restarts: the lineage still suggests every crash time of every node (runs = schedules), so enumeration
  stays the faster oracle for these specs: LDFI's gains there have to come from pruning, not encoding.
- **The oracle by size (user choice, 2026-10-05).** `blossom ldfi --method auto` (the default) decides by enumeration
  when the spec's admissible schedules fit `--max-schedules`, and by the lineage-driven search beyond it
  (`blossom_ldfi::decide`); `--method lineage|enumerate` forces one (`--find-all`, `--lineage` use the lineage-driven
  search). Replaces S11's `--enumerate`.
