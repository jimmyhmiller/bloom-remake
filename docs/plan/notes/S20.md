# S20 — user-defined lattices

The user (2026-10-06), after an explanation of LANGUAGE §11.8: "Add it". Scope as explained then: lattice aliases,
product lattices, `impl` blocks with method classes and the law harness; `extern lattice` and SMT proofs later.

## What was built

- **Lattice types.** `lattice X = L;` names a lattice type (a plain type is BLS0300). `lattice X { f: L, … }` is a
  product (`LatticeCtor::Product { name, fields }`): nominal, its fields lattices, merged, ordered and ⊥ fieldwise
  (`blossom_lattice::Kind::Product` over `LatValue::Seq`). A literal may leave fields out (they are ⊥, the HIR's
  `Bottom`); `x.f` reads a field (a morphism); `join`, `leq!`, `is_bot!` and `reveal!` (the struct of the fields'
  reveals, named after the product) work as on every lattice. No plain value lifts into a product. A product that
  contains itself is BLS0300.
- **Methods.** `impl X { [class] fn m(self, …) -> T { … } }` on a product, at a file's top level. Each method is a
  pure function taking the receiver first, and an entry of the lattice's catalogue: every `LatOpDecl` now says how it
  is evaluated (`LatOpImpl::{Builtin, Field(n), Method(f)}`), so the engine, the oracle and the polarity analysis read
  methods like built-in operations. Calls follow the bang rule by class (BLS0700/0701). A `stable fn m … after t` has
  two entries: `m` (classed `Stable`, monotone in its receiver), used where the same body guards the receiver with
  `t`, and `m!` (non-monotone) for a banged read; an unguarded read without a bang is BLS0703. A class constrains the
  signature (BLS0300). The validator checks every entry against its implementation.
- **Polarity.** A guarded stable read is data: its value is fixed wherever it is read, so a `monotone` view or
  module may make one (the cart's `finish` has no point of order).
- **The law harness** (`blossom_verify::laws`, `blossom_lattice::laws`, TEST-083). A product's merge laws hold by
  construction ("proven") and are checked on samples anyway. Each classed method is a claim, tested on values
  generated from the lattice's types over small domains (plus joins of samples that reach the claim's threshold),
  evaluated through the oracle (`Oracle::eval_op`). A case where the method raises a runtime error is set aside, and
  a stable claim is checked only where its threshold holds at both ends. A refuted claim is BLS0704 at the method
  (`BlsArtifact::methods`), with the counterexample's values as notes. The CLI runs it wherever it compiles a program;
  `blossom check --laws` prints the statuses.
- **Map library**: `keys`, `values`, `entries`, `insert`, `remove`, `contains_key` (LANGUAGE Appendix B), needed by
  the cart programs.
- **Wire**: products encode as their fields, each length-prefixed (`LAT_SEQ`).

Corpus: BENCH-060a–c (the monotone cart), 063c (causal CRDTs as products) and 076d (an OR-set) now pass on the
oracle and the engine. 063a needs `Lex`/`Lww` (LANG-131), 076c and e05 final outputs (LANG-212).

## Decisions made on the way

- **`impl` only on products, only at a file's top level.** An alias is not nominal, and a lattice's methods are
  type-level: a module instantiated twice must not give its lattice two sets of methods.
- **A field read's catalogue name is `.f`**, so fields and methods have separate names, as in Rust.
- **The harness found a real gap in the corpus's cart**: `summary` changes when an operation outside the checkout's
  range arrives after completion. In that state `complete` raises the program's error, so no guarded read happens
  there; the stable obligation was made precise accordingly (`a ⊑ b ∧ t(a) ∧ t(b) ⇒ m(a) = m(b)`) and documented.
- **A failing synchronous round runs to its end**: the other nodes' ticks do not depend on the failing one, so the
  simulator reports every failure of the round (`SimError::Node::also`), and the corpus runner requires the failures
  to be exactly the expected errors (BENCH-060b expects BLSR006 on three replicas).

## Known limits

- `extern lattice` (LANG-027/LANG-135 (3)) is still BLS0908; claims are never "proven" (no SMT, VER-014).
- Function classes on free functions (`monotone fn` outside an `impl`, LANG-182) are still BLS0908.
- The harness does not run on a spec's compiled target (`blossom sim --spec`, `blossom ldfi --spec`), nor in the
  browser's live editor; a program's own compile runs it.
- Coverage depends on the generated domains: a threshold that only a large or specific value reaches is tested on
  few cases (`--laws` shows the counts).
