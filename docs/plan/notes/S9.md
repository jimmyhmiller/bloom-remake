## Goal

KAFKA.md's acceptance for groups: `kcat -G`, the Java `KafkaConsumer` in a group (the console consumer with
`--group`), and a franz-go group consumer work against three to five `blossom run` brokers with default settings.
Groups rebalance when members join, leave or die; committed offsets survive a coordinator failover; committed
offsets never move backwards.

## Items

1. **`__consumer_offsets`.** An internal topic created when the cluster bootstraps (Kafka's defaults:
   `offsets.topic.num.partitions` 50, replication `min(3, brokers)`), placed and replicated like any other. A group's
   coordinator is the leader of partition `abs(java_hash(group_id)) % partitions`, as Kafka computes it. Metadata hides it
   unless asked for by name (Kafka marks it internal).
2. **FindCoordinator (10).** Versions 0–6 (v4+ batches keys, KIP-699). Key type GROUP; TRANSACTION is refused
   (out of scope, K1). Answers the coordinator partition's leader, or COORDINATOR_NOT_AVAILABLE while it has none.
3. **The classic group protocol at the coordinator.** JoinGroup (11), SyncGroup (14), Heartbeat (12), LeaveGroup (13):
   - member ids (KIP-394: a first join without one gets MEMBER_ID_REQUIRED and an id), generations, the protocol
     chosen from the members' common protocols, the group leader (the first member to join);
   - states Empty / PreparingRebalance / CompletingRebalance / Stable / Dead;
   - the initial rebalance delay (`group.initial.rebalance.delay.ms`, 3 s), rebalance timeout, session timeout
     (members that stop heartbeating are removed), via guarded timers (only while a group needs them);
   - NOT_COORDINATOR from a broker that is not the coordinator; ILLEGAL_GENERATION, UNKNOWN_MEMBER_ID,
     REBALANCE_IN_PROGRESS as Kafka answers them;
   - membership is volatile: a new coordinator starts every group Empty, as Kafka does; static membership
     (`group.instance.id`) is out of scope unless a client needs it.
4. **OffsetCommit (8) and OffsetFetch (9).** A commit is a record in the group's `__consumer_offsets` partition,
   appended through its Raft group and answered when committed (so it survives coordinator failover); the committed
   offsets are materialized per (group, topic, partition). Generation and member checks as Kafka's; a commit from a
   simple consumer (generation -1, no member) is accepted for an Empty group. OffsetFetch reads them (v8+ batches
   groups).
5. **ListGroups (16), DescribeGroups (15).** For the admin tools (`kafka-consumer-groups.sh --list/--describe`).
6. **Tests.**
   - The codec oracle for every new request and response (kafka-protocol), as for S7/S8.
   - Simulator: members join, leave and die; rebalances settle to one assignment per generation; a coordinator kill
     moves groups, and committed offsets survive it; a log checker for committed offsets (never backwards, every
     acknowledged commit visible to a later fetch).
   - Real clients against real processes: the console consumer with `--group`, a Java `KafkaConsumer` program,
     `kcat -G`, franz-go; a group rebalancing across a broker kill.
   - Every safety test mutation-checked.
7. **Adversarial review**, fixes, notes, merge.
