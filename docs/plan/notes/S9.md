## Goal

KAFKA.md's acceptance for groups: `kcat -G`, the Java `KafkaConsumer` in a group (the console consumer with
`--group`), and a franz-go group consumer work against three to five `blossom run` brokers with default settings.
Groups rebalance when members join, leave or die; committed offsets survive a coordinator failover; committed
offsets never move backwards.

## Items

1. **`__consumer_offsets`.** An internal topic created when the cluster bootstraps (Kafka's defaults:
   `offsets.topic.num.partitions` 50, replication `min(3, brokers)`), placed and replicated like any other. A group's
   coordinator is the leader of partition `abs(java_hash(group_id)) % partitions`, as Kafka computes it. Metadata hides it
   unless asked for by name (Kafka marks it internal).
2. **FindCoordinator (10).** Versions 0–6 (v4+ batches keys, KIP-699). Key type GROUP; TRANSACTION is refused
   (out of scope, K1). Answers the coordinator partition's leader, or COORDINATOR_NOT_AVAILABLE while it has none.
3. **The classic group protocol at the coordinator.** JoinGroup (11), SyncGroup (14), Heartbeat (12), LeaveGroup (13):
   - member ids (KIP-394: a first join without one gets MEMBER_ID_REQUIRED and an id), generations, the protocol
     chosen from the members' common protocols, the group leader (the first member to join);
   - states Empty / PreparingRebalance / CompletingRebalance / Stable / Dead;
   - the initial rebalance delay (`group.initial.rebalance.delay.ms`, 3 s), rebalance timeout, session timeout
     (members that stop heartbeating are removed), via guarded timers (only while a group needs them);
   - NOT_COORDINATOR from a broker that is not the coordinator; ILLEGAL_GENERATION, UNKNOWN_MEMBER_ID,
     REBALANCE_IN_PROGRESS as Kafka answers them;
   - membership is volatile: a new coordinator starts every group Empty, as Kafka does; static membership
     (`group.instance.id`) is out of scope unless a client needs it.
4. **OffsetCommit (8) and OffsetFetch (9).** A commit is a record in the group's `__consumer_offsets` partition,
   appended through its Raft group and answered when committed (so it survives coordinator failover); the committed
   offsets are materialized per (group, topic, partition). Generation and member checks as Kafka's; a commit from a
   simple consumer (generation -1, no member) is accepted for an Empty group. OffsetFetch reads them (v8+ batches
   groups).
5. **ListGroups (16), DescribeGroups (15).** For the admin tools (`kafka-consumer-groups.sh --list/--describe`).
6. **Tests.**
   - The codec oracle for every new request and response (kafka-protocol), as for S7/S8.
   - Simulator: members join, leave and die; rebalances settle to one assignment per generation; a coordinator kill
     moves groups, and committed offsets survive it; a log checker for committed offsets (never backwards, every
     acknowledged commit visible to a later fetch).
   - Real clients against real processes: the console consumer with `--group`, a Java `KafkaConsumer` program,
     `kcat -G`, franz-go; a group rebalancing across a broker kill.
   - Every safety test mutation-checked.
7. **Adversarial review**, fixes, notes, merge.

## Decisions

- **D1 Versions.** Exactly Kafka 4.0's ranges: FindCoordinator 0–6, JoinGroup 2–9, SyncGroup 0–5, Heartbeat 0–4,
  LeaveGroup 0–5, OffsetCommit 2–9, OffsetFetch 1–9, DescribeGroups 0–6, ListGroups 0–5. librdkafka 2.15 (kcat)
  speaks their legacy (non-flexible) versions, so every message has both encodings, in one format each, by the new
  `select(cond, A, B)` element (LANGUAGE §16.7): `kstr(flex)` and friends in `protocol.bls`.
- **D2 `__consumer_offsets`.** Created when a FindCoordinator first needs it (as Kafka does), by a creation command
  like Metadata's auto-creation; the coordinator lookup answers COORDINATOR_NOT_AVAILABLE meanwhile (clients retry).
  `OFFSETS_PARTITIONS` (50) partitions, replication `min(3, brokers)`. Metadata lists it marked internal (as Kafka
  does: `kafka-topics.sh --list` and `kcat -L` show it); Metadata never auto-creates it; Produce to it is refused
  with INVALID_TOPIC_EXCEPTION, as Kafka refuses clients appending to an internal topic.
- **D3 The coordinator** of a group is the leader of partition `abs(java String.hashCode(group)) % partitions`
  (Kafka's `Utils.abs`: MIN maps to 0), hashed over UTF-16 units. It answers group requests once it has committed an
  entry of its own term (so every entry an earlier leader committed is committed here): before that,
  COORDINATOR_LOAD_IN_PROGRESS, as a Kafka coordinator loading its partition does. Elsewhere, NOT_COORDINATOR.
- **D4 Membership is volatile**, at the coordinator: a group's whole state is one value (`Group`, in `groups.bls`) and
  the protocol is pure functions over it (one request or timer per group per tick, in arrival order, as Kafka's
  coordinator serializes a group's events). A new coordinator starts each group Empty; its members' next requests
  get UNKNOWN_MEMBER_ID / ILLEGAL_GENERATION and they rejoin. Kafka persists the group's assignment; a rebalance
  after failover costs the same here without it. Deadlines (session, rebalance, initial delay, pending members) are
  noticed at the node's ticks (`raft_heartbeat` keeps it ticking, as for every request deadline).
- **D5 Offset commits** are entries of a new kind, OFFSETS (4), in the group's `__consumer_offsets` partition log,
  proposed by its leader (the coordinator) and answered once committed and held by the in-sync replicas, like
  `acks=all`. Every replica materializes the committed entries in log order into a durable `committed` table; the
  coordinator answers OffsetFetch from it and from the committed entries not materialized yet. So an acknowledged
  commit survives any coordinator failover, and a fetch never sees an older offset than one acknowledged before it.
  A committed offset carries its topic's id when committed, and is shown only while that topic exists under that id.
  A partition named twice in one commit is committed at its last value. OffsetFetch is answered only once the
  coordinator's leadership is confirmed after the request arrived (Raft's ReadIndex: a majority answered a heartbeat
  sent since; heartbeats carry their send time and answers echo it), so a deposed coordinator cut off from its
  successor answers nothing stale; unconfirmed after `OFFSET_FETCH_CONFIRM`, it answers NOT_COORDINATOR.
- **D6 Compaction of the offsets logs**, as the controller's (HD): an offsets partition's applied entries are
  compactable but the last `OFFSETS_KEEP` (1000), in steps of that many; a replica that takes a snapshot point
  (InstallSnapshot) is `offsets_stale` (durable) until another replica that applied that far sends its committed
  offsets (`offsets_want`, `offsets_chunk`); it adopts them and their index. A stale replica neither materializes nor
  coordinates.
- **D7 Static membership** (`group.instance.id`), partly: as in Kafka, a static member joins without
  MEMBER_ID_REQUIRED, and a static member joining anew replaces the member of its instance id (so a restarted one
  leaves no copy of itself holding partitions). Unlike Kafka, the replacement rebalances the group (Kafka keeps the
  assignment), and requests from a replaced member get UNKNOWN_MEMBER_ID (Kafka's FENCED_INSTANCE_ID).
- **D8 Two language extensions** made the codecs and the coordinator small: the `select(cond, A, B)` format element
  (one format for a message's legacy and flexible encodings) and struct update `S { f: e, ..base }`.
- **D9 Raft: CheckQuorum and PreVote** (§6.2, §9.6; `raft.bls`, params `RAFT_CHECK_QUORUM`, `RAFT_PRE_VOTE`, both on).
  A coordinator cut off from the other brokers (not from its clients) went on believing it led: its members kept
  heartbeating it while their commits timed out (Kafka has the same failure mode). With CheckQuorum a leader that
  hears from no majority for a period (`RAFT_ELECTION_MIN`) steps down, and is never its term's candidate again (it
  holds that term's votes). Stepped-down leaders then ran elections while cut off and raised their terms, deposing
  working leaders when back (kafka_topics' controller test settled late); PreVote stops that: a member asks whether
  it could win before it raises its term, and a member that heard a leader recently (or leads) says no. PreVote
  needs CheckQuorum (a leader refuses pre-votes); the S4 re-election scenario runs Raft without both. A pre-vote
  answer carries the answerer's term, which a member behind adopts (etcd does the same): otherwise two survivors, one
  with the most complete log and an older term, the other with a newer term from a failed election, refuse each
  other for ever (the full tier's `kafka3` raft test found a partition that never got a leader).
- **Not done (out of scope, recorded):** offsets retention (`offsets.retention.minutes`: Kafka expires an empty group's
  offsets after 7 days; here they stay); the consumer protocol of KIP-848 (ConsumerGroupHeartbeat); transactional
  offset commits (TxnOffsetCommit, K1).

## Debugging tooling, and the kafka3 leaderless partitions

The kafka3 kill -9 test (`three_brokers_keep_every_acknowledged_record_under_kill_9_and_partitions`) failed from
7002a6a on: some partitions had no stable leader after the faults. Bisecting and guessing at Raft changes (PreVote's
answer term, CheckQuorum off) did not find it. The user's direction (2026-10-02): build the tooling that makes it
findable, then use it. Built (`docs/dev/DEBUGGING.md`): `blossom run --record`, `blossom trace replay | show |
history | why | whynot | profile`, `replay --slow`, the engine's per-rule work counters, `BLOSSOM_RECORD_DIR` in
kafka3. The traces found it in a few steps: a Fetch from offset 0 took one tick of ~3.7 s (debug build) to evaluate,
the broker missed its election timeout, and leadership rotated every few seconds, so the test never read every
partition. The cost was the engine's: recursive strata ran naively (O(n²) for a chain of n batches), and the chain's
second probe used only a range. Fixed in the engine (semi-naive recursive strata where that reaches the same
fixpoint; a later binding keys a probe past checks that cannot fail), not in the Kafka program; the recorded traces
replay to the same outcomes. Why the failure began at 7002a6a is not established (it did not touch fetch, and main's
run was not recorded); the stall was the engine's either way.

## Performance note (for S10)

Each partition is a Raft group, and an idle group costs work at every heartbeat (50 ms): beats, acks, the election
deadline and `heard_at` rewritten, the leader's announcement. `__consumer_offsets`' 50 partitions make a three-broker
cluster carry ~54 groups: idle, a debug build saturates a core per broker (produce latency ~0.8 s), against ~25% with
the topics alone; a 150 ms heartbeat halves it. Release builds are about ten times faster. The tests run with 4–5
offsets partitions. Making idle groups cheap (heartbeats batched per broker pair, deadlines not rewritten per beat,
announcements on change) belongs to S10's performance work; any topic with many partitions pays the same.

  without CheckQuorum (ReadIndex alone keeps it from answering stale offsets). Checks: every assignment is the
  leader's; no fetch below an offset acknowledged before it (or before it on the same connection); the live members
  settle into one generation covering every partition; the replicas of each offsets partition agree.

- Mutations (`~/bloom-s9-mut.py` on the server): caught — an answer before the commit (M1), a wrong assignment (M2),
  members that never expire (M3), an adopted snapshot without its offsets (M6), no dedup of a partition named twice
  (M8c), no ReadIndex (M9), no CheckQuorum (M10). Survive by design: fetching without the committed-but-not-
  materialized entries (M4) and serving before the term's first entry commits (M5) — the ReadIndex wait outlasts
  both windows; each one of the two dedups alone (M8, M8b) — each covers the other.
