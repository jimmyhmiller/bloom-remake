# S11: LDFI over the whole Kafka broker, under crash-restart (working notes)

The user's goal (2026-10-04): "get all the Molly stuff working for this so we can really have confidence that this is
correct." Choices (question tool): the **whole broker directly** (not the Raft layer first), and **crash-restart from
the start** (not Molly's crash-stop). Branch `slice-11`, worktree `.worktrees/s11`, from main after S10 (aae7510).

## Where LDFI stands

- Molly parity on `.ded` programs (S1), Blossom programs with `spec … for Module` (e04, e12: BENCH-137a–h), on the
  synchronous-round world (`blossom-sim::sync`, `spec`), the protocol run on the **oracle** (lineage needs every
  firing; the engine records none).
- Faults: omissions before EFF, crashes under `Frozen` (CR-20) or `MollyContinue`. Crash-recovery is TEST-037 (P1,
  "experimental"): R10 §A3.4(8), "a crash deletes non-durable relations and a restart resumes persistence from durable
  ones". Molly lists crash-recovery as future work (R06 §2.2): it is a loss window *and* a loss of ephemeral state.
- Refused today, and used by the broker: guarded timers in lineage (LANG-172; the world already simulates them),
  host streams (the broker's every request; the world has none).
- Feasibility (measured): the oracle runs the broker at ~1.6 ms a tick (the engine 0.11 ms): a 40-round run of four
  nodes is ~160 ticks, under a second before capture. Lineage size and the SAT encoding at this scale are the open
  questions.

## Plan

1. **Crash-restart in the synchronous world.** A fault `restart(n, t, t')`: `n` does not run rounds `t..t'`; messages
   to it are lost and it sends none; at `t'` it boots with the durable relations as they were after round `t − 1`
   (a round is atomic: a crash in a round loses that round, as a crash before its WAL sync does), every volatile
   relation empty, `boot()` and `recovered()`, its timers re-armed.
2. **Streams in the synchronous world.** Node-to-node connections on a node's streams (dial, accept, `opened`,
   `data`, writes delivered the next round, `closed`), in `seq` order; a crash closes its connections at both ends.
3. **A spec over the broker.** The broker and the Blossom Kafka client as a spec target, the client driven by spec
   facts (produce, fetch), with the Kafka properties as `pre`/`post`: an `acks=all` batch is never lost and holds its
   acknowledged offset on every replica that is up; an acknowledged batch is fetched back; an idempotent batch is
   stored once.
4. **LDFI lineage and hazards** for the new world: stream data as message-like premises; guarded timer firings
   derived from their guards; restart variables (the frames of volatile relations break at a restart, firings and
   sends stop while down, the crash budget counts restarts). Validated on small programs first: a toy protocol that
   acknowledges before its write is durable must give a counterexample, the correct one must hold.
5. **The broker under LDFI**: the failure-free run, its lineage, the search; seeded bugs (a produce answered before
   its commit, a leader counting its own unsynced copy, an in-sync replica not waited for) must be found, the
   correct broker must hold at its bounds.
6. **Performance** as the runs require (capture cost, snapshot resume, parallel runs).

## Progress

- **Step 1 (4e8a192).** `FaultSchedule.restarts`: a crashed node runs again from its restart round, with the durable
  relations of its last round, a new incarnation, `boot()` and `recovered()` (Frozen view only; under the `.ded` view
  a restart is `Unimplemented`, TEST-037). The round loop now makes every timer's firings, not only the guarded ones,
  counted from the incarnation's boot as `blossom_node::timers` does (a restart re-anchors them); `BlsSim` reuses
  `runtime::Runtime` instead of its own copy of the timer scan.
- **Step 2.** `blossom_sim::fabric`: streams between the nodes of a synchronous run, on the runtime's `StreamInbox`,
  `SeqWriter` and `host_request`, with the cluster simulator's rules on rounds. Decisions:
  - A round's host requests are done in two phases: what is local to each node (a write's place in `seq` order,
    pause and resume, the node end's own close, retirement) at every node first, then what crosses the network
    (bytes, the close the peer learns of, dials), at the start of the next round. Without the split a node's pause or
    close in round `t` would or would not catch its peers' round-`t` bytes depending on the nodes' order.
  - A dial in round `t` opens both ends in round `t + 1` (no separate handshake round), so the connecting end may
    write in `t + 1` and the accepting end reads it in `t + 2`.
  - Faults keep one vocabulary: an omission of `from → to` in round `t` resets every connection carrying bytes or a
    close from `from` to `to` in that round, and fails a dial `from` makes to `to` in it. A crash resets every
    connection of the node from its crash round (the peer learns in that round).
  - Every stream event a node takes carries its causes (`fabric::Cause`: the writes and resume its bytes come from,
    the dial it answers, the close, crash or omission behind a `closed`), the premises lineage needs in step 4.
  - `SpecSim` connects streams whenever the program has them; `BlsSim` only with `.connecting_streams()` (its tests
    feed stream events as inputs).
- **Step 3 (aeb9a8b).** `examples/kafka/ldfi.bls`: the broker and the Blossom client as a module `Kafka`, one broker
  and the client, the producer guarantees (durability: an acknowledged batch is in the log of every broker that is
  up; read back: a client that read to the end read every acknowledged batch). The failure-free run acknowledges at
  round 15 (50 ms rounds) and holds both. On the way: a frontend bug (a module's types resolved their field types at
  file level) fixed.
- **Step 4a/4b: LDFI under crash-restarts and over guarded timers.** Decisions:
  - `faults { …, restart: d }`: every crash is a crash-restart, the node down for `d` ticks (one fixed downtime per
    spec, so a crash is one fault variable; a spec per downtime explores others). Without `restart`, crash-stop.
  - Fault variables: crash-stop keeps the monotone `K(n,t)` chain; crash-restart uses exact crash-time variables
    `X(n,c)`, at most one per node (a ladder), so "down at `t`" is a disjunction of `X`s and the encoding stays
    monotone in the fault variables (minimal enumeration unchanged). Hypotheses keep the run's own crash fixed.
  - New premises: `NoRestart(n,t)` on a volatile relation's frame (a restart at `t` loses it), `NotRestarted(n, from,
    t)` on a timer's firing (a restart after `from`, the start of the firing's incarnation, starts the count again),
    `Up(n, from, to)` (for stream events, step 4c). A restarted node reloads what its last round carried out (that
    round's next state, not its instance): a durable head of an inductive firing in the round before the crash holds
    again in the restart tick, the firing relocated there (the crash tick never ran). A firing is made by a rule or by
    the runtime (`By`).
  - A guarded timer's firing needs some guard tuple in the node's previous round; faults can make timer firings,
    `boot()` and `recovered()` appear (restarts, a guard that appears), which tuple-level negative support now knows
    (`Origin::Timer`, `Origin::Restart`).
  - The spec's `crashed(n)` is "down at EOT" (a restarted node is up). Spec targets take arguments
    (`for Store(DURABLE = false)`), for seeded-bug variants.
  - Validated on toys (`tests/integration/fixtures/ldfi/`): a store that keeps an acknowledged write volatile fails
    under crash-restart and holds under crash-stop (the frozen view hides it), durable holds; a sender whose resend
    timer is guarded by volatile pending state fails under a restart, durable holds; a guarded timer armed by one
    message is silenced by losing it (only the guard's lineage shows it; mutation-checked).
  - Exhaustive certification refuses crash-restarts (TEST-037): it steps rounds itself, without restarts.
- **Step 4c: LDFI over streams.** Host requests (`write`, `close`, `dial`, `pause`, `resume`) are goals of their
  async firings. A stream event is supported by a runtime firing whose premises are its causes (the request rows
  whose bytes it carries, the resume that let them through, the close it reports, the closed event a retiring end
  took, the dial it answers) and its connection: `opened` at its end, a `Clock` for every round traffic crossed the
  connection up to the event's causes (an omission resets it), `Up` for both ends meanwhile (a crash resets it and
  clears the inbox), and for bytes the connection's previous bytes at its end. The fabric records this (precise
  causes, each event's connection and "as of" round, every connection's dial and traffic). Faults beyond the run's
  own can make any stream event appear (a reset, a failed dial, new requests): conservative, which the broker's
  `while not kafka.closed(c, _)` tables need. Appearance counts only faults the run does not already have (the run's
  own crash and omissions are already in it; under crash-restart a node crashes once).
  - Toys: the store over a stream (durable holds under lost messages and a restart, volatile fails), and an eager
    client that counts its own write acknowledged, found by `O(C,S,1)` only through the traffic clocks
    (mutation-checked).
  - Tooling: an incomplete lineage now says which run and goal, and `explain::lost_under` walks the derivation under
    the run's faults to the premises they falsify (or says it is a negated read or an aggregate group). It found the
    appearance bug above at once.
- **Step 5 begins: the broker under LDFI.**
  - `blossom ldfi --progress`: a line per committed run (faults, lineage size, hypotheses suggested, queue, and the
    time to run it, build its lineage and find its hypotheses), through an `Observer` the CLI implements (the search
    reads no clock: time is injected, the determinism discipline).
  - First measurements, one broker and the client, EOT 30: a run is ~6.1k goals and firings, 0.02 s to run and 0.01 s
    to build its lineage; finding its hypotheses took ~2 s, 63% of it `ArtifactRules::origin` scanning every rule per
    call (now indexed once per search: ~0.2-1 s).
  - Stream appearance made precise for omissions: a lost message can reset a connection only in a tick traffic can
    leave its sender (the run has it make a request or take a stream event then, or a new request can appear then).
  - `SingleRestart` (one crash-restart of either node at any tick, down 2 rounds, no lost messages): **holds**, 59 runs
    in 5 s. With lost messages (`SingleFaults`, EFF 20) the queue grows past 5k: every reset of the client's connection
    makes it redial and resend, a different run each time; such specs need a narrower window or a faster search.
  - A single broker has no natural seeded bug for durability: it syncs a round's durable writes before releasing its
    answers, so even `acks=1` is durable on one node. The seeded bugs (acks=1 lost to a leader crash before followers
    copy, a leader counting its own unsynced copy, an in-sync replica not waited for) need three brokers.
- **Three brokers.**
  - The Blossom client follows the partition's leader: it tries its `contact` brokers in turn (`BROKER_ADDR` alone
    without any), moving on when a connection closes, a dial fails, or a broker answers NOT_LEADER_OR_FOLLOWER /
    LEADER_NOT_AVAILABLE (the batch, not appended, is sent again). `CLIENT_ACKS` (default -1) is the producer's acks.
  - Spec targets bind body `param`s too (`for Kafka(CLIENT_ACKS = 1)`), as a deployment does. A spec trace holds a
    `Blob` column as the blob's reference (hash and length, `Bytes`), so a property may compare which batch replicas
    hold (`trace_value`; lineage and negative support match references against the protocol's blobs).
  - `blossom sim --restart NODE:TICK` (with `--crash`), to look at a counterexample's run.
  - The durability property, refined twice by false counterexamples (both checked in `blossom sim`): a restarted
    replica of an idle, quiesced group does not learn the commit index for many rounds, so "every live replica holds
    it materialized" is too strong; and an acknowledgement just before EOT is committed but not yet materialized. Now:
    some broker holds the batch committed (materialized `batch`, or `pending_batch`; a broker down at EOT counts with
    the state it went down with), and no two brokers hold different batches (by blob) at its offset.
  - Results (EOT 40, 50 ms rounds, one crash-restart of any node, down 3 rounds): `TripleRestart` (acks=all)
    **holds**, 157 runs, 88 s; `TripleRestartAcks1` (acks=1, a misconfigured producer) **fails** as it must: the leader
    crashes right after answering and returns as a follower without the batch (`{C(B2,18), R(B2,21)}`, 61 runs).
    `SingleRestart` still holds (59 runs). Tests: `tests/integration/tests/kafka_ldfi.rs` (the three-broker ones in
    the full tier).
  - A Raft log-check switch was tried as a seeded bug and removed: with acks=all waiting for every in-sync replica,
    every possible new leader already holds an acknowledged entry, so it cannot break durability here.
- **Lost messages.**
  - Unbounded omissions (`TripleOmissions`, EFF 30) do not converge: Raft sends on nearly every link every round, a
    lost heartbeat changes nothing, so each run suggests ~215 single losses and pairs number in the tens of thousands
    (queue past 220k). Inherent to the superset search on a redundant protocol.
  - The search itself was slow: ~900 SAT calls (~30 s) per run, nearly all minimal models of size one. The encoding's
    gates now give the single-fault hitters directly (`FaultVars::single_hitters`, a bottom-up pass: intersection for a
    conjunction, union for a disjunction; under crash-stop a crash counts at its latest useful tick); the solver only
    enumerates larger models: ~2 s and 4 SAT calls per run. Checked against the solver in a unit test and by mutation.
  - `faults { …, omissions: k }`: at most k lost messages (a totalizer like the crash budget; the run's own omissions
    get variables so they count).
  - A false incompleteness found by `explain`: an end's own close (and bytes a resume releases) is local, done before
    the round's traffic crosses, so it needs the connection as of the round before, not a clock premise on its own
    round's traffic.
  - `TripleOneLoss` (any one lost message, between any two nodes, until round 30): **holds**, 217 runs, complete
    lineage.
- **Retries and idempotence.**
  - The client gains `CLIENT_RETRY` (send again a produce whose connection closed unanswered, Kafka's `retries`) and
    `CLIENT_IDEMPOTENT` (InitProducerId first, in the same write as the topic's Metadata; batches carry the producer
    id, epoch and per-partition sequence), both off by default. It redials the same broker after a close (it rotates
    on a failed dial or a NOT_LEADER answer): rotating on every close took it away from the leader after a reset, so
    a retry did not reach the leader before EOT (which made the first `TripleRetry` run hold, correctly, for that
    client).
  - Guarantees gains "stored once" (a client that read to the end read no record twice).
  - `TripleRetry` (retries, no idempotence, one lost message): **fails** as it must, `{O(B2,C1,34)}`: the answer is
    lost, the connection resets, the batch is stored twice. `TripleRetryIdempotent`: **holds** (264 runs); by hand, the
    retried batch is answered with its original offset and the log holds it once.
- **Larger fault sets (server, 20 + 10 workers).**
  - `TripleLossRestart` (any one lost message and any one crash-restart, down 3 rounds): **holds**, 34 275 runs,
    ~1.6 h. (A first attempt hit the CLI's default 20 000-run budget: no verdict; rerun with `--max-runs 500000`.)
  - `TripleTwoCrashes` (two crash-restarts, so a majority can be down at once): **holds**, 9 283 runs.
  - The workspace fast tier on the server: every failure is environmental and fails the same on the slice's base
    (kcat cannot negotiate with the broker; z3 is not installed): recorded in the pad.
- **Committed offsets.**
  - The client can commit the offset it read for a group (`CLIENT_COMMIT`, `CLIENT_GROUP`), outside group management
    (OffsetCommit v9 at generation -1, which Kafka 4.0 accepts for an Empty group), through the coordinator: it asks
    FindCoordinator v4 (which, as in Kafka, makes the cluster create `__consumer_offsets`; until a partition leader is
    ready it is asked again on the same connection), and goes to the coordinator by its `contact_id` facts. Getting
    the offsets topic and a coordinator takes ~16 rounds, the commit ~7.
  - Guarantees gains "commit kept": an acknowledged commit is held by some broker at the committed offset
    (`current_offset`: committed, or committed and waiting to be applied).
  - `TripleCommitRestart` (EOT 85, offsets replicated on all three, any one crash-restart): **holds**, 337 runs.
- **A broker bug the full tier found** (not LDFI): two `quiesce` messages for one group delivered in one tick made
  `go_quiesced` write two `quiesced` rows for one key, a runtime fault (BLSR002) that took the broker down
  (`kafka3::consumer_groups_with_stock_clients_across_a_coordinator_failure`, 2 of 3 runs). Fixed: only the newest
  quiesce of a tick is applied (1e8e2a1). The synchronous-round world never delivers two messages of one sender in
  one round, so LDFI cannot see such timing bugs: the cluster simulator and the real-process tests cover them.
- **Full tier (server):** every Rust test and all 281 corpus checks pass, except tests that depend on the machine's
  kcat: the server's `/usr/bin/kcat` has librdkafka 2.3.0, older than 2.11.0 (the first with Metadata v13, the
  broker's only Metadata version). The kcat tests now check the version and skip below it;
  `scripts/test-tiers.sh` puts `.tools/bin` first on PATH, where the server links its librdkafka 2.15.1 kcat (with
  it every kcat test passes).
- **A spec can target a program file.** `spec S for e03_raft_election` named a file, not a module, and was "unknown
  module". A one-segment spec target that no loaded file declares as a module is now loaded as a file next to the
  root (after every module the files `use`, so a used module is never mistaken for a file), and resolved as the
  program root with the file's items; spec arguments bind its `param`s, as a deployment does. A file without a
  `program` header is no target (BLS0200 says so). Fixture `fixtures/ldfi/relay{,_specs}.bls`: the store as a
  program, its bug behind `param DURABLE`; both verdicts as expected. `e10_specs.bls` RaftElectionSafety now resolves
  and stops at its asynchronous fault model (TEST-001, not built).
- **Encoding speed (profiled with samply on `TripleTwoLosses`).** The encoder asked the rules where a relation's
  tuples come from, and its lattice columns, through B-tree lookups and a fresh `Vec` per call, for every tuple it
  reasoned about; the lineage graph's place index was a B-tree only ever probed. Both are now dense per relation, or
  hashed: encoding a run's lineage 1.25 s → 0.99 s (−21%), the same hypotheses and queue. What remains is flat: the
  precise negative support's recursion over rules and the memo's hashing of row patterns. A larger gain needs sharing
  encodings across runs.
