# S4 — Raft

Slice 4 of docs/design/SLICES.md, toward the flagship goal (a linearizable key-value store replicated with Raft,
written in Blossom, running as three processes over TCP).

## Evidence

- **LDFI (BENCH-137a–h).** All eight verdicts on e12 match the `.ded` ones at the same bounds, with the same
  falsifiers. The seeded bugs are caught: voting twice, eager commit, and a missing log check. The correct versions
  are certified, the crash cases by exhaustive check. Counterexamples replay and break the named property.
- **The cluster simulator** (`raft_kv.rs`):
  - After every step, an observer checks Raft's safety properties on the nodes' state: election safety, state
    machine safety over the committed prefix, and leader completeness.
  - e11 is linearizable without faults, and under 1–2% message loss and an overlapping nemesis (six seeds on three
    nodes, three on five):
    - partitions: isolations, arbitrary splits, and one-way cuts;
    - crashes: some between a WAL append and its sync, some with downtime;
    - power loss of the leader.
  - A 200-run soak (`sweep`, `RAFT_SEEDS=1-100`, on three and five nodes) finds nothing.
  - A directed scenario drives the stale-leader-state case the review found.
  - Mutation checks catch a commit that ignores the majority, and the review's bug (a leader-completeness
    violation).
- **Three processes over TCP** (`crates/blossom-cli/tests/it/raft3.rs`):
  - Setup: three `blossom run` processes, with every directed peer link through a proxy the test can cut.
  - Nemesis: a seeded mix, with the seed printed on failure and settable with `RAFT3_SEED`.
    - Kills go round a shuffled order, so every server is killed; some servers stay down through later actions.
    - It isolates one server, splits the three at random, or cuts one-way links.
    - Faults overlap until a heal.
  - Result: the whole history is linearizable, typically 500–950 answered operations per run. An earlier version of
    these notes said about 1,300; the review measured 490–964.
  - Mutation check: eager commit is caught.
  - Limit: kill -9 keeps the OS page cache, so a real process never loses a written-but-unsynced WAL record. The
    simulator covers that case.

## Deviations

- **Params fold at compile time.** The program is compiled per deployment, so a `param` is a constant of that
  compilation. The IR's `params` table and the oracle's `Expr::Param` evaluation exist, but nothing emits them yet.
- **`index!` limits.** Only `index!()` is supported: `by` and `per` are BLS0908, and so is mixing it with another
  aggregate column. The lowering is the quadratic reference.
- **`majority` domains.** It takes a role only; a closed unary relation is BLS0908 (LANG-113).

## Review (adversarial, 2026-09-29)

**Critical, fixed.**
- **The bug.** e11 did not reset `match_idx` and `sent` when a node became leader again. Under the relation-level
  `choose_most`, the fresh `0` lost to a larger value left from an earlier leadership. A re-elected leader then
  counted a stale acknowledgement toward commits: it committed entries only it held, and a later leader committed
  different entries at those indexes, losing acknowledged writes.
- **The fix.** A new leader deletes the old rows (`forget_match`, `forget_sent`), which is Fig. 2's "reinitialized
  after election".
- **The tests.** Both test files missed it:
  - the nemesis only isolated single nodes and restarted crashes at once;
  - nothing checked the committed log.

  The simulator now has invariant observers, scripted faults, splits, one-way cuts, downtime, and crashes between
  append and sync. `a_reelected_leader_forgets_its_old_follower_state` reproduces the bug on three seeds.

**Fixed.**

| Finding | Fix |
|---|---|
| `recovered()` was `restarts > 1`, so a crash before the first boot tick synced skipped `bootstrap fresh` forever | A fresh node's first boot tick always writes a WAL record; `recovered()` holds iff a checkpoint or a replayed record exists |
| BLS0402 (a durable write in a plain `bootstrap`) was never checked | Checked in the resolver |
| `rand_range` without a key crashed the compiler | BLS0301 |
| `rand_range` over spans above 2^64, or `u128` bounds above `i128::MAX`, was an internal error | A shared unbiased `prf::uniform_below`; draws for spans up to 2^64 are unchanged |
| `majority` over a plain `Set` crashed the compiler | BLS0300: a quorum counts a set-like lattice |
| `set[self]` into an `LSet<Node<R>>` crashed the compiler unless the type was interned elsewhere | The literal's type is interned for `self`'s `Node<R>` |
| A negative duration binding was accepted | Rejected, as for duration literals |
| A `const` could not use a `param` | `const` and `param` items fold in dependency order; a cycle is BLS0200 |
| A module's `param` took the root's binding of the same name | A module's parameter binds by its qualified name (`c.LIMIT`) |
| bls_e03's "no two leaders" check ran only without faults, and only per tick | Checked over the whole run, with 20% message loss and a crash |
| raft3: fixed nemesis seed (s2 never killed), no overlap, no one-way cuts, and a proxy race (a connection accepted at a cut stayed open) | See the evidence above; the proxy checks and registers under one lock |

**Not reproduced.** `argmax!` inside a correlated `not { … }` is per outer valuation. It is kept as a regression test.

**Open.**
- *Performance:* a follower drops entries that arrive before their predecessor, and each heartbeat repairs the
  gap. Raft is designed for this, but on an unordered network it costs throughput (about 15x in the reviewer's
  measurement). TCP delivers in order per link, so the process runtime rarely hits it. Buffering early entries is
  follow-up work.
- *Performance:* the oracle's per-tick cost grows faster than linearly with the log. The S5 engine is the fix.
- The workload client's retry routing, in both raft3 and the simulator, is plausible but unconfirmed.

## e11's design notes

- **Replication.** The leader tracks `match_idx` per follower, plus a `sent` high-water mark so new entries go out
  in the tick after they are appended. Both start afresh at each election. Each heartbeat resends from
  `match_idx + 1` (at most `BATCH` entries). That prefix was acknowledged in the current term, so the follower's
  consistency check always passes on it.
- **Commit.** An index is committed when a majority stores it and it is of the leader's term. Followers learn the
  commit index from heartbeats whose `prev` matches their log.
- **Apply.** Every server applies committed entries in order, and the server that took a request answers the
  session. A put answers `put_ok`; a get answers the value just before its entry; a delete answers whether the key
  existed. Several entries on one key in one batch resolve by index. After a restart, the old sessions are gone
  (session ids carry the incarnation), so re-applying the log answers nobody twice.
- **No log compaction.** The log grows without bound. The naive oracle re-evaluates views over it every tick, which is
  what step 3 (the fast interpreter) must fix before the benchmark.
