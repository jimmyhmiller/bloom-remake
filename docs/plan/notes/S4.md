# S4 — Raft

Slice 4 of docs/design/SLICES.md, toward the flagship goal (a linearizable key-value store replicated with Raft,
written in Blossom, running as three processes over TCP).

## Evidence

- **LDFI (BENCH-137a–h).** All eight verdicts on e12 match the `.ded` ones at the same bounds, with the same
  falsifiers. The seeded bugs are caught: voting twice, eager commit, and a missing log check. The correct versions
  are certified, the crash cases by exhaustive check. Counterexamples replay and break the named property.
- **The cluster simulator** (`raft_kv.rs`): e11 is linearizable without faults, and over six seeds under 2% message
  loss, network partitions and crash-restarts that lose or tear unsynced writes. It is mutation-checked: a commit
  that ignores the majority is caught.
- **Three processes over TCP** (`crates/blossom-cli/tests/it/raft3.rs`):
  - Setup: three `blossom run` processes, with every directed peer link through a proxy the test can cut.
  - Nemesis: it alternates SIGKILL-and-restart of a random server with isolating each server in turn.
  - Result: the whole history, about 1,300 operations, is linearizable.
  - Mutation check: eager commit is caught. The check first failed to catch it, because randomly chosen partition
    victims never hit the leader; partitions now visit every server in turn.

## Deviations

- **Params fold at compile time.** The program is compiled per deployment, so a `param` is a constant of that
  compilation. The IR's `params` table and the oracle's `Expr::Param` evaluation exist, but nothing emits them yet.
- **`index!` limits.** Only `index!()` is supported: `by` and `per` are BLS0908, and so is mixing it with another
  aggregate column. The lowering is the quadratic reference.
- **`majority` domains.** It takes a role only; a closed unary relation is BLS0908 (LANG-113).

## e11's design notes

- **Replication.** The leader tracks `match_idx` per follower, plus a `sent` high-water mark so new entries go out
  in the tick after they are appended. Each heartbeat resends from `match_idx + 1` (at most `BATCH` entries). That
  prefix was acknowledged in the current term, so the follower's consistency check always passes on it.
- **Commit.** An index is committed when a majority stores it and it is of the leader's term. Followers learn the
  commit index from heartbeats whose `prev` matches their log.
- **Apply.** Every server applies committed entries in order, and the server that took a request answers the
  session. A put answers `put_ok`; a get answers the value just before its entry; a delete answers whether the key
  existed. Several entries on one key in one batch resolve by index. After a restart, the old sessions are gone
  (session ids carry the incarnation), so re-applying the log answers nobody twice.
- **No log compaction.** The log grows without bound. The naive oracle re-evaluates views over it every tick, which is
  what step 3 (the fast interpreter) must fix before the benchmark.
