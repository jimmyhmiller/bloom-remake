## Rules (the Kafka decisions, K1–K7 in KAFKA.md)

- Stock clients must work unmodified: kcat, the Java 4.0 console producer and consumer, and franz-go.
- No Rust translation layer. Everything Kafka-specific is Blossom code. Platform additions must be generic: blobs, the

## Work items, in order

### 0. Role inference (from S6's bugs) — done
- **Build:** `Node<R>` subtyping the way the literature does it. Merges take the join and conjunctions the meet;
  requirements are checked, never inferred from. See LANGUAGE §5.3 and "Item 0" below.

### 1. Blobs (FOREIGN-PROTOCOLS §5, LANGUAGE §16.6)
- **Language:**
  - `Blob` values;
  - `blob_of(b: Bytes) -> Blob`, pure, since the handle is a function of the bytes;
  - `blob.len()`;
  - `blob_read(b, lo, hi) -> Option<Bytes>`;
  - `Part::Blob(b, lo, hi)`.
- **Evaluators:** both evaluators see the node's blob store through one interface. A tick's new blobs are
  collected with its output.
- **Node and store:**
  - a blob store (files in the store directory; `SimFs` in simulation);
  - a tick's new blobs that durable rows reference are synced before its WAL record;
  - recovery re-opens the store;
  - blobs that no durable row references are collected after a checkpoint.
- **Runtime:** a stream write of `Part::Blob` sends the stored bytes without copying them through the engine.
- **Acceptance:** crash-point tests (as in S3) show that no recovered row names a missing blob, mutation-checked.
  Oracle and engine agree.

### 2. Storage that follows change (FOREIGN-PROTOCOLS §6)
- **Build:**
  - incremental checkpoints: chained deltas, with background compaction;
  - deletion at scale: deleting rows costs in proportion to the rows deleted, index maintenance included.
- **Acceptance:** checkpoint cost is flat as retained state grows (a benchmark test like `engine_planner`'s
  flat-work tests), and crash points across the chain lose nothing.

### 3. Record batches (KAFKA.md "Record batches and offsets")
- **Build:**
  - a v2 batch header decoder in Blossom;
  - CRC32C validation through the standard library;
  - offset assignment by writing `baseOffset` and `partitionLeaderEpoch` (both before the CRC);
  - batches stay compressed.
- **Acceptance:** the Rust codec oracle builds batches (including compressed ones) and checks the decoded fields and
  the patched bytes.

### 4. Topics: CreateTopics, DeleteTopics, DescribeConfigs; Metadata with topics
- **Build:**
  - topic ids from the seeded PRF;
  - partitions, all led by this broker;
  - topic configs (`retention.ms`, `retention.bytes` and the defaults the tools read).
- **Acceptance:** `kafka-topics.sh --create/--delete/--describe` and `kcat -L` show the topics.

### 5. Produce
- **Build:**
  - append each batch as a blob-backed durable row `(offset, count, max_timestamp, batch: Blob)` per partition;
  - acks 0, 1 and -1 (all equal on one broker);
  - errors: UNKNOWN_TOPIC_OR_PARTITION, CORRUPT_MESSAGE, and the rest as Kafka answers them.
- **Acceptance:** an acknowledged produce is durable before its response leaves (Invariant B, mutation-checked).

### 6. Fetch and ListOffsets
- **Build:**
  - Fetch with the session id always 0 (KIP-227 allows it);
  - `max_wait_ms` and `min_bytes` parked fetches, completed by new data or a timer;
  - responses built from `Part::Bytes` headers and `Part::Blob` batch ranges;
  - ListOffsets: earliest, latest, and by timestamp.

### 7. Retention
- **Build:** `retention.ms` and `retention.bytes` delete whole batches from the front and advance the log start
  offset; their blobs are collected.

### 8. Clients, checker and the gate
- **Build:**
  - the Blossom client and the Rust oracle client produce and fetch in the cluster simulator;
  - a log checker: every acknowledged produce appears exactly once at its offset, observers agree, and consumers
    see offsets in order with no gaps below the high watermark.
- **Gate:**
  - kcat and the Java console producer and consumer round-trip messages with explicit partitions and offsets;
  - franz-go produces and fetches;
  - kill -9 of the broker loses no acknowledged record, and the log checker validates each run.

### 9. Close the slice
- A corpus pass on both evaluators, and the workspace tests.
- An adversarial review, with its findings fixed.
- These notes completed; a merge commit "Slice 7: a single-node broker".

## Findings and deviations

### Item 0: role inference (done)

S6's review found that inferring `Node<R>` meets at every unification, which is sound only for rule variables:
- in a rule, `let x = if c { a } else { b }` typed `x` as `Node<S>`, so `send … to x` was accepted though `x` could
  be another role's node;
- in functions it surfaced as V8 internal errors.

Asked what the literature says, the answer was MLsub's biunification (Dolan and Mycroft, POPL 2017) and TAPL §16.3.
Merges take the join; a conjunction's variables take the meet; `==` narrows only as a conjunct, which is occurrence
typing's restriction (Tobin-Hochstadt and Felleisen). The user chose to fix it before S7. What changed:

- **Type checker.**
  - Merge points no longer unify. They are *flows*: `if`/`match`, collection elements, `push`, `concat`,
    `unwrap_or`, a fold's accumulator, `++`, and inferred view columns from their alternatives and writers.
  - A flow gives an unknown side the other's shape with fresh positions, so two sides never share a `Node` position.
    `Node` positions are joined by role edges.
  - Requirements are flows with a check: columns written, `to` (now `Node<R>` for a channel to role `R`), call
    arguments, results, struct fields, variant payloads, `let x: T`.
  - Comparisons (`==` in expressions, `!=`, `contains`) relate their operands without constraining roles. `==` as a
    conjunct of a rule body stays an equation.
  - Atoms under `not`, `any` and `forall` relate rather than bind.
  - A read of an inferred view column takes a copy of the column, so the reader's equations do not narrow it.
  - `self` in a placed rule is `Node<R>`.
  - After the shapes are solved, roles are solved over the edges. The least fixed point is taken: a position's role
    is the glb of its own type and the lub of what flows in. Requirements are then checked.
  - An integer flow is an equation, since integers carry no roles. A merge whose source is otherwise unconstrained is
    settled as an equation.
  - A requirement gives an unknown source its shape at once, which decides a lattice lift, as before. The positions
    it creates are *free*: their role is only what flows in, so a `None` or `[]` (nothing flows in) fits any
    requirement. A free position joined by an equation to a declared type becomes a source.
- **IR validator.** It computes joins for `if`, `match`, collections, `push`, `concat` and `unwrap_or`. A fold's
  accumulator is the closure's first parameter. A closure parameter may be wider than what is passed. A rule's
  `x := e` may narrow `e`'s roles, since the body is a conjunction; the shapes must agree.
- **Tests.**
  - `blossom-front` `node_roles_join_at_merges_and_meet_only_in_conjunctions`, 12 cases: the unsound program
    rejected; narrowing by an atom and by a conjunct `==` accepted; nothing narrowed under `not` or by an `==` inside
    an expression; the function cases compiling; no flow typing in functions; a `Node` passed as a `Node<A>`
    rejected; view columns as joins.
  - Mutation-checked: typing `if` by unification again fails it.
- **Checks:**
  - the corpus unchanged on both evaluators: core 193, lattices 47, async 36, net 3, lprov with the known failures,
    ldfi 92 of 96;
  - the workspace tests pass, e11 and e12 included.

### Item 1: blobs (done)

What landed is in FOREIGN-PROTOCOLS §5a. The decisions:
- **`Blob::of` is pure.** The handle is BLAKE3 plus the length, and the evaluator hands the bytes over with the
  tick's output. The engine evaluates only changed rows, so it may report a blob once where the oracle reports it
  every tick. The node therefore keeps created blobs in a cache rather than relying on seeing them again.
- **Durability is per referencing record.** A blob is written only when a durable row first references it, and
  before that record syncs. Blobs that are never stored never touch the disk.
- **Collection needs every root.** A blob a WAL record after the checkpoint references can come back in a recovery
  even if a later, unsynced tick deleted its row. So the roots include every blob handed to the driver since the
  checkpoint, as well as the running node's rows and output.
- **A write of a blob range outside the blob** is refused like a bad `seq`: the connection closes and its `closed`
  event says why (`HostRequest::Refused`).
- **Tests.**
  - `node_blobs.rs`, on the oracle and the engine:
    - 12 chunks stored as blobs, with checkpoints; crash at every durable syscall under lost, torn and mixed fates.
      Every recovered row's blob is in the store with its bytes, and every acknowledged chunk is recovered. Each
      acknowledgement is the blob's bytes, read by the host through `Part::Blob`.
    - After a restart, three rows are deleted and a checkpoint collects exactly their blobs. A kept blob is read
      back through the stream afterwards.
  - `bls_functions.rs` `blobs_are_made_measured_and_read_on_both_evaluators`: `Blob::of`, `len` and `read` in rules
    and functions, and blobs made in earlier ticks read whole, on both evaluators.
  - Front end: a `Blob` in a channel or a host input is BLS0908.
  - Mutation-checked:
    - making the blobs durable after the WAL sync instead of before loses a row's blob at a crash point;
    - skipping the collection keeps the forgotten blobs.

### Item 2: storage that follows change (done)

FOREIGN-PROTOCOLS §6a has what landed. The decisions:
- **Layers, not segments.** A layer is the net change since the previous checkpoint, in the WAL's own delta
  encoding. Its size follows the change whatever the relation's shape. Segmenting relations would not help a log
  that appends to one relation.
- **When to compact.** Compaction happens when layers outgrow the image or reach 16, so the work amortizes.
- **Full images off the engine thread.** The runtime sends a copy of the image's row handles to the checkpoint
  thread, which owns its own codec. The engine thread's cost for a full checkpoint is copying `Arc`s.
- **Tests.**
  - `node_checkpoints.rs`:
    - A workload of inserts and deletes over two incarnations, checkpointing every three chunks. After every
      checkpoint, a clean recovery finds exactly the released rows. Over ten layered checkpoints happen, and the
      chain compacts.
    - Over 400 chunks, which grow the state 80-fold, each new layer stays the size of its change.
  - `engine_deletes.rs`: deleting 100 rows from a table of 20,000 examines no more rows than from one of 2,000, by
    key and by a range sweep.
  - The crash-point suites (`node_blobs`, `node_streams`, `node_kvs`) now recover through layered checkpoints.
  - Mutation-checked: layering after a recovery that replayed WAL records, and keeping deletes of rows inserted
    since the checkpoint in the layer, each fail the recovery test.

### Item 3: record batches (done)

- **`examples/kafka/records.bls`:**
  - the magic-2 header decoder;
  - `split_batches` for a records field, which at most `len / 61` batches can fill;
  - `batch_ok`: magic, length, sane counts, and a CRC32C over `attributes..end` through the standard library;
  - `with_offsets`: writes `baseOffset` and `partitionLeaderEpoch`, both before the CRC's cover.
- **A length read from the wire is checked before any arithmetic** (a batch length under the 49-byte minimum is
  malformed). This is the lesson of S6's review.
- **`kafka_records.rs`**, on both evaluators, against `kafka-protocol`'s encoder and decoder: 60 random fields of
  1–3 batches, uncompressed and "compressed". A compressed batch's content passes through untouched, as the broker
  never decompresses. Some fields have a corrupted byte, some are truncated.
  - Splitting, soundness and truncation match.
  - An assigned batch changes only in its offset and epoch bytes. An uncompressed one decodes, checksum included,
    with its records at the new offsets.
  - Mutation-checked: dropping the CRC check fails it.

### Item 4: topics (done)

- **Files.**
  - `examples/kafka/topics.bls`: CreateTopics v7, DeleteTopics v6 and DescribeConfigs v4 codecs; Kafka's topic
    rules (legal names, `.`/`_` collisions, partition and replication checks, the configurations this broker
    supports); topic ids.
  - `examples/kafka/topics_node.bls`: the durable `topic`, `log_end` and `log_start` tables and the handlers.
  - `metadata.bls` describes topics, and auto-creates them.
  - ApiVersions advertises the three new APIs.
- **One writer per tick.** Requests from several connections are answered in one tick, and their answers must fit
  one order.
  - The first design took a winner per topic (the least connection). The history checker found why that is not
    enough. Take a DeleteTopics that misses a topic another request creates, and a Metadata request that sees both
    that topic and one the deletion removes: there is no order for the three.
  - Now a tick changes the topics for one request, the oldest (by arrival, then connection) that creates or
    deletes. Other writing requests wait at the head of their queues.
  - Every other request answered in the tick sees the state after the writer, so the tick's order is the writer,
    then the rest.
  - A Metadata request that would auto-create a topic the writer just deleted also waits (the second anomaly the
    checker found).
- **Topic ids** are two `rand` words keyed by the name. Kafka's `Uuid.randomUuid` redraws the zero id, the
  metadata topic id (0, 1), and ids whose base64 form starts with `-`. Here the top bit is cleared (so no id starts
  with `-`) and the two reserved ids map to (0, 2) and (0, 3).
- **Deviations from Kafka, all documented in the code.**
  - Metadata answers an auto-created topic at once, where Kafka answers LEADER_NOT_AVAILABLE until the controller
    has made it. Clients accept either.
  - A Metadata request naming topics whose names collide auto-creates none of them.
  - A CreateTopics naming colliding topics refuses them all with INVALID_TOPIC_EXCEPTION.
  - DescribeConfigs describes the eight topic configurations this broker knows, and no broker configuration.
  - Duplicate entries in a Metadata request are answered once each.
- **Kafka behaviour matched after the checker or the tools caught it.**
  - An empty DescribeConfigs key list means all keys.
  - A DeleteTopics entry by name whose topic another entry names by id is INVALID_REQUEST.
- **Platform additions (generic).**
  - `collect!(e)`: the frontend, and `CollectVec` on both evaluators. Its value is once per valuation, in canonical
    order. A `per` driver gives `[]`. `by` stays a clear not-implemented error.
  - `rand(k…)`: the frontend, the oracle and the engine, with the PRF of LANGUAGE §15.1.
  - `s.parse_i64()` replaces this slice's earlier `to_i64`, matching Appendix B's name.
  - The runtime's engine thread gets a 64 MiB stack (`blossom_node::EVAL_STACK_BYTES`), and `.cargo/config.toml`
    gives test threads the same. The CreateTopics decoder nests about 30 closures, and debug frames (oracle
    `eval` 6.7 KB, engine `eval` 14.8 KB) overflowed Rust's 2 MiB default.
- **Fixed on the way: the cluster simulator's error for a program error.** A node's failed tick (BLSR001 and the
  like) was wrapped as "internal error (a bug in Blossom)". It is now `SimError::Node` with the node, the tick and
  the program's error, as the runtime halts the node. Only a failure of the node machinery is internal.
- **Open: an evaluation depth bound.** Blossom has no recursion, so a program's evaluation depth is bounded by its
  text. Nothing checks that bound against the stack yet, so a deep enough program overflows it and aborts the
  process rather than failing with a diagnostic. The fix is a compile-time bound over the call DAG (expression
  nesting plus callee depth, closures counted inside the library call that applies them), with the thread stacks
  sized for it. To be done before the slice closes.
- **Tests.**
  - `kafka_codec.rs`: requests Rust encodes (CreateTopics, DeleteTopics, DescribeConfigs) decode in Blossom. The
    responses Blossom encodes, Metadata with topics included, decode in `kafka-protocol`. The S7 captures of all
    six clients decode.
  - `kafka_topics.rs`: Rust clients send random admin requests; the history must be linearizable against a
    sequential model of Kafka's rules written in the test.
    - Across broker crashes and dropped connections (8 seeds).
    - With requests arriving together over three names, so creations and deletions race within ticks (10 seeds).
    - At the end, each topic has exactly its partitions' offsets.
    - Mutation-checked:
      - volatile topic tables lose the topics at the first crash;
      - letting every writer through makes two `topic` rows share a key (BLSR001);
      - answering a waiting Metadata request is not linearizable.
  - `kafka_gate.rs`, against the broker over TCP:
    - `kafka-topics.sh --create` (with `--config`), a refused second create, `--list`, `--describe` (partitions,
      leader, configs) and `--delete`;
    - `kafka-configs.sh --describe`;
    - `kcat -L` showing the topics.
  - `bls_aggregates.rs`: `collect!` (per valuation, with a driver, over pairs) and `rand` (stable per key and tick)
    on both evaluators.
