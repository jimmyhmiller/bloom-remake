## Validation

Every verdict was confirmed by exhaustive search, except Flux 22/21/1 (beyond it; see below):

- delivery, commit, Kafka, Nemo, BENCH-135 and Raft: exhaustive search of every configuration, all agree;
- Paxos 8/3/1 (5162 merged states) and 7/6/1 (970025), bully 10/9/1 (231540): no counterexample;
- Raft additionally at 12/6/1, 10/7/1 and 14/8/1 (correct program): no counterexample;
- Flux: exhaustive at 8/4/1 (no counterexample); 22/21/1 rests on a construction argument: the egress delivers
  sequence number S only when S = 1 + the highest delivered number (1 when none), each delivered tuple carries the
  data the ingress assigned to S and nothing else can reach the egress, so no run delivers a wrong, duplicate or
  out-of-order tuple, under any fault. The lineage search finds no counterexample within its run budget.
- Every stated falsifier set equals the exhaustive Appendix-B-minimal set; every oracle expectation holds on the
  checker's evaluator.
- The final checker (commit "checker models Molly's aggregate guard") was rerun over every case but BENCH-133b–d:
  93 cases, 0 problems. Those three long searches ran on the checker before that commit, which differed only in
  dropping an aggregate row whose first column is not a node; in paxos, bully and Flux every aggregate head's first
  column is the rule's location, which the guard already requires to be a node, so both versions evaluate those
  programs identically.

Reproduce with `python3 -B tests/corpus/ldfi/tools/ldfi_ref.py check [case …]`.

## Deviations from the spec, and why

1. **3pc at 8/0/2 is `counterexample`** (BENCH-131p), where FEATURES BENCH-131 says "no CE at 8/0/1 or 8/0/2". The
   three-phase commit the paper describes (the coordinator aborts when it detects a failed participant; precommitted
   participants roll forward to commit on timeout; Figure 9) violates agreement with two crashes and no loss:
   participant a crashes after voting and before acking, the coordinator times out on the missing ack, decides abort
   at step 6 and crashes at step 6 before its abort leaves; b and d commit at 7. The decision precedes the crash, so
   this holds under CR-20's crash semantics as well as MollyContinue. The same schedule (`--crash a:3,C:6`) violates
   agreement for Molly's own `3pc.ded`, and exhaustive search of it finds violations at 8/0/2. Molly's test table
   reports none, so Molly's search did not reach them; a search without negative support misses them too (the abort
   decision has no message in its positive lineage), while ARCHITECTURE's search (conservative negative support,
   CR-31) finds one in 10 runs. A complete LDFI (Appendix B, TEST-029) must report it, so the golden verdict is the
   true one. 8/0/1 stays `no_counterexample`, and 9/7/1 `counterexample`, as published.
2. **Run counts not pinned for paxos-synod (173), bully-le (2) and Flux (187)**, which BENCH-136 lists. A run count
   is a property of a program; each of these was measured on a program the corpus cannot reproduce:
   - Molly's `paxos_synod.ded` lets acceptors take accept requests below a promised ballot; the lineage-driven search
     finds a concrete agreement violation at 7/6/1 (`{O(b,a,3), O(b,c,3)}`: ballot 5 chooses foobar, then ballot 7,
     promised before those acceptances, chooses peter), so its published certification is a search miss.
   - The bully-le program is not published and not identifiable (R06 §13); `util/leader.ded` has agreement
     violations at 10/9/1 (exhaustive).
   - On the four nodes Figure 13's Combinations column implies, the repository's `flux_clusterpairs.ded` has an empty
     `pre` at EOT in its failure-free run (the membership facts `pre` reads persist only at the non-node `Z`), so the
     certification is vacuous.
   The corpus certifies re-derived programs for all three (BENCH-133) and records the counts, with these reasons, in
   `golden/run_counts.toml`. The other nine counts are pinned (BENCH-136a–i).
3. **The delivery family's spec** (`delivery_spec.ded`) states Molly's delivery oracle with a monotone `post`
   (per-node: "N holds P") and the broadcaster-exclusion and crash conditions in `pre`. The file proves that it
   judges every run exactly as Molly's spec does on the paper's fully connected input. With `notin missing_log` in
   `post`, conservative negative support (CR-31) makes every earlier log fact a possible cause of the negated goal,
   which multiplies hypotheses far beyond the published counts (retry-deliv 4/2/1: 6 runs instead of 3;
   classic-deliv 5/3/0: 22 instead of 5, on Molly's original programs). Figure 3 verbatim is kept in one case
   (BENCH-130r) so the negative-support path stays under test.
4. **FF-certification of redun-deliv at 6/3/1** (FEATURES BENCH-130: "the failure-free lineage alone must certify
   it") is pinned as its own case, BENCH-130q, with `runs_max = 1` and TEST-031 in its features (until M9). The claim
   holds only when hypotheses that also falsify `pre` are skipped before they run (LDFI §4.3's optimization, TEST-031,
   P1): crashing the broadcaster at time 1 falsifies every post goal and is vacuous. Without the pruning the core loop
   takes 4 runs; the verdict itself is BENCH-130k (until M8).
5. **FF oracle cases do not include the specification**: pre/post become an implicit spec (ARCHITECTURE §13.12) whose
   evaluation needs later work packages; the failure-free cases check the protocol and pin protocol relations.
   PLAN §8 asks for "[[expect]] rows for post"; `post` is a spec relation, not located at a node, and schema v1's
   node-keyed `[[expect]]` cannot name it. The Nemo case studies carry their spec in the same file as the protocol,
   so no failure-free case is derived from them; their LDFI cases pin their verdicts.

## Judgement calls (for the M6.7/M8.8 triage)

- **Re-derivation choices.** classic-deliv relays every copy it receives (the paper: "it has infinite behaviors like
  the protocols submitted in Rounds 2-3"). redun-deliv relays at the step it receives the entry, as Figure 6 draws it
  (support `O(A,C,1) v O(C,B,2)`); §3.1.3's `bcast(N,P)@next :- log(N,P)` relays one step later and has a
  counterexample at 11/10/1, where Figure 13 certifies redun-deliv. The commit protocols follow the paper's
  descriptions with the timings of Figure 9 (canCommit? at 1, votes 2, preCommit 3, acks 4, coordinator decision 6,
  participants 7) and Molly's termination check (at least two deciders once a participant prepared). Kafka's client
  knows the leader statically so the failure-free acknowledgment reaches it at 6; Figure 12 gives 6/4/1 as the
  minimal counterexample parameters and Figure 10 shows the leader crashing at 5 (the repository's `kafka.ded` acks
  at 7, which makes 6/4/1 vacuous). Paxos is textbook synod with learners and Paxos agreement (a single learned
  value); Molly's spec (every value accepted by a correct acceptor agrees) is stronger than Paxos guarantees. The
  bully election uses one vote per node and a majority (agreement by quorum intersection). Flux's spec is its safety
  guarantee (no loss, duplication or reordering in what the egress delivered). Raft is split into modules so each
  seeded bug replaces one rule, with the correct program as the control on the same input and failure spec.
- **Hidden parameters.** Figure 13 omits crash bounds and node counts. Molly's grossEstimate reproduces the
  Combinations column exactly for 3 nodes and 1 crash (redun, ack, paxos, bully) and 4 nodes and 1 crash (Flux), and
  for no other node count up to 8 or crash bound; those are the configurations used. The same formula reproduces all
  seven Figure 12 entries and Molly's eight unit-test values (`golden/gross_estimate.toml`).
- **Stated falsifier sets** are given only where a source states them: simple-deliv (Figure 4a, both receivers),
  retry-deliv 4/2/1 (§3.1.2's "crash after reaching one node"), the Netflix toy, the §4.3 formula (four failure specs
  that isolate each disjunct), the provenance `_net` variants and the negative-support test. Each is the exact
  Appendix-B-minimal set (clock-fact comparison, ARCHITECTURE §8.3), which differs from "minimal models" (below).
- **Nemo repairs.** The repaired programs are not published; they implement the repairs the Nemo paper describes
  (ack_log from every replica as the success condition; ZK-1270's `success(L) :- sent_flag(L), ack(F)` with the ack
  remembered). "After the repair, no CE" is stated for pb_asynchronous; for ZK-1270 the paper says the repair "is
  confirmed". CA-2083's repair is described but not required by FEATURES and not encoded.
- **Provenance counts** (BENCH-135) cannot be stated in a manifest; the `_net` variants make them observable:
  `runs_max = 2` for two firings or two derivations pins complete lineage (TEST-023), and one falsifier per aggregate
  contributor pins the conjunctive aggregate encoding (TEST-024).
- **Conventions** (for M5.2's runner; `tests/corpus/ldfi/README.md`): `.ded` deployments use `role = "Node"`;
  `[run] ticks = n` runs ticks 0..n−1; `[[expect]]` rows omit the location column; `falsifiers` is the union over post
  goals of each goal's Appendix-B-minimal falsifiers; `runs_max` counts the failure-free run, up to the first
  counterexample or to exhaustion.
- **Crash times** considered by the checker are 1..EOT−1 (Molly's hypothesis space); a crash at EOT removes no
  message and would only change the crash oracle.

## Bugs

Problems in documents and code this WP does not own. Each has a reproducer in the corpus; "owner" is the WP that
implements the affected feature.

1. **ARCHITECTURE §8.3 has no hazard for the crash oracle** (owner: M8.1, blossom-ldfi). A negated
   `notin crash(_, N, _)` premise gets conservative negative support, and `crash` has no rules, so the premise is
   unfalsifiable. The Kafka durability violation (BENCH-132a/c) needs a crash that removes no message on the
   outcome's lineage (the leader crashes after acknowledging) and is then unreachable by lineage: the reference
   search without such a hazard exhausts its hypotheses without a counterexample (469 runs at 7/4/1, 85 at 6/4/1).
   Sound fix: `Neg{crash(_, n, _)}` ↦ K(n, EOT−1) (crashing n at the latest admissible time falsifies the premise);
   with it the counterexample is found in 128 runs (7/4/1) and 52 (6/4/1). Reproducer: BENCH-132a.
2. **ARCHITECTURE §8.3's claim "minimal models are exactly the Appendix-B-minimal falsifiers" is false** when an
   omission can replace a crash (owner: M8.1; its required test `minimal_models_are_appendix_b_minimal`). For the
   §4.3 formula with EFF 3 and two crashes, `{K(a,2..), O(b,c,1)}` is a minimal model, but it removes a strict superset
   of the clock facts `{O(a,c,2), O(b,c,1)}` removes. The corpus follows §8.3's stated definition (comparison by
   removed clock facts); an implementation must convert models to fault sets and drop those whose removed-clock set
   strictly contains another's before comparing falsifier sets. Reproducers: BENCH-135b and BENCH-135e.
3. **TEST-031 (vacuity pruning) is unsound if `pre`'s hazard uses conservative negative support** (owner: M9.4). The
   over-approximation claims that a lost registration falsifies Kafka's acknowledgment (it makes it arrive earlier),
   so the real counterexample is pruned as vacuous (reference: 1 run, wrong verdict). Only certain falsification may
   prune: `pre`'s positive lineage plus the crash oracle. Reproducer: BENCH-132c with TEST-031.
4. **FEATURES BENCH-131, "3pc: no CE at … 8/0/2"**, is contradicted by the protocol (Deviation 1). Reproducer:
   BENCH-131p; the run is `--crash a:3,C:6`.
5. **FEATURES BENCH-136's counts for paxos-synod, bully-le and Flux** refer to programs the corpus cannot reproduce
   (Deviation 2); the Molly paxos program is also wrong (Deviation 2).
6. **FEATURES BENCH-130's FF-certification claim** needs TEST-031 (P1) (Deviation 4).
7. **LANGUAGE §21.1 says "node names are the lowercase constants in location position"**, but Molly and Nemo name
   nodes `"C"`, `"Z"`, `"FF"`, `"LL"`, `"A"` (owner: M3.6, front::ded). The vendored Nemo files and the commit and
   Kafka cases need upper-case node names; the node set is the failure spec's `nodes`.
8. **R06 §12.6's expected falsifiers for the §4.3 formula** ("include {C(a,1 or 2), O(b,c,1)} and {O(a,c,2), C(b,1)}")
   are minimal models, not Appendix-B-minimal falsifiers (see 2). BENCH-135b–e give the exact sets for four specs.
9. **The Soufflé provenance paper's Figure 10** attributes the iteration-3 height update of `vpt(b, l1)` to rule r3
   through `alias(c, c)`, which r4 (`Var1 != Var2`) cannot derive (recorded in `golden/provenance.toml` for M5.7).
10. **Molly's solver-normalization test** removes an omission whose receiver crashes at the delivery step
    (`O(B,A,1)` with `C(A,2)`); that matches the Frozen view but not MollyContinue, where a crashed node still
    receives (ARCHITECTURE §8.4 already scopes the receiver rule to Frozen). Both results are in
    `golden/fault_normalization.toml`.

## Notes for the work packages that consume the corpus

- **M3.6 (the `.ded` frontend).** Molly evaluates a rule only where its location (the first column of its first body
  predicate) is a node; `_` there matches any clock, so such a rule is unguarded. For a head aggregate the guard applies
  to each valuation of the body, not to the aggregated row: Molly rewrites clocks before it splits aggregates, so the
  clock atom stays in the bindings rule, and a group keyed by a non-node still yields its row (CA-2434's
  `votes(Data, count<Node>)`, BENCH-134g, depends on this). The corpus's own programs are written so
  that this clock guard and a global spec engine agree (every rule's first body predicate is node-located or `_`).
  `include` is resolved relative to the including file; only `program.ded` includes, so Molly's "relative to the first
  file" rule gives the same result. Absolute-time body atoms (`p(…)@1`) occur only in `pre`/`post` and their helpers.
  Protocol rules respect body locality; only spec rules join across nodes or read `crash`. `count<X>` counts distinct
  values of X per group (LANGUAGE §10.1); no corpus aggregate depends on whether bindings or values are counted.
- **M8.1 (LDFI).** Besides Bugs 1 and 2: the reference search reaches the pinnable Figure 12 counts only with a
  queue ordered by (fault count, number of removed clock facts, canonical order), which tries a crash at its latest
  useful time first; with (fault count, canonical order) 2pc 5/0/1 takes 3 runs where Figure 12 publishes 2.
- **M9.4 (LDFI P1).** Reference counts for the pinned BENCH-136 cases (default = ARCHITECTURE §8.3–§8.5 with CR-31;
  vacuity = plus TEST-031 on pre's positive lineage; no-neg = negative support off, which reproduces Molly's delivery
  counts exactly but misses the 3pc and Kafka counterexamples):

  | Case | runs_max | default | vacuity | no-neg |
  |---|---|---|---|---|
  | 136a simple-deliv 4/2/0 | 2 | 2 | 2 | 2 |
  | 136b retry-deliv 4/2/1 | 3 | 3 | 2 | 3 |
  | 136c classic-deliv 5/3/0 | 5 | 3 | 2 | 3 |
  | 136d 2pc 5/0/1 | 2 | 2 | 2 | 2 |
  | 136e 2pc-ctp 8/0/1 | 3 | 2 | 2 | 2 |
  | 136f 3pc 9/7/1 | 55 | 36 | 36 | 8, misses the CE |
  | 136g Kafka 6/4/1 | 38 | 52 | 25 | 10, misses the CE |
  | 136h redun-deliv 11/10/1 | 11 | 11 | 1 | 11 |
  | 136i ack-deliv 8/7/1 | 673 | > 5000 | > 5000 | 831 |

  ack-deliv is the paper's Figure 5, so 673 is a like-for-like target; conservative negative support on the
  protocol's own `notin ack` generates far more hypotheses than Molly's search did. Meeting it needs negative support
  more precise than CR-31's rule (for example tuple-level causes, TEST-051), the parity filter alone does not help
  (measured). The unpinned counts show the same effect: Paxos 7/6/1 > 4000 with and without vacuity pruning (271
  without negative support), bully 10/9/1 1000 without negative support.
