# S18 — a fast browser page

The user (2026-10-06), after the TodoMVC benchmark (docs/dev/todomvc-bench.md) put Blossom at 1482 ms against
6–72 ms for the JavaScript frameworks: "let's start here with incremental stuff and make this fast". The user-defined
lattices slice planned as S18 moves to S19.

## What was built

- **The benchmark.** `scripts/bench-todomvc.sh` runs the Blossom TodoMVC as two Speedometer 3 suites beside
  Speedometer's own TodoMVC suites (its runner and steps, headless Chromium); the host has a `?bench` mode.
  `examples/todomvc_work` (blossom-web) runs the same workload natively and prints time, rounds and work per rule.
- **Handler relations hold only what is read.** A handler's header relation (`$when`) and each block's (`$if`,
  `$for`) hold only the variables their statements read; a block or a statement reads its parent through a projection
  onto what it uses (`Lowerer::through`, a `Projection` construct, shared per relation and kept variables). A header
  count or typed text that changes no longer re-derives every row of the page below it. Head aggregates keep every
  variable (they count valuations).
- **The page is incremental.** `Engine::changes_of` gives a relation's row changes in the last tick; `Page::apply`
  re-checks only what they touch (the same errors as before, re-checked each round while they last), and
  `take_patches` emits patches in proportion to the change. `Patch::Place { parent, id, before }` replaces the whole
  child list: an element is placed only when it is new, moved, or under a new parent, last sibling first.
- **The inspector's history keeps changes.** It keeps the state the oldest kept round started from and each round's
  changes, and rebuilds a round's starting state when asked, instead of copying the state every round.
- **TodoMVC** finds an event's todo through views from element ids (`toggle_of`, `destroy_of`, `label_of`): an index
  lookup, not a string comparison against every todo.
- **The host** applies a placement with one `insertBefore` (it re-appended every child of a list, and searched the
  list for each: O(n²) per list).
- Smaller: the engine keeps each literal's dependency position in its plan and a rule evaluation's join orders in a
  short list; the page shares the output rows' strings and hashes its id-keyed maps.

Browser 1482 → 52.8 ms (React 20.5, jQuery 75.5); native 968 → 20.7 ms.

## Decisions made on the way

- The new placement patches are checked against the page itself, in a model of the host's DOM with node identity
  (every round's patches must build exactly the page). That model showed the old whole-list comparison never placed
  an element replaced (a new tag) under a parent whose list of ids stayed the same: its new node stayed detached.
  Fixed by the placement patches.
- Projection is exact for sets; it is skipped under head aggregates, which count valuations.
- `Page::ids` returns the ids sorted (the page's maps are hashed; no order is read from them).

## Known limits

- The remaining gap to React is the engine's work per event in WebAssembly (about 100 µs: B-tree stores of rows of
  values, string comparisons and allocation), and two rounds per event (a write shows in the next tick).
- `?bench=persist` (the host's default) saves the whole durable state after every event.
